## 들어가며

Client Prediction은 내 입력을 즉시 적용하면서도 서버 권위를 유지하는 구조다. 클라이언트는 미래를 잠시 빌리고, 서버 snapshot이 오면 그 빚을 reconciliation으로 정산한다.

## 1. 입력 command와 pending 큐

입력은 순서 번호를 가진 command로 만든다. 클라이언트는 입력을 서버로 보내는 동시에 로컬 상태에 적용하고, 서버 확인 전까지 pending 큐에 둔다.

pending 길이는 대략 RTT × tick rate에 비례한다. 이 값이 계속 자라면 서버 응답이 멈췄거나 클라이언트 시계가 앞서는 신호다.

## 2. 클라이언트와 서버 경로

Scene은 두 이동 함수를 둔다.

```cpp
float ClientApply(float x, int input) const;
float ServerApply(float x, int input) const;
```

정상 상태에서는 같은 규칙을 사용한다. `server wall` 토글처럼 서버만 아는 장애물을 추가하면 예측이 의도적으로 틀리고 보정이 발생한다. 이는 실제 게임에서 클라이언트가 모르는 동적 충돌을 단순화한 모델이다.

## 3. Reconciliation

서버 응답에는 권위 위치와 마지막 처리 입력 번호가 들어 있다.

1. 클라이언트 위치를 권위 위치로 되돌린다.
2. 확인된 pending 입력을 버린다.
3. 남은 입력을 다시 적용한다.
4. 보정 크기를 기록한다.

시퀀스가 wrap될 수 있다면 단순 `<=` 대신 wrap-safe 비교가 필요하다.

## 4. 표시 상태 분리

시뮬레이션 상태는 즉시 권위 결과로 고쳐야 한다. 화면 위치는 그 결과를 부드럽게 따라갈 수 있다. 두 상태를 섞으면 smoothing된 틀린 위치 위에 입력을 다시 적용해 오차가 지속된다.

## 5. 검증 실험

1. 예측 ON/OFF의 입력 반응 시간을 비교한다.
2. latency를 올려 pending 입력 수가 비례해 늘어나는지 본다.
3. server wall을 켜 평균 보정량과 snap 순간을 본다.
4. prediction OFF에서 보정은 없지만 입력 지연이 RTT에 가까운지 확인한다.
5. 긴 실행에서 pending 큐가 누수 없이 정리되는지 본다.

Prediction의 성공 기준은 보정이 전혀 없는 것이 아니라, *보정이 작고 드물며 항상 서버 상태로 수렴하는 것* 이다.

---

## 결론

입력 command에 시퀀스를 부여하고 클라이언트가 먼저 적용한 뒤, 서버가 승인한 상태 위에 미확인 입력만 재적용하는 reconciliation 경로를 구성했다. 권위 시뮬레이션 상태와 화면 표시 상태를 분리해 smoothing이 게임 규칙을 오염시키지 않게 했다.

현재 예제는 단순한 단일 개체 운동과 제한된 시퀀스 범위를 가정한다. 충돌하는 다수 개체, 누락된 command의 재전송, wrap-safe 비교, 치트 검증은 이 모델의 보장 범위 밖이다.
