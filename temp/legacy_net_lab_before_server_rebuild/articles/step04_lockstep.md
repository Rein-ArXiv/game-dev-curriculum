## 들어가며

Lockstep은 상태를 보내지 않고 입력만 공유한다. 모든 참가자가 같은 초기 상태와 같은 입력을 같은 순서로 실행하면 상태도 같다는 전제다. 대역폭은 작지만 결정론이 깨지는 순간 전체 월드가 갈라진다.

## 1. 두 시뮬레이션

Scene은 같은 초기 입자 배열을 가진 `simA_`와 `simB_`를 매 tick 동일하게 진행한다. 정상이라면 모든 입자의 위치와 속도가 계속 일치해야 한다.

렌더링은 한쪽 결과만 그려도 되지만, 검증은 양쪽 전체 상태를 비교해야 한다.

## 2. 상태 해시

매 tick 상태를 정해진 순서로 직렬화해 FNV-1a 해시를 계산한다. 구현은 위치와 속도의 `float` 비트 패턴을 모두 해시하므로 한 비트 차이도 탐지한다. 해시가 다르면 상태가 다르다는 강한 신호지만, 같은 32비트 해시가 상태 동일성을 수학적으로 증명하지는 않는다.

```cpp
uint32_t LockstepScene::HashSim(const std::vector<Particle>& particles) const {
    uint32_t hash = 2166136261u;
    auto mix = [&](float value) {
        uint32_t bits = 0;
        std::memcpy(&bits, &value, sizeof(bits));
        for (int byte = 0; byte < 4; ++byte) {
            hash ^= (bits >> (byte * 8)) & 0xFFu;
            hash *= 16777619u;
        }
    };
    for (const Particle& p : particles) {
        mix(p.x); mix(p.y); mix(p.vx); mix(p.vy);
    }
    return hash;
}
```

주의할 점:

- 컨테이너 순회 순서를 고정한다.
- 패딩 바이트를 그대로 해시하지 않는다.
- float을 허용하면 연산 순서, FMA, 비정규수, 컴파일러 옵션의 플랫폼별 차이를 통제한다.
- 해시는 디싱크 탐지용이지 암호학적 무결성용이 아니다.

## 3. 디싱크 주입

토글을 켜면 한쪽 시뮬레이션의 속도 비트를 바꾸는 작은 오차를 넣는다. 처음에는 화면상 차이가 거의 없어도 속도까지 해시하므로 즉시 갈라지고, 시간이 지나면 시각적 차이가 커진다.

첫 디싱크 tick을 기록하면 입력 로그와 상태 덤프를 그 지점부터 비교할 수 있다.

## 4. 결정론의 조건

lockstep이 요구하는 것은 “비슷한 결과”가 아니라 “같은 비트 결과”에 가깝다.

- 고정 tick과 고정 실행 순서
- 결정론적 난수 시드
- 정렬된 엔티티 순회
- 플랫폼별 부동소수점 차이 통제
- 외부 시계와 비결정 입력 제거

## 5. 검증 실험

1. 주입 OFF에서 장시간 해시가 일치하는지 본다.
2. 주입 ON에서 첫 디싱크 tick이 재현되는지 본다.
3. 입자 수를 바꿔 해시 비용과 프레임 비용을 측정한다.
4. Reset 후 같은 초기 해시로 돌아오는지 확인한다.
5. 시뮬레이션 순회 순서를 바꿨을 때 결과가 갈리는지 실험한다.

Lockstep의 핵심 비용은 네트워크가 아니라 *결정론을 유지하고 깨진 순간을 재현하는 공학* 이다.

## 결론

동일 입력을 소비하는 두 시뮬레이션의 정규화된 상태 해시를 tick마다 비교하고, 의도적인 비결정성 주입이 처음 발현한 tick을 재현하도록 만들었다. 결정론 요구를 막연한 규칙이 아니라 관찰 가능한 실패 위치로 바꾼 것이 핵심 결과다.

두 시뮬레이션은 같은 프로세스와 빌드에서 실행되므로 CPU, 컴파일러, 표준 라이브러리가 다른 실제 피어의 차이를 모두 대변하지 않는다. 디싱크 이후의 상태 전송과 세션 복구도 제공하지 않는다.
