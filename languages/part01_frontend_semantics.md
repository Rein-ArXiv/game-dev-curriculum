## 들어가며

프로그래밍 언어 구현의 첫 번째 과제는 소스 코드를 실행하는 것이 아니라, 소스 코드가 **무엇을 뜻하는지 모호하지 않게 결정하는 것**이다. 컴파일러 프런트엔드는 문자 스트림을 토큰, 구문 트리, 이름과 타입이 연결된 의미 구조로 바꾼다.

게임 개발에서도 이 과정은 낯설지 않다. 셰이더 언어, 콘솔 명령, 퀘스트 조건식, 비주얼 스크립트, 데이터 검증 규칙은 모두 작은 언어다. 프런트엔드 설계를 이해하면 문자열을 즉흥적으로 해석하는 코드를 넘어, 오류를 일찍 발견하고 도구가 이해할 수 있는 DSL을 만들 수 있다.

## 1. 언어의 계약

언어는 표기법만이 아니라 세 층의 계약이다.

- **구문론(syntax)**: 어떤 문자열이 올바른 프로그램인가
- **정적 의미론(static semantics)**: 실행 전에 판정할 수 있는 제약은 무엇인가
- **동적 의미론(dynamic semantics)**: 올바른 프로그램이 실행될 때 어떤 상태 변화가 일어나는가

예를 들어 `damage(target, 10)`이 문법적으로 올바르더라도 `target`이 선언되지 않았거나 `damage`가 숫자를 첫 인자로 요구한다면 의미적으로는 잘못된 프로그램이다. 반대로 타입 검사를 통과해도, 실행 중 대상이 이미 제거되었다면 런타임 오류가 될 수 있다.

좋은 언어 설계는 같은 입력이 문맥에 따라 뜻이 바뀌는 경우를 최소화한다. 암묵적 변환과 예외 규칙은 작성자의 편의를 높이지만, 독자와 도구가 추론해야 할 상태 공간을 넓힌다.

## 2. 어휘 분석

렉서(lexer)는 문자 스트림을 토큰 스트림으로 변환한다.

```text
health <= 0 && state != "dead"

IDENT(health) LE NUMBER(0) AND IDENT(state) NE STRING(dead)
```

토큰은 보통 종류, 원문 또는 해석된 값, 소스 위치를 가진다. 공백과 주석은 실행 의미가 없더라도 정확한 오류 위치와 포매터를 위해 보존할 수 있다.

### 정규 언어와 유한 오토마톤

식별자, 숫자, 연산자처럼 국소적인 패턴은 정규식과 유한 오토마톤으로 표현할 수 있다. 정규식은 선언적 명세이고, DFA는 입력 문자마다 상태를 하나씩 전이하며 선형 시간에 토큰을 인식하는 실행 모델이다.

렉서는 보통 가능한 가장 긴 토큰을 선택하는 **최장 일치(maximal munch)** 규칙을 쓴다. `>=`를 `>`와 `=`로 나누지 않는 이유다. 길이가 같다면 키워드 우선순위 같은 명시적 규칙이 필요하다.

### 렉서가 처리해야 할 경계

- 숫자 범위 초과와 잘못된 진법
- 문자열 이스케이프와 닫히지 않은 따옴표
- UTF-8 코드 포인트와 바이트 위치의 차이
- 주석 중첩 여부
- 키워드와 식별자의 구분

입력 포인터를 한 바이트 되돌리는 임시방편보다, 현재 위치와 토큰 시작 위치를 분리하고 전이 규칙을 명시하는 편이 오류에 강하다.

## 3. 문법과 구문 분석

문법은 토큰이 어떤 구조를 이루는지 정의한다.

```ebnf
expression  = equality ;
equality    = comparison, { ("==" | "!="), comparison } ;
comparison  = term, { ("<" | "<=" | ">" | ">="), term } ;
term        = factor, { ("+" | "-"), factor } ;
factor      = unary, { ("*" | "/"), unary } ;
unary       = ("!" | "-"), unary | primary ;
primary     = NUMBER | IDENT | "(", expression, ")" ;
```

이 문법은 규칙의 계층으로 연산자 우선순위를 표현한다. `*`는 `+`보다 아래 규칙에서 결합하므로 더 강하게 묶인다.

### 모호성과 결합 법칙

문법이 하나의 입력에 둘 이상의 구문 트리를 허용하면 모호하다. `a - b - c`가 `(a - b) - c`인지 `a - (b - c)`인지 정해야 한다. 우선순위와 좌·우 결합 법칙은 언어 명세의 일부이며 파서 구현 세부사항이 아니다.

### 파서 선택

- **재귀 하강 파서**: 문법 규칙을 함수로 옮긴다. 읽기 쉽고 진단을 제어하기 좋다.
- **Pratt 파서**: 연산자의 결합 세기를 테이블로 표현해 표현식 문법에 적합하다.
- **LL/LR 계열**: 문법으로부터 파서를 생성하고 더 넓은 문법을 체계적으로 다룬다.

파서의 목표는 “성공 여부”만이 아니다. 잘못된 입력에서 어디까지 복구하여 후속 오류를 유용하게 보고할지도 설계해야 한다.

### 예측 파싱이 가능한 조건

재귀 하강 파서가 토큰 하나를 보고 어떤 규칙을 선택하려면 후보 규칙의 시작 토큰 집합이 겹치지 않아야 한다. 문법 기호 $X$에서 시작해 만들 수 있는 첫 터미널 집합을 $FIRST(X)$라 하고, $X$ 뒤에 올 수 있는 터미널 집합을 $FOLLOW(X)$라 한다.

```ebnf
statement = "if", expression, statement
          | "while", expression, statement
          | IDENT, "=", expression, ";"
          | IDENT, "(", arguments, ")", ";" ;
```

마지막 두 규칙은 모두 `IDENT`로 시작하므로 토큰 하나만 보고 선택할 수 없다. 다음 토큰까지 확인하거나, 공통 접두사를 묶는 left factoring이 필요하다.

```ebnf
statement   = "if", expression, statement
            | "while", expression, statement
            | IDENT, ident_tail ;
ident_tail  = "=", expression, ";"
            | "(", arguments, ")", ";" ;
```

직접 왼쪽 재귀도 재귀 하강 파서에서 그대로 구현할 수 없다.

```ebnf
expression = expression, "+", term | term ;
```

함수 `parseExpression()`이 입력을 소비하기 전에 자신을 다시 부르면 무한 재귀가 된다. 반복 형태로 바꾸거나 Pratt 파서의 binding power로 표현한다.

```ebnf
expression = term, { "+", term } ;
```

LL 문법에서 nullable 규칙이 있을 때는 $FIRST$와 $FOLLOW$의 충돌도 확인해야 한다. 파서 생성기는 이 집합을 계산해 선택 충돌을 보고하고, 손으로 쓴 파서는 같은 모호성을 코드의 조건문 안에 숨길 수 있으므로 문법 테스트가 필요하다.

### LR 파서의 상태와 충돌

LR 계열 파서는 지금까지 본 접두부가 어떤 규칙의 어느 위치까지 진행되었는지를 상태로 가진다. 다음 토큰을 스택에 넣는 shift와 완성된 우변을 좌변으로 줄이는 reduce를 반복한다.

```text
모호한 문법:
  expression = expression, "+", expression
             | expression, "*", expression
             | NUMBER ;

stack:  expression + expression
lookahead: *

선택:
  reduce expression + expression -> expression
  shift * and continue expression * expression
```

두 선택이 모두 가능한 상태가 shift/reduce conflict다. 두 규칙으로 줄일 수 있으면 reduce/reduce conflict다. 우선순위 선언으로 충돌을 없앨 수 있지만, 선언이 문법의 모호성을 가린 것인지 의도한 언어 규칙인지 구분해야 한다.

LR 파서는 더 넓은 문법을 처리하지만 상태와 스택이 오류 원인을 소스 수준 규칙에서 멀어지게 만들 수 있다. DSL처럼 진단과 빠른 변화가 중요하면 손으로 쓴 재귀 하강·Pratt 파서가 유리하고, 문법이 크고 안정적이면 생성기의 충돌 검사와 자동화가 유리하다.

### Pratt 파서의 binding power

Pratt 파서는 토큰마다 전위 파싱 함수와 중위 파싱 함수, 좌·우 binding power를 등록한다. 중위 연산자는 오른쪽 식을 자신의 결합 세기보다 강한 범위까지만 읽는다.

```text
parse_expression(min_bp):
    lhs = parse_prefix(next_token)
    while lookahead.left_bp >= min_bp:
        op = consume()
        rhs = parse_expression(op.right_bp)
        lhs = Binary(op, lhs, rhs)
    return lhs
```

좌결합 연산자는 오른쪽 binding power를 더 높게 두어 같은 연산자가 오른쪽에 묶이지 않게 한다. 대입과 거듭제곱 같은 우결합 연산자는 반대로 설정한다. 이 작은 차이가 `a - b - c`와 `a = b = c`의 트리 모양을 결정한다.

## 4. 추상 구문 트리

구체 구문 트리(CST)는 괄호와 구분자까지 문법 구조를 보존한다. 추상 구문 트리(AST)는 실행 의미에 필요한 구조만 남긴다.

```text
Binary(
  op: Add,
  left: Name("base"),
  right: Binary(op: Mul, left: Name("level"), right: Number(2))
)
```

AST 노드는 소스 위치를 유지해야 한다. 이후 타입 오류와 런타임 스택 추적이 원래 코드로 돌아가려면 변환 단계마다 위치 정보를 보존하거나 대응 관계를 기록해야 한다.

AST 설계에서는 구문 형태와 의미 형태를 구분한다. 예를 들어 `a += b`를 별도 노드로 유지할 수도 있고, 대입과 덧셈으로 낮출 수도 있다. 너무 일찍 낮추면 정확한 오류 메시지를 잃고, 너무 오래 유지하면 이후 단계가 처리할 경우의 수가 늘어난다.

## 5. 이름 해석과 스코프

이름 해석(name resolution)은 식별자를 그 선언과 연결한다. 단순 문자열 비교가 아니라 스코프, 가시성, 섀도잉, 모듈 경계를 판정하는 과정이다.

```text
global x
function f(x):
    block:
        local y = x
```

블록의 `x`는 전역이 아니라 매개변수 선언을 가리킨다. 프런트엔드는 각 이름 사용에 선언 ID나 심볼 참조를 연결해 이후 단계가 문자열 검색을 반복하지 않게 한다.

심볼 테이블은 일반적으로 중첩 스코프의 스택이나 부모 링크를 가진 테이블로 구현한다. 선언 순서가 의미를 갖는 언어에서는 같은 스코프 안에서도 사용 시점보다 앞선 선언만 보이도록 해야 한다.

클로저가 있는 언어에서는 이름 해석 결과가 런타임 저장 위치에도 영향을 준다. 지역 변수인지, 상위 함수에서 캡처할 변수인지, 전역인지가 이 단계에서 결정된다.

### 이름 공간과 선언 정체성

문자열 이름은 선언의 정체성이 아니다. 서로 다른 스코프의 `x`는 텍스트가 같아도 다른 선언이며, 이름을 바꾸는 리팩터링은 같은 선언을 가리키는 사용처만 바꿔야 한다.

```text
SymbolId 1042
  name: x
  declaration span: file.dsl:18:9
  type: Int
  storage: local slot 3
```

프런트엔드가 각 이름 사용을 `SymbolId`에 연결하면 타입 검사, 참조 찾기, rename, 캡처 분석이 같은 해석 결과를 공유한다. 문자열 해시 맵을 후속 단계마다 다시 조회하면 섀도잉과 오류 복구 상태에서 서로 다른 답을 만들기 쉽다.

언어에 따라 타입, 값, 레이블, 모듈이 같은 이름 공간을 공유하거나 분리된다. C의 태그 이름 공간, 함수 안 레이블, C++의 오버로드 집합처럼 규칙이 복잡할수록 “이름 하나가 선언 하나를 가리킨다”는 단순 모델만으로는 부족하다. 오버로드 해석은 후보 집합을 만들고 변환 비용과 제네릭 제약을 비교하는 별도 의미 분석이다.

## 6. 타입과 의미 검사

타입은 값의 집합과 허용 연산을 기술한다. 타입 검사는 “이 연산이 모든 실행 경로에서 정의되는가”를 실행 전에 근사한다.

```text
damage: (EntityHandle, Float) -> DamageResult
```

호출 인자의 개수와 타입, 반환값 사용 방식, 대입 가능성을 검사할 수 있다. 정적 타입 시스템은 모든 런타임 오류를 제거하지는 않지만, 특정 오류 부류가 실행 전에 발생하지 않음을 보장한다.

### 타입 시스템의 판단

- 명목적 타입과 구조적 타입
- 암묵적 변환의 허용 범위
- 제네릭과 타입 변수
- null 가능성
- 효과(effect): 함수가 상태를 변경하거나 실패할 수 있는가

타입 추론은 제약식을 만들고 해를 구한다. `x + 1`에서 `x`가 덧셈 가능한 타입이어야 한다는 제약이 생긴다. 추론이 강할수록 표기는 줄지만, 오류 원인을 설명하기 어려워질 수 있다.

정적 의미 검사는 타입 외에도 `break`가 반복문 안에 있는지, 모든 반환 경로가 값을 제공하는지, 상수 표현식인지, 순환 의존성이 있는지 등을 판정한다.

### 타입 판단과 보존하려는 성질

타입 규칙은 보통 판단식으로 표현할 수 있다.

```text
Γ ⊢ e : T
```

이는 타입 환경 $\Gamma$ 아래에서 표현식 $e$가 타입 $T$를 가진다는 뜻이다. 덧셈 규칙을 단순화하면 다음과 같다.

```text
Γ ⊢ e1 : Int    Γ ⊢ e2 : Int
--------------------------------
Γ ⊢ e1 + e2 : Int
```

정적 타입 안전성은 흔히 progress와 preservation으로 설명한다.

- progress: 타입이 맞는 닫힌 표현식은 값이거나 한 단계 실행할 수 있다.
- preservation: 타입이 맞는 표현식이 한 단계 실행된 뒤에도 타입이 유지된다.

이 두 성질이 보장되면 “타입이 맞는 프로그램은 정의되지 않은 타입 오류 상태에 막히지 않는다”는 결론을 얻는다. 파일 없음이나 제거된 엔티티처럼 타입 밖의 실패까지 사라지는 것은 아니다.

### 단일화와 occurs check

타입 추론은 미지 타입 변수 사이의 등식을 푸는 문제로 볼 수 있다.

```text
identity(x) = x

parameter: α
return:    α
result:    α -> α
```

함수 적용 `f(x)`에서는 `type(f) = type(x) -> β`라는 제약이 생긴다. 단일화(unification)는 두 타입 구조를 재귀적으로 맞추며 타입 변수에 해를 대입한다.

```text
unify(List<α>, List<Int>)  => α := Int
unify(α -> Bool, Int -> β) => α := Int, β := Bool
```

타입 변수 $\alpha$를 `List<α>`에 대입하면 무한 타입이 생긴다. 변수 자신이 대입 대상 안에 나타나는지 검사하는 occurs check가 이를 막는다. occurs check를 생략하면 구현은 빨라질 수 있지만 언어가 재귀 타입을 어떤 방식으로 허용하는지 별도 규칙이 필요하다.

let-polymorphism에서는 일반화 가능한 타입 변수와 현재 환경에 묶인 변수를 구분한다. 변경 가능한 참조와 무제한 일반화를 함께 허용하면 한 저장 위치를 서로 다른 타입으로 사용할 수 있어 타입 안전성이 깨진다. value restriction 같은 규칙이 필요한 이유다.

### 서브타이핑과 variance

`Dog`가 `Animal`의 서브타입이어도 `List<Dog>`를 `List<Animal>`로 항상 볼 수 있는 것은 아니다. 후자에 `Cat`을 삽입할 수 있다면 원래 `List<Dog>`의 불변식이 깨진다.

- 읽기 전용 생산자: 공변(covariant)이 안전할 수 있다.
- 쓰기 전용 소비자: 반공변(contravariant)이 안전할 수 있다.
- 읽기와 쓰기 모두: 일반적으로 무공변(invariant)이어야 한다.

함수 타입은 인자에서 반공변, 반환에서 공변이다. 넓은 범위의 입력을 받을 수 있는 함수는 더 좁은 입력만 요구하는 위치에 안전하게 놓을 수 있고, 더 구체적인 결과를 반환하는 함수는 더 일반적인 결과를 기대하는 위치에 놓을 수 있다.

## 7. 진단과 복구

진단 품질은 언어의 실제 사용성을 결정한다. 좋은 오류는 다음을 답한다.

1. 어디에서 문제가 발견되었는가
2. 무엇을 기대했는가
3. 실제로 무엇을 받았는가
4. 가능한 수정은 무엇인가

첫 오류 뒤에 파서를 즉시 중단하면 수정 반복이 느려진다. 반대로 무리하게 복구하면 하나의 실수에서 수십 개의 가짜 오류가 파생된다. 문장 종료자나 블록 경계처럼 안전한 동기화 지점까지 건너뛰는 패닉 모드가 실용적인 절충이다.

진단은 발견 위치와 원인 위치가 다를 수 있다. 닫히지 않은 괄호는 파일 끝에서 발견되지만 원인은 여는 괄호다. 소스 범위와 관련 위치를 함께 제시해야 한다.

## 8. 프런트엔드 검증

프런트엔드는 입력 공간이 크고 경계 조건이 많다. 다음 검증을 조합한다.

- 토큰별 최소·경계·잘못된 입력 테스트
- 연산자 우선순위를 AST 스냅샷으로 검증
- 파싱 후 다시 출력하고 재파싱하는 왕복 속성
- 임의 입력에 대해 충돌하지 않는지 퍼징
- 이름 해석과 타입 오류의 정확한 소스 위치 검증
- 유효 프로그램과 무효 프로그램의 명세 예제 모음

가장 중요한 기준은 각 단계의 계약이다. 렉서가 만든 모든 토큰 스트림을 파서가 안전하게 처리하고, 파서가 만든 모든 AST를 의미 분석기가 정의된 방식으로 처리해야 한다.

## 9. 실제 구현 파이프라인

프런트엔드 구현은 알고리즘 하나가 아니라 산출물의 흐름이다. 각 단계는 소비자가 신뢰할 수 있는 형태로 정보를 보존해야 한다.

```text
SourceFile
  -> TokenStream + SourceSpan
  -> ConcreteSyntaxTree 또는 ParseTree
  -> AST
  -> SymbolTable + ResolvedNames
  -> TypedAST 또는 TypedIR
  -> Diagnostics
```

`SourceSpan`은 단순한 편의 기능이 아니다. 모든 토큰과 AST 노드가 원본 파일의 범위를 보존해야 오류 메시지, 리팩터링, 자동 완성, 디버거 중단점이 같은 위치를 가리킬 수 있다. 매크로나 include처럼 소스가 다른 소스에서 생성될 수 있으면, 생성된 위치와 원본 위치를 함께 추적하는 source map이 필요하다.

구문 트리에는 두 종류가 있다.

- **Concrete Syntax Tree(CST)**: 괄호, 쉼표, 주석, 공백처럼 원문 구조를 거의 보존한다.
- **AST**: 의미 분석과 실행에 필요한 구조만 남긴다.

컴파일만 한다면 AST면 충분할 수 있다. 하지만 에디터, formatter, refactoring tool, visual scripting round-trip이 필요하면 손실 없는 CST나 green/red tree 같은 구조가 필요하다. 주석과 공백을 버린 AST만으로는 사용자가 쓴 파일을 안정적으로 다시 출력할 수 없다.

이름 해석 단계의 산출물은 문자열이 아니라 선언의 정체성이다.

```text
Identifier("hp") -> SymbolId(42)
SymbolId(42) -> declaration span, type, storage class, module
```

두 변수가 같은 이름을 가져도 서로 다른 scope에 있으면 서로 다른 symbol이다. 반대로 import와 alias를 거친 이름이 같은 선언을 가리킬 수 있다. 타입 검사, rename refactoring, jump-to-definition은 모두 문자열 비교가 아니라 이 symbol identity 위에서 동작한다.

타입 검사 뒤에는 AST에 타입 주석을 덧붙이거나 별도 typed IR을 만든다. 중요한 점은 IR 소비자가 암묵적 변환, overload 선택, generic instantiation 같은 결정을 다시 하지 않도록 결과를 명시하는 것이다.

```text
CallExpr "damage(target, 10)"
  callee: FunctionId(17)
  args:
    target: EntityHandle
    10: Int literal -> Float conversion inserted
  result: DamageResult
```

이 산출물이 없으면 런타임이나 코드 생성기가 다시 이름을 찾고 타입을 추론해야 하며, 프런트엔드와 백엔드가 서로 다른 결정을 내릴 위험이 생긴다.

도구 친화적 프런트엔드는 전체 파일을 매번 처음부터 처리하지 않는다. 작은 수정마다 토큰화·파싱·이름 해석·타입 검사의 영향을 받은 범위를 계산하고 캐시를 재사용한다. 증분 파싱은 다음 불변식이 필요하다.

- 수정되지 않은 소스 범위의 syntax node identity를 유지한다.
- 수정 범위가 문법적으로 상위 구조를 얼마나 깨뜨리는지 계산한다.
- 이전 진단 중 영향을 받은 것만 폐기한다.
- 파일 간 symbol 의존성을 기록해 import한 파일의 변경을 전파한다.

게임용 DSL에서도 이 구조는 중요하다. 퀘스트 조건식 하나를 고칠 때 모든 콘텐츠를 다시 검증하면 반복 속도가 무너진다. 반대로 의존성 전파가 부족하면 이미 깨진 참조가 에디터에서 정상으로 보인다.

프런트엔드의 완료 조건은 "유효한 입력을 받는다"가 아니다. 유효한 입력은 모호하지 않은 symbol과 type이 붙은 구조로 낮추고, 무효한 입력은 가능한 많은 후속 진단을 제공하면서도 내부 자료구조의 불변식을 깨지 않아야 한다.

---

## 결론

언어 프런트엔드는 문자를 구조로 바꾸는 단순 전처리가 아니다. 문법, 이름, 타입, 오류 규칙을 통해 프로그램의 의미를 고정하고, 그 결정을 백엔드와 도구가 재해석하지 않아도 되는 산출물로 남기는 계층이다.

작은 DSL도 이 원칙을 따를 때 예측 가능해진다. 입력을 구조화하고, 의미 제약을 일찍 검사하며, 소스 위치와 symbol identity를 보존하고, 잘못된 입력에서도 유용하게 실패해야 한다. 이것이 문자열 파싱 코드와 언어 구현을 가르는 경계다.
