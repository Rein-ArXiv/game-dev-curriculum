## 들어가며

컴파일러 최적화의 목적은 코드를 영리하게 보이도록 바꾸는 것이 아니다. 관측 가능한 의미를 보존하면서 실행 비용을 줄이는 것이다. 이를 위해 컴파일러는 소스 언어와 기계어 사이에 중간 표현을 두고, 제어 흐름과 데이터 흐름을 분석하며, 마지막에는 운영체제와 다른 모듈이 이해하는 ABI를 따라야 한다.

이 장의 핵심은 개별 최적화 기법보다 **정당화 조건**이다. 어떤 변환이 언제 안전하며, 그 사실을 어떤 분석과 검증으로 뒷받침하는지가 컴파일러의 본질이다.

## 1. 의미 보존과 중간 표현

컴파일은 여러 표현 사이의 변환 연쇄다.

```text
source -> AST -> typed IR -> control-flow IR -> machine IR -> object code
```

각 변환은 이전 표현의 관측 가능한 동작을 보존해야 한다. 관측 가능성에는 반환값뿐 아니라 메모리 변경, 예외, I/O, 동기화, 종료 여부가 포함될 수 있다.

중간 표현(IR)은 분석과 변환에 적합하도록 소스 언어의 복잡성을 줄인다. 고수준 IR은 객체와 예외 같은 의미를 유지하고, 저수준 IR은 명시적 메모리 접근과 분기를 드러낸다. 하나의 IR로 모든 목적을 만족시키려 하면 지나치게 복잡하거나 정보를 너무 일찍 잃는다.

## 2. 제어 흐름 그래프와 SSA

기본 블록은 중간에 분기 없이 순차 실행되고 끝에서만 제어가 이동하는 명령열이다. 기본 블록을 노드, 가능한 이동을 간선으로 만들면 제어 흐름 그래프(CFG)가 된다.

```text
entry -> condition -> then -> merge -> exit
                    \-> else -/
```

CFG는 도달 가능성, 루프, 지배 관계, 예외 경로를 분석하는 기반이다. 블록 A가 블록 B로 가는 모든 경로에 반드시 나타나면 A가 B를 지배한다.

SSA(static single assignment)는 각 변수 이름이 한 번만 정의되도록 만든다.

```text
x1 = 1
if cond:
    x2 = 2
x3 = phi(x1, x2)
```

`phi`는 어떤 선행 블록에서 왔는지에 따라 값을 선택한다. SSA에서는 값의 정의와 사용 관계가 명시적이므로 상수 전파, 죽은 코드 제거, 공통 부분식 제거가 단순해진다.

### 지배 트리와 phi 배치

블록 $A$가 블록 $B$로 가는 모든 진입 경로에 반드시 나타나면 $A$는 $B$를 지배한다. 각 블록의 즉시 지배자를 부모로 연결하면 지배 트리가 된다. SSA 이름의 정의는 모든 사용을 지배해야 한다.

분기 양쪽에서 정의된 변수가 합류점에서 사용되면 phi가 필요하다. 모든 합류점에 무조건 phi를 넣으면 IR이 불필요하게 커진다. dominance frontier는 한 정의가 지배하던 경로와 지배하지 않던 경로가 처음 만나는 지점을 찾아 필요한 phi 후보를 계산한다.

```text
entry
  |
 branch
 /    \
x1    x2
 \    /
 merge: x3 = phi(x1, x2)
```

phi는 실제 기계 명령이 아니라 제어 흐름 간 값 선택을 표현한다. SSA를 기계 IR로 낮출 때는 선행 간선마다 복사 명령으로 바꾸고, 서로 값을 교환하는 parallel copy를 안전하게 순서화해야 한다.

## 3. 데이터 흐름 분석

데이터 흐름 분석은 CFG 위에서 프로그램 지점을 통과하는 사실을 계산한다. 분석은 보통 격자, 전이 함수, 고정점 반복으로 표현된다.

- 도달 정의: 어떤 대입이 이 지점에 도달할 수 있는가
- 생존 변수: 이후에 읽힐 수 있는 값은 무엇인가
- 사용 가능한 표현식: 이미 계산되었고 피연산자가 바뀌지 않은 표현식은 무엇인가
- 범위 분석: 값이 가질 수 있는 구간은 무엇인가

분석 결과는 보수적이어야 한다. 안전성을 증명하지 못한 경우 최적화를 포기해야 한다. 잘못된 음성 판단은 기회를 놓치지만, 잘못된 양성 판단은 프로그램 의미를 바꾼다.

별칭 분석은 두 포인터가 같은 메모리를 가리킬 수 있는지 판정한다. `*p`에 쓰기가 `*q`의 값을 바꾸지 않는다고 증명해야 메모리 연산을 재배치할 수 있다. 포인터와 외부 호출이 많은 언어에서 최적화가 어려운 이유다.

### 고정점 방정식

정방향 데이터 흐름 분석은 각 블록의 입력 사실에서 출력 사실을 계산한다.

```text
IN[B]  = meet(OUT[P] for every predecessor P)
OUT[B] = transfer_B(IN[B])
```

후방 분석은 successor의 입력에서 현재 블록의 출력을 계산한다. 생존 변수 분석은 대표적인 후방 분석이다.

```text
OUT[B] = union(IN[S] for every successor S)
IN[B]  = USE[B] union (OUT[B] - DEF[B])
```

루프가 있으면 한 번 순회로 답이 나오지 않는다. 초기값에서 시작해 결과가 더 이상 바뀌지 않을 때까지 worklist로 블록을 반복 처리한다. 격자의 높이가 유한하고 전이 함수가 단조적이면 반복은 고정점에 도달한다.

분석의 meet 연산이 교집합인지 합집합인지에 따라 must 분석과 may 분석이 갈린다. 최적화를 허용하려면 모든 경로에서 사실이어야 하는 경우가 많고, 위험을 찾으려면 한 경로에서라도 가능하면 보고해야 한다. 이 방향을 뒤집으면 안전하지 않은 최적화나 과도한 경고가 생긴다.

### 메모리 효과와 호출 요약

함수 호출이 모든 메모리를 읽고 쓸 수 있다고 가정하면 호출 주변의 최적화가 거의 막힌다. 반대로 실제보다 약한 효과를 선언하면 쓰기와 읽기를 잘못 재배치한다.

컴파일러는 함수별 효과를 요약할 수 있다.

- 순수 함수: 외부 상태를 읽거나 쓰지 않고 인자만으로 결과 결정
- readonly: 외부 상태를 읽지만 쓰지 않음
- argmemonly: 인자로 받은 메모리만 접근
- no-throw: 예외 경로 없음
- no-return: 정상 복귀 없음

이 속성은 언어 의미에서 증명하거나, 함수 본문 분석으로 추론하거나, 외부 함수 선언에서 신뢰한다. 잘못된 외부 속성은 컴파일러 버그가 아니라 프로그램의 계약 위반으로 취급될 수 있으므로 FFI 경계에서 특히 보수적이어야 한다.

## 4. 핵심 최적화

### 지역 최적화

상수 접기는 컴파일 시간에 알려진 연산을 계산한다. 대수적 단순화는 `x + 0`을 `x`로 바꾼다. 단, 부동소수점의 NaN, 부호 있는 0, 오버플로 규칙 때문에 정수 대수와 같은 변환이 항상 안전하지는 않다.

죽은 코드 제거는 결과가 사용되지 않고 부작용도 없는 연산을 지운다. “사용되지 않는다”와 “관측되지 않는다”를 구분해야 한다.

### 전역 최적화

공통 부분식 제거는 같은 피연산자와 같은 연산의 중복 계산을 재사용한다. 루프 불변 코드 이동은 반복마다 바뀌지 않는 계산을 루프 밖으로 옮긴다. 둘 다 메모리 별칭과 예외 발생 가능성을 고려해야 한다.

인라이닝은 호출 경계를 없애 후속 최적화를 열지만 코드 크기와 명령 캐시 압력을 높인다. 호출 비용 자체보다 상수 인자와 구체 타입을 노출하는 효과가 더 중요할 때가 많다.

벡터화는 독립 반복을 SIMD 연산으로 묶는다. 반복 간 의존성이 없고 정렬, 범위, 예외 규칙을 만족해야 한다. 자동 벡터화가 실패하면 보고서를 통해 어떤 의존성을 증명하지 못했는지 확인해야 한다.

### 변환 정당성은 언어 의미에 의존한다

`x * 0`을 `0`으로 바꾸는 변환은 수학적 실수에서는 안전하지만 IEEE 754 부동소수점에서는 `x`가 NaN이나 무한대일 때 결과를 바꾼다. `(a + b) + c`를 `a + (b + c)`로 재결합하면 반올림 순서와 overflow가 달라진다.

정수 overflow도 언어마다 다르다.

- 모듈러 wrap을 보장하면 변환은 그 대수 안에서 증명해야 한다.
- overflow를 trap으로 정의하면 예외 발생 순서를 보존해야 한다.
- overflow를 미정의 동작으로 두면 컴파일러는 발생하지 않는다고 가정할 수 있다.

메모리 접근 제거도 동일하다. 사용되지 않는 load라도 volatile 장치 레지스터 읽기나 fault 발생이 관측 가능하면 제거할 수 없다. 동시성 메모리 모델에서 atomic 연산은 값 외에 happens-before 관계를 만들 수 있다.

최적화 옵션은 단순 속도 단계가 아니라 어떤 의미 완화를 허용하는지에 대한 계약이다. fast-math, strict aliasing, overflow 가정은 생성 코드와 재현성에 직접 영향을 준다.

## 5. 코드 생성과 레지스터 할당

명령 선택은 IR 연산을 대상 기계 명령 조합으로 바꾼다. 같은 계산도 주소 지정 모드와 즉시값 범위에 따라 더 짧은 명령으로 표현할 수 있다.

기계의 물리 레지스터 수는 제한되어 있다. 레지스터 할당기는 동시에 살아 있는 값의 간섭 그래프를 만들거나 선형 스캔으로 구간을 배치한다. 공간이 부족하면 값을 스택으로 spill하며, 이는 추가 메모리 접근을 만든다.

명령 스케줄링은 데이터 의존성을 지키면서 지연 시간을 숨기도록 순서를 조정한다. 그러나 현대 비순차 실행 CPU에서는 정적 스케줄링만으로 성능을 예측할 수 없다. 코드 크기, 분기 예측, 캐시와 메모리 대역폭을 함께 측정해야 한다.

### 명령 선택과 lowering

고수준 IR 연산은 대상 기계가 직접 지원하지 않을 수 있다. 64비트 나눗셈, 원자 연산, 벡터 셔플, 예외 처리를 기계 명령이나 런타임 호출 조합으로 낮춰야 한다.

명령 선택은 트리 패턴 매칭으로 볼 수 있다.

```text
IR: add(load(base + index * 4), 1)

x86 candidate:
  mov eax, [base + index*4]
  add eax, 1
```

주소 지정 모드처럼 여러 IR 노드를 한 명령에 포함하면 명령 수를 줄인다. 그러나 가장 짧은 지역 패턴 선택이 전체 최적은 아닐 수 있다. 레지스터 압력, 즉시값 범위, 이후 fusion 가능성을 비용 모델에 포함해야 한다.

호출, 나눗셈, 원자 연산처럼 고정 레지스터를 요구하는 명령은 레지스터 할당 전에 제약을 표현해야 한다. 대상 독립 IR을 너무 오래 유지하면 이런 제약을 늦게 발견하고 불필요한 복사가 늘어난다.

### 레지스터 할당의 실제 문제

값의 live range가 겹치면 같은 물리 레지스터를 사용할 수 없다. 그래프 색칠 할당은 값을 노드, 겹침을 간선으로 만든 간섭 그래프에 물리 레지스터 색을 배정한다. 색을 배정하지 못한 값은 spill한다.

spill은 단순히 값을 스택에 한 번 저장하는 것이 아니다. 각 사용 앞에 reload, 정의 뒤에 store가 생겨 새 임시값과 간섭을 만들 수 있다. 어느 값을 spill할지 결정할 때 사용 빈도, 루프 깊이, 재계산 비용을 고려한다.

선형 스캔은 live interval을 시작 위치 순으로 처리해 빠르게 할당한다. 최적화 품질은 그래프 색칠보다 낮을 수 있지만 컴파일 시간이 중요한 JIT에 적합하다. 긴 live range를 여러 구간으로 split하면 호출 경계나 레지스터 압력이 높은 구간만 spill할 수 있다.

호출 규약은 caller-saved와 callee-saved 레지스터를 구분한다. 호출을 가로질러 살아 있는 값은 callee-saved에 두거나 호출 전후로 보존해야 한다. 함수 하나의 할당 결과가 호출 비용과 prologue·epilogue 크기를 바꾼다.

## 6. JIT와 특수화

JIT 컴파일러는 실행 중 관찰한 타입과 호출 빈도로 코드를 특수화한다. 자주 실행되는 경로만 최적화하고, 가정이 깨지면 일반 코드로 되돌리는 역최적화가 필요하다.

```text
guard: receiver type == Enemy
fast path: direct field offset and direct call
failure: deoptimize to generic execution
```

JIT의 비용 모델은 실행 속도뿐 아니라 컴파일 시간과 코드 캐시 메모리를 포함한다. 짧게 실행되는 스크립트에 고비용 최적화를 적용하면 총 시간이 늘어난다.

런타임이 생성한 기계어는 쓰기 가능 메모리와 실행 가능 메모리를 분리하는 W^X 원칙, 명령 캐시 동기화, 디버그 정보 등록을 고려해야 한다.

## 7. ABI, 링킹, 모듈

ABI(application binary interface)는 서로 별도로 컴파일된 코드가 만나는 계약이다.

- 인자와 반환값의 레지스터·스택 배치
- 보존해야 하는 레지스터
- 스택 정렬
- 구조체 레이아웃과 패딩
- 심볼 이름과 예외 전파 방식

소스 수준 타입이 같아 보여도 컴파일러 설정이나 ABI가 다르면 바이너리 경계에서 호환되지 않을 수 있다. 플러그인 경계에서는 C ABI, 명시적 크기의 타입, 불투명 핸들, 소유권 함수처럼 좁고 안정된 계약이 유리하다.

링커는 심볼 참조를 정의와 연결하고 주소를 재배치한다. 정적 링크는 코드를 결과물에 포함하고, 동적 링크는 실행 시 공유 라이브러리를 연결한다. 심볼 가시성, 버전, 초기화 순서는 빌드 문제가 아니라 런타임 의미에 영향을 준다.

모듈 시스템은 이름 공간과 의존성 그래프를 정의한다. 순환 의존성, 초기화 순서, 공개 인터페이스와 구현 분리는 증분 빌드와 핫 리로드의 안정성을 좌우한다.

## 8. 검증과 운영 경계

최적화 컴파일러는 입력 공간이 너무 커서 예제 테스트만으로 검증할 수 없다.

- 최적화 전후 IR을 실행해 결과 비교
- 임의 프로그램을 여러 컴파일러·최적화 수준에서 차등 테스트
- IR 검증기로 형식 불변식 확인
- sanitizer와 미정의 동작 검출
- 실제 워크로드 프로파일과 회귀 기준
- 생성 코드 디스어셈블과 성능 카운터 분석

미정의 동작이 있는 언어에서는 컴파일러가 “일어나지 않는다”고 가정할 수 있다. 개발자가 하드웨어에서 우연히 관찰한 동작과 언어가 보장하는 동작을 구분해야 한다.

DSL과 스크립트 컴파일러는 오류 시 호스트 프로세스를 손상시키지 않아야 한다. 입력 크기, 컴파일 시간, 생성 코드 크기를 제한하고, 캐시 키에 언어 버전과 옵션을 포함하며, 이전 버전 산출물의 호환 정책을 명시해야 한다.

## 9. 디버그 정보, 스택맵, 역최적화

컴파일러가 코드를 바꾸면 실행 중인 기계 상태와 원래 소스의 대응이 흐려진다. 인라이닝은 호출 프레임을 없애고, 죽은 코드 제거는 변수를 지우며, 레지스터 할당은 값의 위치를 계속 바꾼다. 디버거, 예외 스택 추적, 프로파일러, GC는 그래도 "지금 이 값은 소스의 어떤 변수인가"를 알아야 한다.

따라서 컴파일 결과에는 코드뿐 아니라 메타데이터가 붙는다.

| 메타데이터 | 역할 |
|---|---|
| 소스 위치 테이블 | 기계 명령 주소를 파일·라인·컬럼에 연결 |
| 인라인 스택 | 인라인된 함수 호출 관계 복원 |
| 변수 위치 정보 | 특정 지점에서 값이 레지스터·스택·상수 중 어디 있는지 기록 |
| 스택맵 | GC safepoint에서 어떤 슬롯이 객체 참조인지 기록 |
| 예외 처리 테이블 | 명령 주소별 정리 코드와 핸들러 위치 기록 |

스택맵은 관리형 런타임에서 특히 중요하다. 최적화된 코드가 실행 중일 때 GC가 멈추면, 수집기는 각 스택 프레임의 어느 레지스터와 스택 슬롯이 객체 포인터인지 알아야 한다. 정수와 우연히 같은 비트 패턴을 포인터로 착각하면 살아 있지 않은 객체를 붙잡고, 실제 포인터를 놓치면 살아 있는 객체를 회수한다. 그래서 컴파일러는 safepoint마다 정확한 루트 정보를 내보내야 한다.

JIT의 역최적화(deoptimization)는 최적화된 프레임을 일반 실행기가 이해하는 프레임으로 되돌리는 작업이다. guard가 실패하면 단순히 느린 함수로 점프하는 것으로 끝나지 않는다. 이미 사라진 지역 변수, 인라인으로 합쳐진 호출 프레임, 레지스터에 흩어진 값을 다시 구성해야 한다.

```text
optimized frame:
  rax = health
  rbx = enemy pointer
  inlined ApplyDamage frame 없음

deopt state:
  frame Enemy.Update
  frame ApplyDamage
  local damage = constant 10
  local health = rax
  local self   = rbx
```

이 정보를 만들지 못하는 최적화는 JIT에서 사용할 수 없다. 빠른 코드가 맞는지만이 아니라, 틀린 가정이 발견됐을 때 정확한 느린 상태로 돌아올 수 있어야 한다. 디버거에서 변수 값을 보여주는 문제와 JIT deopt 문제는 같은 뿌리를 가진다. 최적화가 값을 어디로 옮기고 어떤 프레임을 없앴는지 추적해야 한다는 점이다.

운영 환경에서는 이 메타데이터의 크기도 비용이다. 모든 지점에 완전한 변수 위치를 기록하면 코드보다 디버그 정보가 커질 수 있다. 그래서 일반적으로 breakpoint 가능 지점, safepoint, 호출 지점처럼 관측 가능한 지점에 정보를 집중한다. 최적화 컴파일러의 산출물은 기계어 바이트열 하나가 아니라, 실행·수집·디버깅·프로파일링이 공유하는 메타데이터 묶음이다.

---

## 결론

컴파일러 백엔드는 구문을 기계어로 치환하는 번역기가 아니다. 제어 흐름과 데이터 흐름을 분석하고, 증명된 조건 안에서 의미를 보존하며 비용을 줄이는 시스템이다.

IR, SSA, 별칭 분석, ABI, 디버그 메타데이터를 이해하면 최적화 결과를 막연히 믿지 않고 설명할 수 있다. 좋은 컴파일러와 좋은 저수준 코드는 같은 태도를 공유한다. 계약을 명시하고, 변환의 전제를 확인하며, 최종 판단은 실제 생성 코드와 측정으로 내린다.
