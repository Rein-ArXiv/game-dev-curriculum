## 들어가며

프런트엔드가 프로그램의 구조와 의미를 결정했다면, 런타임은 그 의미를 실제 상태 변화로 구현한다. 같은 언어도 AST를 직접 순회할 수 있고, 바이트코드 가상 머신에서 실행할 수 있으며, 기계어로 번역할 수도 있다. 구현 방식은 달라도 호출, 변수 수명, 객체 정체성, 오류 전파라는 언어 계약은 보존되어야 한다.

게임용 스크립트 런타임은 처리량만으로 평가할 수 없다. 프레임 예산, 중단 가능성, 핫 리로드, 디버깅, 저장 데이터와의 호환성까지 실행 모델에 포함된다.

## 1. 실행 상태와 평가 규칙

실행은 표현식과 문장을 현재 환경과 저장소에 적용해 값과 새 상태를 얻는 과정이다.

```text
evaluate(expression, environment, store) -> value, store
```

환경은 이름을 저장 위치에 연결하고, 저장소는 위치를 실제 값에 연결한다. 둘을 구분하면 변수 이름과 객체의 수명, 별칭을 명확히 설명할 수 있다.

평가 순서는 언어 의미의 일부다. `f() + g()`에서 어느 함수가 먼저 호출되는지 정의하지 않으면 부작용이 있는 프로그램의 결과가 구현마다 달라질 수 있다. 단락 평가, 정수 오버플로, 부동소수점 비교, 실패 시 상태 변경 여부도 명시해야 한다.

## 2. 트리 순회 인터프리터

트리 순회 인터프리터는 AST 노드 종류에 따라 평가 함수를 호출한다.

```cpp
Value Evaluate(const Expr& expr, Environment& env) {
    return std::visit(Overload{
        [&](const Literal& n) { return n.value; },
        [&](const Name& n) { return env.Lookup(n.symbol); },
        [&](const Binary& n) {
            Value left = Evaluate(*n.left, env);
            Value right = Evaluate(*n.right, env);
            return Apply(n.op, left, right);
        }
    }, expr.node);
}
```

구현과 언어 의미의 대응이 직접적이어서 첫 실행기와 참조 구현에 적합하다. 그러나 노드마다 분기와 포인터 추적이 발생하고, 반복 실행하는 구조를 압축하지 못한다.

트리 순회 실행기는 최적화된 실행기의 정답 오라클로도 가치가 있다. 동일 프로그램을 두 실행기에서 실행해 결과와 부작용을 비교하면 최적화가 의미를 바꾸는 오류를 발견할 수 있다.

## 3. 바이트코드 가상 머신

바이트코드는 AST를 작은 명령어 열로 낮춘 중간 실행 형식이다.

```text
LOAD_LOCAL 0
PUSH_CONST 2
MUL
LOAD_GLOBAL base
ADD
RETURN
```

스택 VM은 피연산자를 값 스택에 쌓는다. 명령 형식이 단순하고 코드가 조밀하지만, 스택 이동이 많다. 레지스터 VM은 가상 레지스터를 명시해 명령 수를 줄일 수 있으나 인코딩과 생성기가 복잡해진다.

VM의 핵심 상태는 명령 포인터, 값 스택, 호출 프레임, 전역 환경이다. 디스패치 루프는 명령을 읽고 실행한다.

```cpp
for (;;) {
    Op op = ReadOp(ip);
    switch (op) {
    case Op::Add: {
        Value rhs = Pop();
        Value lhs = Pop();
        Push(lhs + rhs);
        break;
    }
    case Op::JumpIfFalse: {
        auto target = ReadTarget(ip);  // true/false와 무관하게 operand 소비
        if (!Peek().Truthy()) ip = target;
        break;
    }
    case Op::Return: return Pop();
    }
}
```

위 코드에서 `ReadOp`는 opcode만 전진시키고 `ReadTarget`이 operand를 소비한다고 가정한다. `ReadOp`가 instruction 전체를 선해독하는 구현이라면 `ReadTarget`은 이미 해독된 operand를 조회하는 규약이며, 어느 쪽이든 조건과 무관하게 operand를 소비하는 규약이 정의되어야 한다.

바이트코드 검증기는 실행 전에 잘못된 점프 대상, 상수 인덱스, 스택 언더플로 가능성을 차단해야 한다. 외부에서 로드하는 바이트코드는 신뢰할 수 없는 입력이다.

### 명령 인코딩과 디스패치 비용

바이트코드 명령은 opcode와 피연산자를 어떤 폭으로 인코딩할지 결정해야 한다.

```text
1 byte opcode
1 byte local index
2 byte constant index
4 byte jump offset
```

고정 폭 명령은 다음 명령 위치를 빠르게 계산하고 디코더를 단순하게 만든다. 가변 폭 명령은 코드가 조밀해 명령 캐시와 메모리 대역폭에 유리하지만 디코딩과 임의 접근이 복잡하다. 자주 쓰는 작은 상수·지역 변수용 짧은 명령과 큰 인덱스용 확장 명령을 함께 둘 수 있다.

switch 디스패치는 이식성이 좋지만 매 명령마다 간접 분기와 루프 복귀가 발생한다. direct threading은 각 명령 핸들러가 다음 핸들러 주소로 직접 이동해 디스패치 비용을 줄일 수 있지만 구현 언어와 컴파일러 확장에 의존한다. superinstruction은 자주 연속하는 명령을 하나로 합쳐 디스패치 횟수를 줄이지만 명령 집합과 생성기 복잡도를 늘린다.

성능 판단은 명령 수만 세면 부족하다. 코드 크기, 분기 예측, 핸들러의 캐시 배치, 값 표현의 태깅 비용을 함께 측정해야 한다.

### 바이트코드 검증은 데이터 흐름 분석이다

점프 대상이 명령 경계인지 확인하는 것만으로는 안전하지 않다. 각 프로그램 지점에서 가능한 스택 높이와 값 종류를 추적해야 한다.

```text
entry stack height = 0
PUSH_CONST: +1
ADD:         -2 +1
JUMP:        successor receives current height
```

두 제어 흐름이 합쳐지는 지점에서는 스택 높이와 슬롯 타입이 호환되어야 한다. 고정점에 도달할 때까지 각 기본 블록의 입력 상태를 전파하면 실행 전에 스택 언더플로, 초기화되지 않은 지역 변수, 잘못된 반환 형태를 거부할 수 있다.

검증기가 받아들인 바이트코드는 VM이 메모리 범위를 벗어나거나 타입 규칙을 깨뜨리지 않는다는 계약을 가져야 한다. 검증기와 실행기가 opcode 의미를 서로 다르게 구현하면 검증 우회가 생기므로 하나의 명령 명세에서 둘을 생성하거나 차등 테스트하는 편이 안전하다.

## 4. 호출 프레임과 클로저

함수 호출 프레임은 반환 주소, 매개변수, 지역 변수, 임시값을 보관한다. 호출 규약은 인자를 어디에 두고 결과를 어디서 가져오며 누가 상태를 복원하는지 정의한다.

재귀 호출마다 독립 프레임이 필요하다. 프레임을 값 스택의 연속 구간으로 만들면 할당을 줄이고 캐시 지역성을 높일 수 있다.

### 클로저

클로저는 함수 코드와 정의 시점의 환경을 묶는다.

```text
function makeCounter():
    count = 0
    return function():
        count = count + 1
        return count
```

`makeCounter` 호출이 끝난 뒤에도 `count`는 살아 있어야 한다. 캡처된 지역 변수를 힙의 셀로 승격하거나, 열린 업밸류가 스택 위치를 가리키다가 프레임 종료 시 닫히도록 만들 수 있다.

캡처가 값 복사인지 참조 공유인지에 따라 의미가 달라진다. 이는 성능 최적화가 아니라 언어 계약이다.

### 열린 업밸류와 닫힌 업밸류

스택 기반 VM에서 아직 실행 중인 함수의 캡처 변수는 스택 슬롯에 있다. 이때 업밸류는 슬롯 주소를 가리키는 열린 상태다. 함수가 반환되기 전에 그 값을 힙 저장소로 복사하고 업밸류가 새 위치를 가리키게 하면 닫힌 상태가 된다.

```text
call stack slot 7 <--- open upvalue

function returns

heap cell <---------- closed upvalue
```

같은 지역 변수를 여러 클로저가 캡처하면 모두 같은 업밸류 객체를 공유해야 변경이 서로 보인다. 캡처마다 값을 복사하면 언어가 참조 캡처를 약속했는데도 서로 다른 상태가 된다.

열린 업밸류를 스택 주소 순으로 연결하면 함수 반환 시 해당 프레임 범위에 속한 업밸류만 닫을 수 있다. 업밸류 수명은 호출 프레임보다 길 수 있으므로 GC 루트와 쓰기 장벽에도 포함해야 한다.

## 5. 객체와 메모리 관리

객체 모델은 값, 정체성, 필드 조회, 상속 또는 조합 규칙을 정의한다. 값 타입은 내용이 같으면 대체 가능하지만, 참조 객체는 같은 내용을 가져도 서로 다른 정체성을 가질 수 있다.

동적 언어의 객체는 흔히 타입 포인터와 필드 저장소를 가진다. 모든 객체를 해시 맵으로 표현하면 단순하지만 비싸다. 동일한 필드 배치를 공유하는 shape/hidden class는 이름 조회를 오프셋 접근으로 바꾼다.

### 값 표현과 루트 집합

런타임 값은 대개 정수, 부동소수점, 불리언, 문자열, 객체 참조, 함수 참조를 하나의 `Value` 타입에 담는다. 단순한 구현은 태그와 payload를 분리한다.

```cpp
struct Value {
    ValueTag tag;
    union {
        double number;
        bool boolean;
        Object* object;
    };
};
```

이 구조는 명확하지만 값 하나가 커진다. NaN-boxing, pointer tagging, 압축 포인터 같은 기법은 값 크기와 캐시 효율을 개선하지만, 플랫폼의 포인터 정렬, 부동소수점 NaN 표현, 주소 공간 크기에 의존한다. 값 표현은 최적화 기법이기 전에 ABI다. 다만 여기서 말하는 layout 결합은 같은 프로세스에서 실행 중인 in-memory 값, 네이티브 바인딩, 디버거, 바이트코드 상수 풀이 같은 ABI를 공유한다는 뜻이다. 바이트코드 파일 형식과 저장 파일(disk) 스키마는 별개의 versioned 표현이며, 논리 값을 명시적으로 encode/decode하는 경계를 둔다.

GC는 모든 살아 있는 객체를 루트에서 찾아야 한다. 루트는 전역 변수만이 아니다.

| 루트 | 예시 |
|---|---|
| VM 스택 | 값 스택, 호출 프레임의 지역 변수 |
| 전역 상태 | 전역 변수, interned string table |
| 네이티브 경계 | C++에서 임시로 붙잡은 스크립트 객체 |
| 코루틴 | 중단된 스택과 대기 상태 |
| 디버거 | watch expression, breakpoint 조건 |

네이티브 코드가 스크립트 객체 포인터를 들고 있는데 GC가 이를 모르면 객체가 회수된다. 반대로 루트 등록을 해제하지 않으면 객체가 영원히 산다. 그래서 호스트 경계에는 `Handle` 또는 `Rooted<T>`처럼 명시적 루트 등록 타입을 두는 편이 안전하다.

### 자동 메모리 관리

참조 카운팅은 마지막 참조가 사라질 때 즉시 회수하지만 순환을 자체적으로 수집하지 못하고 갱신 비용이 든다. 추적형 GC는 루트에서 도달 가능한 객체를 표시하고 나머지를 회수한다.

- mark-sweep: 이동하지 않아 포인터가 안정적이지만 단편화 가능
- copying: 살아 있는 객체를 압축하지만 이동 비용과 포인터 갱신 필요
- generational: 대부분 객체가 짧게 산다는 가정으로 젊은 세대를 자주 수집
- incremental/concurrent: 긴 중단을 나누거나 병렬화하지만 쓰기 장벽과 복잡성 증가

게임 런타임에서는 평균 처리량보다 최악 중단 시간이 중요하다. 할당 예산, 세대 크기, 수집 시점과 한 프레임의 작업량을 제어할 수 있어야 한다.

### 삼색 불변식과 쓰기 장벽

증분·동시 추적 GC는 객체를 개념적으로 세 색으로 구분한다.

- 흰색: 아직 도달 가능함이 확인되지 않음
- 회색: 도달 가능하지만 자식 스캔이 끝나지 않음
- 검은색: 객체와 자식 스캔이 끝남

수집 중 프로그램이 검은 객체에서 흰 객체로 새 참조를 만들면, 수집기가 그 흰 객체를 놓쳐 살아 있는 객체를 회수할 수 있다. 쓰기 장벽은 이 변화를 감지해 흰 객체를 회색으로 만들거나, 검은 객체를 다시 스캔 대상으로 돌려 삼색 불변식을 보존한다.

```cpp
void StoreField(Object* owner, Object*& slot, Object* value) {
    slot = value;
    if (gc.marking && value != nullptr &&
        owner->color == Black && value->color == White) {
        MarkGray(value);
    }
}
```

이 예는 mutator와 마킹 작업이 교대로 실행되는 증분 수집기의 개념 코드다. 실제 동시 수집기에서는 필드 저장과 색·마킹 큐 접근 사이의 원자성 및 메모리 순서를 별도로 보장해야 한다.

세대별 GC에서는 오래된 객체가 젊은 객체를 가리키는 참조를 remembered set에 기록한다. 젊은 세대 수집 때 전체 오래된 세대를 스캔하지 않으려면 이 장벽이 정확해야 한다. 장벽 누락은 드물고 비결정적인 use-after-free처럼 나타난다.

### 정지 시간의 예산화

수집 작업을 여러 프레임으로 나눈다고 자동으로 마감이 보장되지는 않는다. 한 단계가 스캔하는 객체 수와 바이트 수의 상한이 있어야 한다.

```text
frame GC budget = 0.5 ms
work unit        = object scan or N bytes
deadline reached -> preserve queue and resume next frame
```

루트 스캔, 큰 배열 스캔, 최종화처럼 쪼개기 어려운 단계가 최악 중단 시간을 결정한다. 큰 객체를 별도 공간에 두거나 카드 테이블로 변경 영역만 추적하고, finalizer가 오디오·렌더링 자원을 직접 해제하지 않게 하는 이유다.

GC 처리량, 평균 정지, p99 정지, 최대 정지를 따로 측정해야 한다. 게임에서는 총 CPU가 조금 늘더라도 최대 정지를 낮추는 설정이 더 나을 수 있다.

## 6. 오류, 예외, 코루틴

런타임 오류는 정의되지 않은 연산, 자원 부족, 호스트 API 실패 등에서 발생한다. 오류를 값으로 반환할지, 예외로 비지역 전파할지에 따라 제어 흐름과 정리 규칙이 달라진다.

예외 구현은 프레임을 되감으며 핸들러를 찾고, 각 프레임의 정리 동작을 실행해야 한다. 오류 발생 경로가 정상 경로의 불변식을 깨지 않도록 자원 소유권을 명확히 해야 한다.

코루틴은 실행을 중단하고 상태를 보존했다가 재개한다. 보존 대상은 명령 위치, 지역 변수, 대기 이유다. 스택 전체를 보존하는 방식과 상태 머신으로 변환하는 방식이 있다.

코루틴 취소는 단순 플래그가 아니다. 중단된 작업이 가진 자원을 정리하고, 재개되지 않을 것을 대기자에게 알리며, 취소가 중첩 호출로 어떻게 전파되는지 정의해야 한다.

## 7. 호스트 경계와 샌드박스

스크립트는 엔진 기능을 호스트 API로 호출한다. 이 경계는 타입 변환, 수명, 스레드, 권한의 경계다.

- 제거된 엔티티를 가리키는 참조를 어떻게 검증할 것인가
- 스크립트가 메인 스레드 전용 API를 호출하면 어떻게 할 것인가
- 한 프레임 명령 수와 메모리를 어떻게 제한할 것인가
- 파일, 네트워크, 시스템 시간 접근을 허용할 것인가

샌드박스는 금지 목록이 아니라 능력(capability)을 명시적으로 부여하는 구조가 안전하다. 실행 명령 수, 재귀 깊이, 할당량, 벽시계 시간을 함께 제한해야 무한 루프와 자원 고갈을 통제할 수 있다.

## 8. 관측성과 검증

실행기는 “결과가 맞다”뿐 아니라 문제가 생겼을 때 설명 가능해야 한다.

- 소스 위치가 포함된 스택 추적
- 함수별 실행 시간과 할당량
- 명령 수와 중단 원인
- 결정적 입력 로그와 재현
- 바이트코드 디스어셈블
- 객체와 루트 그래프 검사

검증은 의미 보존을 중심으로 한다. 트리 순회 실행기와 VM의 차등 테스트, 임의 프로그램 생성, GC 스트레스 모드, 예외와 취소 지점 삽입, 명령 예산 초과 테스트가 유용하다.

결정론이 필요한 시뮬레이션에서는 시스템 시간, 난수, 컨테이너 순회 순서, 부동소수점 환경까지 통제해야 한다. 같은 소스 코드만으로 같은 실행을 보장할 수는 없다.

## 9. 세이브 데이터와 런타임 버전

게임 런타임은 실행 중인 상태가 저장 파일과 패치 사이를 건너야 한다는 제약을 가진다. 스크립트 객체를 그대로 메모리 덤프로 저장하면 포인터 주소, VM 내부 레이아웃, 해시 테이블 순서가 함께 굳어 버린다. 다음 빌드에서 필드 순서나 값 표현이 바뀌면 로드가 깨진다.

저장 가능한 상태와 실행 전용 상태를 분리해야 한다.

| 상태 | 저장 가능 여부 | 이유 |
|---|---|---|
| 퀘스트 변수, 인벤토리 플래그 | 가능 | 게임 의미를 가진 안정 데이터 |
| 객체 포인터 | 직접 저장 금지 | 실행마다 주소가 달라짐 |
| 호출 스택 | 제한적 | 중단 지점과 코드 버전이 맞아야 함 |
| 네이티브 핸들 | 직접 저장 금지 | 엔진 자원 수명과 연결됨 |
| 난수 시드 | 가능 | 결정적 재현에 필요 |

안정적인 저장은 ID와 스키마를 기준으로 한다. 객체 참조는 포인터가 아니라 엔티티 ID나 스크립트 객체 ID로 저장하고, 로드 시 현재 런타임 객체로 다시 연결한다. 필드는 이름 또는 안정된 필드 ID로 기록하며, 누락된 필드의 기본값과 제거된 필드의 무시 규칙을 둔다. 바이트코드 캐시는 언어 버전, 컴파일 옵션, 표준 라이브러리 버전, 호스트 바인딩 버전을 키에 포함해야 한다. 저장 파일 스키마는 native Value layout과 같은 바이트 표현일 필요가 없다. in-memory ABI, 바이트코드 파일 형식, persistence schema를 각각 다른 계약으로 두고, 로드/저장 경계에서 명시적으로 변환·검증한다.

핫 리로드와 세이브 로드는 같은 문제의 두 형태다. 실행 중인 상태를 새 코드 의미에 맞춰 이주시켜야 한다. 함수 본문은 바뀌었지만 중단된 코루틴의 명령 포인터가 옛 바이트코드 오프셋을 가리키면 재개할 수 없다. 따라서 중단 가능한 스크립트는 안정된 await 지점, 상태 머신 ID, 지역 변수 스키마를 따로 보관해야 한다.

런타임 버전 정책은 호환성 계약이다.

```text
save schema version = 12
bytecode version    = language hash + compiler options
binding version     = exposed native API hash
```

이 값이 맞지 않으면 조용히 실행하지 말고 명시적으로 마이그레이션하거나 거부해야 한다. 잘못된 버전의 바이트코드나 저장 상태를 받아들이는 런타임은 타입 안전한 언어 위에 정의되지 않은 상태를 다시 들여오는 셈이다.

---

## 결론

런타임은 구문 트리를 실행하는 반복문이 아니라 언어의 동적 의미를 책임지는 시스템이다. 호출과 수명, 객체 정체성, 오류 전파, 중단과 재개의 규칙이 서로 맞물린다.

게임용 실행기에서는 처리량과 함께 프레임별 상한, 관측성, 호스트 경계, 결정론, 저장 호환성을 설계해야 한다. 실행 모델이 명확할수록 최적화와 도구는 그 위에서 의미를 잃지 않고 성장할 수 있다.
