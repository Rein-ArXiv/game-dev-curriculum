# Mega Defense 구현 과정

이 문서는 최종 코드가 어떤 문제를 어떤 불변식으로 해결했는지 기록한다. 학습 순서별 소스
복사본은 두지 않는다. `include/`, `games/defense/`, `tests/`의 현재 코드가 유일한 실행
가능 원본이며, 이 문서는 결정의 이유와 재현 방법을 소유한다.

## 1. 제품 목표를 먼저 고정했다

캡스톤의 목표는 모듈 이름을 채우는 것이 아니라, 사람이 반복해서 플레이할 수 있는 2D 협동
디펜스에서 다음 경계를 실제로 통과시키는 것이다.

- 입력이 검증된 게임 명령이 된다.
- 권위 시뮬레이션이 렌더와 네트워크 출력의 단일 원본이 된다.
- 외부 콘텐츠는 검증을 통과한 완전한 구성만 채택된다.
- 두 OS 프로세스가 실제 UDP로 명령과 상태를 교환한다.
- 종료 결과가 크래시 복구 가능한 저장소에 원자적으로 기록된다.
- 표시 백엔드를 바꿔도 게임 규칙과 패킷 형식이 바뀌지 않는다.

이 목표로 인해 클라이언트 제품은 `mega_defense` 하나이며 `--host`, `--join`, `--vulkan`은
같은 게임의 실행 모드다. 렌더가 없는 배포 역할만 `mega_defense_server`로 분리한다. 두 타깃은
같은 `GameWorld`, 콘텐츠 로더, 패킷 형식을 사용하며 장르별 샘플이나 단계별 게임 복사본은 없다.

그 경계들을 하나씩 통과시키는 동안 게임이 요구하는 축이 늘어났고, 지금 측정값은
`include/` 헤더 114개 전부가 제품에서 도달 가능, 랩 전용 등재 0개다. 이것은 "모듈을
넣기 위해 게임을 키운" 결과가 아니라 그 반대다 — 규모·지형·개체·운영 네 축으로 게임이
커지면서 각 모듈이 푸는 실패 조건이 게임 안에 실제로 생겼고, 생기지 않은 것은 지금도
들어오지 못한다. 어느 축이 어느 게임 기능에 붙어 있는지는
[`AXIS_OWNERSHIP.md`](AXIS_OWNERSHIP.md)가 소유하며, 도달 불가인데 근거도 등재되지
않은 헤더는 빌드가 실패시킨다.

## 2. 헤드리스 규칙에서 플레이 가능한 게임으로 바꿨다

초기 게임 규칙은 자동으로 적을 생성하고 타워를 배치하는 헤드리스 시뮬레이션이었다.
정확성 테스트에는 충분하지만 사람의 선택이 없으므로 게임은 아니었다. 제품 경계에서는
다음 상태와 명령을 명시했다.

```text
State
  DefenseMap
  Towers / Enemies / Projectiles
  Gold / CoreHp / Wave / MatchResult

Commands
  PlaceTower
  UpgradeTower
  SellTower
  SetTargetMode
```

모든 상태 변경은 `GameWorld` 메서드 또는 wire 명령 적용 함수를 통과한다. UI의 초록색
배치 미리보기는 편의 기능이고 권한 검사가 아니다. 실제 배치는 월드가 골드, 경기 상태,
타일 타입, 중복, 타워 상한을 다시 검사한다.

타워는 Cannon, Gatling, Splash, Sniper 네 종류이며 공격력, 사거리, 발사 간격, 광역
반경, 가격이 다르다. 적은 Normal, Fast, Tank, Swarm, Boss 다섯 종류이며 체력·속도·
코어 피해·보상 배율이 다르다. 강화와 판매는 누적 투자 비용을 기준으로 계산하고,
Nearest, First, Strongest 타게팅은 같은 적 집합에 서로 다른 점수 함수를 적용한다.

## 3. 시뮬레이션 시간과 프레임 시간을 분리했다

창 루프의 실제 경과 시간은 가변적이지만 게임 규칙은 60Hz 고정 스텝으로 전진한다.

```text
real frame delta
      |
      v
 accumulator -- while >= 1/60 --> GameWorld::Step(1/60)
      |
      +--------------------------> render current snapshot
```

한 렌더 프레임에서 최대 다섯 틱만 보충한다. 디버거 중단이나 창 이동으로 큰 시간이 들어왔을
때 밀린 시뮬레이션을 끝없이 따라가며 프레임을 더 늦추는 spiral of death를 막기 위해서다.
상한에 걸리면 남은 누적 시간을 버린다. 이는 완전한 실시간 보존보다 상호작용 가능성을
선택한 정책이다.

한 틱 안의 순서는 웨이브 스폰, 적 이동, 타워 발사, 발사체 충돌, 죽은 객체 정리, 승패
판정으로 고정했다. 같은 입력과 시작 상태가 같은 순서로 처리되어야 테스트와 호스트 권위
결과를 비교할 수 있다.

싱글플레이 일시정지는 누적 시간을 0으로 만들고 시뮬레이션 틱만 멈춘다. 입력과 렌더는
계속되어 정지 중 건설과 강화를 허용한다. 협동 세션에는 일시정지 권한과 합의 프로토콜이
없으므로 제공하지 않는다.

## 4. 자유 좌표를 검증된 타일 맵으로 바꿨다

자유 좌표 배치는 경로 위 건설, 겹치는 타워, 화면과 규칙의 불일치를 만들었다. 맵은
Buildable, Path, Spawn, Core, Blocked 타일로 바꾸고 클릭 위치를 셀 중심에 스냅했다.

외부 `level.txt`는 직사각형이어야 하고 스폰과 코어가 각각 하나여야 한다. 스폰에서
코어까지 상하좌우로 걸을 때 방문하지 않은 경로 후보가 매 위치 정확히 하나여야 하며,
코어 도착 시 모든 경로 셀을 소비해야 한다. 이 검사는 끊긴 경로, 분기, 순환, 사용하지
않는 경로 조각을 거부한다.

검증 실패 때 일부 외부 타일과 일부 기본 타일을 섞지 않는다. 맵 전체를 기본값으로 되돌려
어떤 규칙이 적용됐는지 명확하게 유지한다.

맵의 출처는 이제 둘이고 계약이 다르다. `map=classic`(기본값)은 위 문단 그대로다 — 파일이
정한 무분기 사슬이고 매치 내내 불변이다. `map=procgen` 은 시드에서 41x41 격자를 만들고
(미로 골격 + 노이즈 밀도장), 경로는 파일이 아니라 스폰→코어 BFS 의 결과다. 그래서 타워와
안착 잔해가 칸을 점유해 경로를 바꿀 수 있고, 배치 명령마다 "이 칸을 막아도 코어에 닿는가"를
flood fill 로 검사한다. 두 모델이 공유하는 것은 규칙이 읽는 경로 배열 하나뿐이다.

## 5. 외부 콘텐츠를 원자적 구성으로 취급했다

스프라이트, 레벨, 웨이브, 밸런스는 실행 파일 재컴파일 없이 교체할 수 있다. 각 파일은
서로 다른 신뢰 경계를 가진다.

| 파일 | 검증 | 실패 정책 |
|---|---|---|
| `tower_*.ppm`, `enemy_*.ppm`, `core.ppm` | P3, 256x256 상한, 채널·픽셀 수 | 해당 스프라이트만 내장 외형 |
| `level.txt` | 직사각형, 단일 S/C, 연속 무분기 경로 | 맵 전체 기본값 |
| `waves.txt` | 1~100행, 모든 수치 범위, 적 enum | 웨이브 전체 기본값 |
| `balance.script` | 64KiB, 구문·실행 성공, 유한 수와 범위, 실행 스텝 예산 10⁶·중첩 깊이 64 | 밸런스 전체 기본값 |
| `boss.pose` | 본 수 선언 일치, 키 시각 단조 증가, 들림·롤·고관절 각 범위, 클립마다 키 2개 이상 | 포즈 전체 기본값 |

밸런스 스크립트는 시작 골드, 코어 체력, 적 체력·속도·보상 배율을 계산한다. 스크립트가
성공해도 출력이 wire 체력 표현과 게임플레이 상한을 넘으면 채택하지 않는다. 이는
“실행 성공”과 “도메인 값으로 유효함”이 다른 조건임을 코드로 드러낸다.

## 6. 입력을 물리 키에서 액션으로 분리했다

키 코드를 게임 명령에 직접 연결하면 리매핑과 컨텍스트 전환이 입력 처리 전체를 건드린다.
`InputMap`은 물리 키를 `upgrade`, `sell`, `target_mode`, `pause` 같은 액션에 매핑한다.

프레임 시작에서 눌림·놓임 집합을 비우고, 현재 키 상태를 이전 활성 상태와 비교한다.
따라서 키를 누르고 있는 동안 판매 명령이 매 프레임 제출되지 않는다. 게임 루프는
`WasPressed("sell")`만 묻고 `X` 키를 알지 않는다.

마우스 클릭은 먼저 권위 스냅샷의 타워 선택을 시도하고, 타워가 없으면 배치 명령을 만든다.
클라이언트 화면의 선택 상태는 로컬 UI 상태지만, 배치·강화·판매 결과는 호스트 스냅샷이
돌아온 뒤 확정된다.

## 7. 도메인 AI와 물리 경계를 실제 게임 규칙에 연결했다

타워 AI는 동시 생존 적(기본 상한 64, `--ab scale=large` 에서 2048)을 순회하며 모드별 점수를
최소화한다. First 모드는 경로 진행도를, Nearest는 거리 제곱을, Strongest는 음의 체력을 점수로
사용한다. 조준 후보 자격은 `stealth=1` 에서 기하가 아니라 인지가 정한다 — 은신 개체는
레이더의 시야 원뿔 안이면서 시야 격자 상 시선이 바위에 막히지 않거나, 직전 틱에 발사한 타워의
청각 반경 안일 때만 후보가 된다. 적의 결정은 두 층이다: 잡목은 상태 기계 한 벌을 전원이
돌려 쓰고(상태는 개체가 든다), 정예는 `elite_brain=fsm|bt` 의 두 표현 중 하나로 후퇴·회복·
슬램을 돌린다. 두 표현은 같은 행동 본체를 부르고, 같은 매치에서 위치·체력 열이 비트 동일해야
한다는 것이 그 축의 불변식이다.

작업 스케줄러는 `--ab jobs=N` 으로 켤 수 있고, 그 조준 질의를 인덱스 구간으로 나눈다 — 다만 측정
결과 이 규모에서는 청크 배송비가 청크 안의 일보다 커서 기본값은 직렬(`jobs=0`)이다.

발사체는 발사 시 목표의 안정 ID를 보존한다. 매 틱 살아 있는 목표를 찾아 최신 위치로
유도하고, 공용 물리 모듈의 원-원 충돌 판정으로 명중 여부를 계산한다. 목표가 먼저
사라지면 마지막으로 알려진 위치까지 진행해 소멸한다. 광역 피해도 폭발 원과 적 충돌 원의
겹침으로 계산한다.

충돌로 발사체가 사라진 위치는 렌더 전용 파티클을 만든다. 파티클은 엔진의 수명·
swap-remove 경로를 사용하지만 `GameWorld`, 저장, 네트워크에는 들어가지 않는다. 시각
효과가 권위 상태 checksum을 바꾸지 않는 경계가 유지된다.

## 8. 실제 협동 세션을 호스트 권위로 구성했다

`LoopbackNet`은 손실·지연·재정렬을 결정적으로 주입하는 테스트 백엔드다. 제품은
Winsock/POSIX 비차단 UDP를 사용하는 `UdpTransport`를 쓴다. 둘은 `ITransport` 계약을
공유하지만 loopback 통과를 실제 멀티플레이 완료로 세지 않는다.

클라이언트는 상태를 보내지 않고 명령만 보낸다. 명령에는 32비트 시퀀스가 있으며 호스트는
정확히 기대한 번호만 한 번 적용한다. 클라이언트는 100ms마다 미확인 명령을 재전송하고,
호스트 스냅샷의 누적 ACK가 도착하면 큐 앞에서 제거한다.

```text
client input
   |
   v
pending ordered commands -- UDP/retry --> authoritative host
                                            |
                                            v
                                   validate + apply + tick
                                            |
client render <-- interpolation buffer <-- 20Hz snapshot + cumulative ACK
```

호스트는 첫 데이터그램 주소를 즉시 피어로 고정하지 않는다. magic, 버전, 길이가 맞는
Hello를 상위 프로토콜이 확인한 뒤에만 `AcceptLastSender`로 단일 슬롯을 승인한다. 임의의
선행 패킷이 슬롯을 점유하는 문제를 줄이지만 인증·암호화·rate limiting을 제공하는 것은
아니다.

## 9. 스냅샷을 MTU 예산 안에 고정했다

호스트는 세 틱마다 20Hz 스냅샷을 보낸다. 타워 16, 적 64, 발사체 20의 상한을 두고 위치는
1/8 픽셀, 체력은 1/4 단위 16비트로 양자화한다.

1200바이트 예산을 지키는 것은 런타임 검사가 아니라 `static_assert`다. 세 컬렉션이 전부
상한이면 1198바이트이므로 writer 결과가 1200을 넘는 일은 **구성상 일어날 수 없고**,
상한을 올리면 컴파일이 먼저 멈춘다. writer 뒤의 크기 비교는 그 사실 위에 남겨 둔 마지막
자물쇠일 뿐이며, 어떤 테스트도 그것을 발동시킬 수 없다. "검사로 보장"이 아니라 "구성상
도달 불가"라고 읽어야 한다.

상한을 넘는 월드가 들어오면 초과분은 잘리고 스냅샷 flags에 `truncated`가 실린다. 이것은
조용한 손실이 될 수 있는 유일한 자리라, 보내는 쪽(`WriteSnapshot`의 out 인자)과 받는 쪽
(디코드한 flags) 양쪽이 `snapshots_truncated` 카운터로 센다. 지금의 게임플레이 상한에서는
이 값이 0으로 남지만, 상한 관계가 깨지면 엔티티가 사라지기 전에 이 숫자가 먼저 움직인다.

디코더는 헤더, payload 길이, 컬렉션 상한, enum 범위, 체력 관계, 남은 바이트를 모두
검사한다. “필요한 필드까지 읽었으니 성공”하지 않고 패킷을 정확히 끝까지 소비해야 한다.

클라이언트는 최근 스냅샷 여덟 개를 보관하고 약간 과거의 시각을 렌더한다. 안정 ID가 같은
적과 발사체만 보간하고, 타워 생성 같은 불연속 상태는 최신 값을 사용한다. tick wrap이
감지되면 이전 epoch 표본을 버린다.

## 10. 저장과 지표를 게임 루프 밖의 계약으로 만들었다

매치 종료 시 프로필과 매치 기록을 하나의 WAL 트랜잭션으로 기록한다. COMMIT 마커 뒤
`fsync` 또는 `_commit`까지 성공해야 완료로 센다. 복구는 완전하게 커밋된 접두사만 재생해
잘린 마지막 트랜잭션의 부분 적용을 막는다.

프로필은 실행 파일 디렉터리가 아니라 사용자 데이터 디렉터리에 둔다. 설치 디렉터리가
읽기 전용인 환경에서도 저장이 가능하고 사용자별 상태가 분리된다.

운영 레지스트리는 프레임 시간, 원격 명령 수, 스냅샷 수와 바이트, 스냅샷 잘림 횟수를
집계한다. 집계한 값은 **전부** 종료 시 로컬 콘솔 한 줄에 출력한다 — 프레임 p95,
스냅샷 바이트 p95와 최댓값, `snapshots_truncated`까지. 수집만 하고 출력하지 않는 지표는
두지 않는다. 관측할 수 없는 지표는 없는 지표와 같고, 그 상태는 "집계한다"는 서술만 참으로
남겨 문서를 거짓말로 만든다.

지표는 클라이언트·호스트 실행 파일(`mega_defense`)의 것이다. 렌더 없는 전용 서버
(`mega_defense_server`)는 자기 루프의 tick·players·commands·rejected를 직접 출력하며 이
레지스트리를 쓰지 않는다. 외부 텔레메트리 수집이나 개인정보 파이프라인을 구현한 것처럼
설명하지 않는다.

## 11. 같은 게임에 두 표시 백엔드를 연결했다

게임은 RGBA8 CPU 프레임버퍼에 타일, 스프라이트, HUD, 파티클을 그린다. GDI는 이 버퍼를
창에 blit한다. Vulkan은 staging buffer에서 이미지로 복사하고 풀스크린 삼각형으로
swapchain에 표시한다.

Vulkan이 별도 게임 규칙이나 별도 에셋 포맷을 소유하지 않으므로 백엔드 비교가 같은 입력
프레임을 대상으로 한다. `--gpu-selftest`는 실제 장치와 스왑체인에서 다섯 프레임을
present한다. Vulkan SDK가 없는 구성은 GDI 경로만 빌드하고 `--vulkan` 요청을 명시적으로
거부한다.

이 명령은 `mega_defense_gpu_selftest`라는 이름으로 ctest에 등록돼 있다. 요구 조건(Vulkan
빌드·창 백엔드·장치와 셰이더)이 없으면 실패가 아니라 종료 코드 77로 끝나고, CTest의
`SKIP_RETURN_CODE`가 그것을 Skipped로 센다. 실패는 셋 다 갖췄는데 present가 깨졌을 때만
난다. 조건이 없다고 빨간불을 켜는 게이트는 GPU 없는 러너에서 상시 실패로 남아 곧
무시당하고, 그렇다고 등록하지 않으면 "자동 검증한다"는 서술이 근거를 잃는다.

## 12. 통합하지 않은 모듈에도 이유가 있다

모듈을 제품에 들이는 기준은 하나다. **그 모듈이 푸는 실패 조건이 게임 안에 실제로
있는가.** 이 기준으로 들어온 것과 남은 것이 시간에 따라 바뀜다. 경로 탐색이 대표적이다 —
외부 레벨이 무분기 회랑 하나를 주던 동안은 범용 A*와 Flow Field 가 같은 경로를 다시 계산하는
일이었고, 절차 맵이 분기 지형을 만들면서 그 전제가 사라졌다. 현재는 통행 격자 하나가
통행 가능성을 소유하고, 그 위에서 `pathing=astar|flowfield` 두 팔이 **같은 비용의 경로를
낸다**는 것이 두 팔의 상호 검사다.

아직 들어오지 않은 모듈들은 독립 테스트로 자료구조와 알고리즘 계약만 검증한다. 그
목록과 각각의 근거는 랩 전용 등재부가 소유하며, 등재되지 않은 미도달 헤더는 빌드 실패다.

- 물리: 이동 표적과 충돌 반경이 필요하다.
- 엔진 입력: 키 edge와 액션 분리가 필요하다.
- 엔진 파티클: 렌더 전용 수명 관리가 필요하다.
- 스크립트: 재컴파일 없는 계산형 밸런스 구성이 필요하다.
- DB와 직렬화: 매치 결과의 원자적 영속이 필요하다.
- 네트워크: 두 프로세스 사이 권위 상태 공유가 필요하다.

이 기준은 “모든 기술을 녹인다”를 모든 헤더를 호출한다는 뜻이 아니라, 기술이 해결하는
실제 실패 조건을 제품 경로에서 드러낸다는 뜻으로 고정한다.

## 13. 검증을 계층별로 분리했다

CTest 대상 중 `mega_defense_gpu_selftest` 하나만 환경에 따라 Skipped가 될 수 있고(아래
GPU 행), 나머지는 어디서든 Passed여야 한다. 대상 수를 이 문서가 적지 않는 이유는
그 수를 CMake 의 `tests/test_*.cpp` 글록과 등록된 셀프테스트가 정하기 때문이다 — 적어 두면
파일 하나가 늘 때마다 이 줄이 거짓이 되고, 거짓이 된 줄은 게이트가 아니라 장식이다.
핵심 검증은 다음과 같다.

| 계층 | 검사 |
|---|---|
| 게임 규칙 | 배치, 경제, 업그레이드, 판매, 타게팅, 승패 |
| 콘텐츠 | 맵·웨이브·밸런스 정상 로드와 원자적 폴백 |
| 프로토콜 | 명령·스냅샷 왕복, 손상·절단 거부, 상한 초과 월드의 `truncated` 신호, 1200바이트 예산(런타임 검사가 아니라 `static_assert`) |
| 실제 소켓 | localhost UDP 명령에서 ACK 스냅샷까지 |
| 제품 프레임 루프 | 제품 `DefenseApp`을 클라이언트로 구성해 진짜 소켓 위에서 `Step()` 구동 |
| 프로세스 | 독립 listen host·클라이언트, 전용 서버·두 UDP 끝점의 권위 상태, 제품 실행 파일 둘로 붙인 협동 왕복 |
| 입장 보안 | HMAC-SHA256 알려진 벡터, 토큰 변조·만료·잘못된 server audience 거부 |
| 장애 | 35% 손실, 지연, 재정렬 아래 ordered 명령 수렴 |
| 장기 실행 | 반복 매치의 유한 값, ID 유일성, 엔티티 상한 |
| 저장 | 재오픈 복구와 미완 트랜잭션 폐기 |
| 렌더 | 픽셀, 알파, 클리핑, PPM 검증 |
| GPU | 실제 Vulkan swapchain 5프레임 present. Vulkan 빌드·창·장치가 없으면 실패가 아니라 Skipped(종료 코드 77) |
| 결정성 | 한 프로세스가 기록한 조작 열과 골든 해시 체인을 **다른 프로세스**가 재생해 틱 단위로 대조. 솔로·호스트·아바타 세 팔 |
| 메모리 | 같은 테스트 목록을 AddressSanitizer 계측 아래에서 다시 실행(별도 빌드 디렉터리) |

재현 명령은 다음과 같다.

```powershell
cmake -S . -B build
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
.\build\bin\Release\mega_defense.exe --selftest
.\build\bin\Release\mega_defense.exe --gpu-selftest --vulkan
```

협동 세션은 두 터미널에서 실행한다.

```powershell
.\build\bin\Release\mega_defense.exe --host 27015
.\build\bin\Release\mega_defense.exe --join 127.0.0.1 27015
```

같은 두 명령을 `--selftest`로 붙이면 창 없이 협동 왕복만 확인한다. 이때 두 쪽은 서로 다른
질문에 답한다. 호스트는 솔로와 같은 기준으로 판정한다 — 이겼는가. 클라이언트는 권위
월드를 소유하지 않으므로 그 질문을 물을 수 없고, 대신 왕복이 실제로 일어났는가를 묻는다:
붙었고, 스냅샷을 받았고, 명령 패킷을 실제로 내보냈고, 호스트가 그 명령을 순서대로
반영했다고 통지했는가. 넷이 모두 참일 때만 `result=LINKED`와 종료 코드 0이다. 상태를
받는데 내 명령이 반영되지 않으면 `NO-ACK`, 아예 붙지 못했으면 `NO-LINK`이고 둘 다 1이다.

```powershell
.\build\bin\Release\mega_defense.exe --host 27015 --selftest 6000
.\build\bin\Release\mega_defense.exe --join 127.0.0.1 27015 --selftest 4000
```

이 구분이 필요한 이유는 판정 기준이 없으면 자동 검사가 클라이언트 쪽 결과를 읽을 수
없기 때문이다. 그 상태에서는 클라이언트가 명령을 한 번도 내보내지 못하는 결함 —
협동 플레이어가 타워를 하나도 세울 수 없는 결함 — 이 모든 테스트를 통과한다.
`test_defense_coop_process`가 정확히 이 두 명령을 띄우고 양쪽 표준 출력을 대조한다.

결정성 리플레이는 프로세스를 갈아 끼운다. 기록은 조작만 적지 않고 **배정이 끝난 뒤의
A/B 팔 27개 · 매치 시작 시각 · 전용 프로필 저장소 경로**까지 고정한다 — 셋 중 하나라도
빠지면 결정성 결함이 아닌 것이 결정성 결함으로 보고되고, 거짓 실패를 내는 게이트는
며칠 안에 꺼진다.

```powershell
.\build\bin\Release\mega_defense.exe --selftest 4000 --record solo.mgrp
.\build\bin\Release\mega_defense.exe --verify-replay solo.mgrp
```

`ctest`에는 세 팔의 기록·재생 짝 여섯이 CTest fixture로 묶여 있다(기록이 먼저 끝나야
재생할 파일이 있다). 갈리면 `last_agree`와 `suspect`로 몇 번째 틱인지가 나온다.

새니타이저 빌드는 트리를 따로 쓴다. 계측된 번역 단위와 아닌 것이 섞이면 **없는 결함이
보고되기** 때문이고, 캐시 변수 + 별도 디렉터리가 그 혼합을 구조적으로 막는다.

```powershell
cmake -S . -B build_asan -DMEGA_SANITIZE=address
cmake --build build_asan --config Release
ctest --test-dir build_asan -C Release --output-on-failure --timeout 900
```

`--timeout 900`이 필요한 이유는 계측이 검사마다 다르게 느려지기 때문이다 — GPU present
1.5배, 협동 프로세스 왕복 2.5배, 절차 지형 발파 90배, 전체 8배 안팎(64.83초 → 466~540초).
테스트별 타임아웃은 계측 없는 실행 기준으로 걸려 있어서, 전역 하한을 올리지 않으면
느려진 것이 실패로 보고된다. MSVC가 지원하는 값은 `address` 하나뿐이고 다른 값은 구성
단계에서 거절한다 — 검사하지 않은 것을 검사했다고 믿게 두지 않는다.

## 14. 전용 서버와 라이브 서비스의 경계를 연결했다

listen host는 플레이어 한 명이 권위와 렌더를 함께 소유하므로 LAN 협동을 시작하기 쉽다.
그러나 매치메이킹이 선택한 서버에 두 클라이언트를 배치하려면 렌더 없는 권위 프로세스와
입장 자격 증명이 필요하다. `mega_defense_server`는 끝점별 세션을 보존하는 `UdpServer`로
두 플레이어를 받고, 두 명이 같은 `MatchId`로 승인된 뒤에만 고정 틱을 시작한다.

라이브 서비스의 게임 토큰은 서버 ID, 플레이어 ID, 매치 ID, 일회성 토큰 ID, 만료 시각을
HMAC-SHA256으로 보호한다. 전용 서버는 서명을 상수 시간으로 비교하고 server audience와
만료를 검사한다. 같은 토큰이나 플레이어를 다른 UDP 끝점에서 다시 사용하거나 서로 다른
매치의 토큰을 한 프로세스에 섞으면 입장을 거부한다. 클라이언트 실행 형식은 다음과 같다.

```powershell
.\build\bin\Release\mega_defense_server.exe --port 27016 --server-id mega-local-1
.\build\bin\Release\mega_defense.exe --join 127.0.0.1 27016 --token <PLAYER_1_GAME_TOKEN>
.\build\bin\Release\mega_defense.exe --join 127.0.0.1 27016 --token <PLAYER_2_GAME_TOKEN>
```

개발 기본 비밀은 `live_service_lab`과 일치해 로컬 실습을 단순화한다. 배포에서는 두 프로세스에
같은 32바이트 이상 비밀을 Base64로 넣은 `LIVE_SERVICE_TOKEN_SECRET`을 주입해야 한다. 토큰은
입장 승인만 담당한다. UDP payload 암호화, 패킷별 MAC, 재접속 자격 증명은 구현 범위가 다르다.

## 15. 현재 제품 경계

현재 토폴로지는 listen host 한 명과 원격 클라이언트 한 명, 또는 전용 서버와 원격
클라이언트 두 명이다. 실제 UDP, 권위 명령, 토큰 입장, 스냅샷 보간은 구현했지만 NAT
traversal, relay, 패킷 AEAD, rate limiting, 재접속, delta snapshot, AOI는 구현하지 않았다.
라이브 서비스가 서버를 자동 기동·종료하거나, Mega 서버가 HTTP heartbeat·결과 제출을
수행하는 오케스트레이션 경로도 별도 배포 계층의 책임으로 남아 있다.

그래픽스도 CPU 래스터 결과를 Vulkan으로 표시하는 구조다. GPU가 타일과 스프라이트를 직접
배치하거나 멀티패스 조명·머티리얼 그래프를 실행하는 렌더러가 아니다. 이 제한을 문서와
실행 옵션에서 명시해 캡스톤이 구현한 범위와 이론 커리큘럼 전체를 혼동하지 않는다.
