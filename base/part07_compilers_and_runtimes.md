## 들어가며

소스 코드는 CPU가 직접 실행하는 명령이 아니다. 구문 분석, 타입 검사, 중간 표현, 최적화, 코드 생성과 런타임 서비스를 거쳐 실행된다. 이 경로를 이해하면 언어 기능의 비용과 컴파일러가 허용하는 변환 범위를 설명할 수 있다.

컴파일러는 코드의 뜻을 보존하는 범위에서 프로그램을 바꾼다. 정의되지 않은 동작, 관찰 가능한 부작용, ABI와 런타임 계약은 그 범위를 결정한다. 이 글은 네이티브 컴파일과 관리 런타임을 하나의 실행 모델로 연결한다.

## 1. 소스에서 실행까지

전형적인 컴파일 경로는 다음과 같다.

```mermaid
flowchart LR
    Source[소스] --> Tokens[토큰]
    Tokens --> AST[구문 트리]
    AST --> Typed[타입·의미 분석]
    Typed --> IR[중간 표현]
    IR --> Opt[최적화]
    Opt --> Machine[기계어·바이트코드]
    Machine --> Runtime[실행 런타임]
```

렉서는 문자열을 토큰으로 나누고 파서는 문법 구조를 만든다. 의미 분석은 이름이 무엇을 가리키는지, 연산이 타입 규칙에 맞는지 확인한다. 중간 표현(IR)은 언어 구문을 제어 흐름과 데이터 흐름으로 낮춰 최적화하기 쉬운 형태를 만든다.

컴파일 오류, 링크 오류, 런타임 오류는 서로 다른 경계에서 발생한다.

[LLVM Language Reference](https://llvm.org/docs/LangRef.html)는 실제 산업용 IR이 타입, 제어 흐름, 메모리와 정의되지 않은 값을 어떤 계약으로 표현하는지 보여준다. IR 문법 자체보다 소스 의미가 최적화 가능한 형태로 어떻게 낮아지는지가 핵심이다.

- 컴파일 오류는 한 번역 단위의 구문과 타입 계약을 위반한다.
- 링크 오류는 선언과 정의, 심볼, 바이너리 결합 계약을 위반한다.
- 런타임 오류는 실제 입력과 상태에서만 드러나는 계약 위반이다.

이 구분은 빌드 시스템과 플러그인 경계를 설계할 때 중요하다.

## 2. 타입과 의미론

타입은 값의 집합과 허용된 연산을 정의한다. 정적 타입 검사는 실행 전에 일부 잘못된 프로그램을 거부하고, 동적 타입 검사는 실행 중 값의 태그와 연산을 확인한다.

정적 타입 언어도 모든 오류를 막지 못하며 동적 타입 언어도 타입이 없는 것이 아니다. 차이는 검사가 일어나는 시점과 표현 방식이다.

C++의 객체 모델에는 수명, 별칭, 정렬, 유효한 값 표현에 대한 규칙이 있다. 규칙을 위반한 정의되지 않은 동작은 컴파일러가 “발생하지 않는다”고 가정할 수 있다.

```cpp
int Divide(int value, int divisor) {
    // divisor가 0이거나, value가 표현 범위 최솟값이고 divisor가 -1이면 계약 위반이다.
    return value / divisor;
}
```

검사가 필요하다면 함수 경계에 전제 조건을 표현해야 한다. 디버그 검증만 둘지, 오류 값을 반환할지, 예외를 사용할지는 호출 환경의 실패 정책에 달려 있다.

C#의 nullable reference type은 정적 흐름 분석으로 null 가능성을 표현하지만 런타임에서 모든 `NullReferenceException`을 제거하지 않는다. 리플렉션, 외부 데이터, 억제 연산자, 초기화 경계는 별도 검증이 필요하다.

## 3. 중간 표현과 최적화

컴파일러 최적화는 관찰 가능한 동작을 보존하는 변환이다. 대표 변환은 다음과 같다.

- 상수 전파와 죽은 코드 제거
- 공통 부분식 제거
- 함수 인라이닝
- 루프 불변식 이동
- 벡터화와 명령 결합
- 탈출 분석과 할당 제거

최적화 레벨은 특정 변환을 보장하는 스위치가 아니다. 인라이닝과 벡터화 여부는 코드 크기, 별칭 가능성, 타깃 CPU, 프로파일 정보에 따라 달라진다.

다음 루프가 SIMD로 변환되려면 컴파일러가 반복 간 의존성이 없다고 증명할 수 있어야 한다.

```cpp
void Integrate(std::span<float> position,
               std::span<const float> velocity,
               float dt) {
    // velocity.size() >= position.size()를 전제로 한다.
    for (std::size_t i = 0; i < position.size(); ++i) {
        position[i] += velocity[i] * dt;
    }
}
```

두 span이 같은 메모리를 겹쳐 가리킬 수 있는지, 길이가 같은지, 타깃이 어떤 벡터 명령을 지원하는지가 결과에 영향을 준다. 길이 전제가 어긋나면 성능이 아니라 정확성 문제가 된다. 컴파일러는 정적으로 의존성을 증명하지 못하면 런타임 별칭 검사를 생성한 뒤 안전할 때만 벡터화 경로를 선택하기도 한다. 정적 증명, 런타임 검사 후 분기, 특정 의존성을 처리하는 변환은 서로 다른 메커니즘이다. 컴파일러 보고서와 생성 코드를 확인해야 한다.

분기를 산술식으로 바꾸면 항상 빨라지는 것도 아니다. 예측 가능한 분기는 비용이 작고, branchless 변환은 양쪽 경로의 계산과 추가 의존성을 만들 수 있다.

## 4. ABI와 링크

ABI(Application Binary Interface)는 독립적으로 컴파일된 코드가 만나는 바이너리 계약이다.

- 함수 인자의 레지스터·스택 전달 규칙
- 반환값 표현
- 구조체 레이아웃과 정렬
- 이름 장식과 심볼 규칙
- 예외 전파와 런타임 타입 정보

같은 언어 문법을 사용해도 컴파일러 버전, 옵션, 표준 라이브러리, 빌드 모드가 ABI를 다르게 만들 수 있다. 플러그인 경계에 STL 컨테이너나 컴파일러 종속 클래스 레이아웃을 그대로 노출하면 양쪽 모듈의 할당자와 런타임이 어긋날 수 있다.

안정적인 경계는 보통 명시적인 크기의 값, 불투명 핸들, 생성·해제 함수 쌍을 사용한다.

```cpp
extern "C" {
    RendererHandle* CreateRenderer(const RendererConfig*);
    void DestroyRenderer(RendererHandle*);
}
```

`extern "C"`는 이름 장식과 호출 규약의 일부를 고정하지만 그 자체로 모든 바이너리 호환성을 보장하지 않는다. 전달하는 구조체의 크기와 버전, 호출 규약, 예외 경계, 생성·해제 책임은 여전히 인터페이스 계약으로 명시해야 한다. 이 예는 안정적인 경계를 위한 인터페이스 발췌다.

동적 링크는 코드 공유와 교체를 가능하게 하지만 심볼 해석, 버전 호환성, 로드 순서라는 런타임 조건을 추가한다.

## 5. VM, JIT, 관리 런타임

가상 머신은 소스 언어를 바이트코드나 중간 언어로 실행한다. 인터프리터는 명령을 해석하고, JIT 컴파일러는 실행 중 관측한 타입과 호출 빈도를 이용해 기계어를 만들 수 있다. 다음 도식은 모든 관리 런타임의 필수 순서가 아니라 가능한 실행 구성의 예다.

```mermaid
flowchart LR
    IL[바이트코드] --> Interpreter[인터프리터]
    Interpreter --> Profile[실행 프로파일]
    Profile --> JIT[JIT 최적화]
    JIT --> Native[기계어]
    Native --> Deopt[가정 실패 시 역최적화]
```

JIT는 실제 실행 정보를 사용할 수 있지만 컴파일 시간이 런타임 비용에 포함된다. 계층형 컴파일은 빠른 초기 코드와 뜨거운 경로의 최적화 코드를 나눈다.

관리 런타임은 다음 서비스를 함께 제공할 수 있다.

- 가비지 컬렉션
- 예외와 스택 추적
- 리플렉션과 메타데이터
- 동적 코드 생성
- 비동기 상태 기계

C#의 `async` 함수는 일반적으로 상태 기계로 변환된다. 비동기 작업이 항상 새 스레드를 만들거나 항상 힙을 할당한다는 뜻은 아니다. 완료 방식, 캡처, 반환 타입, 런타임 최적화에 따라 비용이 달라진다.

LINQ도 단일 비용 모델을 갖지 않는다. 지연 실행은 열거 시점까지 작업을 미루며, 연산자 체인과 소스 종류에 따라 할당, 가상 호출, 데이터베이스 쿼리 번역이 달라진다. 표현이 간결하다는 사실과 실행 비용은 별도로 평가한다.

## 6. 성능을 검증하는 방법

언어 기능의 비용은 추측보다 생성 결과와 프로파일로 확인한다.

| 질문 | 확인 수단 |
|---|---|
| 함수가 인라인됐는가 | 최적화 보고서, 디스어셈블리 |
| 루프가 벡터화됐는가 | 벡터화 보고서, 성능 카운터 |
| 할당이 발생하는가 | 할당 프로파일러 |
| GC 일시 정지가 문제인가 | 세대별 수집·pause 분포 |
| JIT 준비 시간이 문제인가 | 시작 구간과 정상 구간 분리 |
| 분기가 문제인가 | branch miss와 입력 분포 |

마이크로벤치마크는 최적화된 릴리스 빌드에서 실행하고 결과를 소비해야 한다. 생성 코드가 같다면 문법 차이만으로 성능 차이를 주장할 수 없다.

정확성 검증도 빌드 모드를 나눠 수행한다. 정의되지 않은 동작은 디버그에서 우연히 동작하고 최적화 빌드에서만 드러날 수 있다. 여러 컴파일러와 sanitizer를 사용하면 한 구현의 우연한 동작에 의존하는 코드를 찾기 쉽다.

---

## 결론

프로그램 실행은 소스 문법에서 바로 CPU 명령으로 건너가지 않는다. 타입과 의미 분석, IR 최적화, ABI, 링크, VM과 런타임 서비스가 코드의 뜻과 비용을 결정한다.

컴파일러는 특정 최적화를 약속하는 마법사가 아니라 언어 계약 안에서 동작을 보존하는 변환기다. 성능은 문법 인상으로 판단하지 않고 최적화 보고서, 생성 코드, 할당과 런타임 프로파일로 검증해야 한다.
