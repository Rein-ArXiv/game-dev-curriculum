## 들어가며

네트워크는 원격 메모리 복사가 아니다. 데이터를 유한한 패킷으로 나누어 여러 장비와 링크를 통과시키며, 지연·손실·중복·재정렬·대역폭 경쟁이 발생한다. 애플리케이션은 필요한 보장을 직접 정의하거나 전송 프로토콜이 제공하는 보장을 사용해야 한다.

TCP와 UDP의 선택을 “신뢰성 대 속도”로만 설명하면 중요한 차이를 놓친다. 데이터 경계, 순서, 혼잡 제어, 연결 상태와 보안이 게임 프로토콜의 동작을 결정한다. 이 글은 전송 계층을 선택하기 위한 기본 모델을 다룬다.

전송 계층의 표준 계약은 [UDP RFC 768](https://www.rfc-editor.org/rfc/rfc768), [TCP RFC 9293](https://www.rfc-editor.org/rfc/rfc9293)에 정의돼 있다. UDP 기반 애플리케이션의 혼잡 제어와 안전한 사용 원칙은 [RFC 8085](https://www.rfc-editor.org/rfc/rfc8085)가 보완한다.

## 1. 패킷이 이동하는 계층

애플리케이션 메시지는 전송 계층, 인터넷 계층, 링크 계층의 헤더와 함께 전달된다.

```mermaid
flowchart LR
    Message[게임 메시지] --> Transport[TCP·UDP]
    Transport --> IP[IP]
    IP --> Link[Ethernet·Wi-Fi]
    Link --> Route[라우터와 링크]
    Route --> Peer[상대 호스트]
```

각 계층은 다른 계약을 소유한다.

| 계층 | 대표 책임 |
|---|---|
| 링크 | 한 링크의 프레임 전달 |
| IP | 주소와 여러 네트워크 사이 라우팅 |
| UDP | 포트가 있는 데이터그램 전달 |
| TCP | 신뢰성 있고 순서가 있는 바이트 스트림 |
| 애플리케이션 | 메시지 의미, 버전, 권한, 시간축 |

IP는 최선형 전달을 제공한다. 경로 중간에서 패킷이 사라지거나 순서가 바뀔 수 있다. 전송 계층과 애플리케이션이 필요한 복구 정책을 결정한다.

메시지 크기가 경로 MTU보다 크면 IP 단편화나 상위 계층 분할이 필요하다. 단편 하나의 손실이 전체 메시지를 무효화할 수 있으므로 게임 프로토콜은 일반적으로 안전한 페이로드 크기를 정하고 자체 메시지 분할·재조립 한계를 둔다.

## 2. 지연, 손실, 혼잡

종단 간 지연은 여러 성분의 합이다.

$$
D =
D_{\text{propagation}} +
D_{\text{transmission}} +
D_{\text{queue}} +
D_{\text{processing}}
$$

거리와 매체가 전파 지연을 만들고, 패킷 크기와 링크 속도가 전송 시간을 만든다. 큐 지연은 경쟁 트래픽에 따라 크게 변한다.

왕복 시간(RTT)은 요청이 상대에 도착해 응답이 돌아오는 시간이다. 단방향 지연은 두 호스트의 동기화된 시계가 없으면 RTT의 절반으로 정확히 구할 수 없다. 경로가 비대칭일 수 있기 때문이다.

손실은 독립적으로 한 장씩 발생하지 않을 수 있다. 혼잡, 무선 간섭, 큐 overflow는 연속 손실을 만든다. 평균 손실률만 사용한 시뮬레이션은 burst loss의 복구 비용을 놓친다.

지터는 지연의 변동이다. 실시간 게임은 평균 RTT뿐 아니라 지터 분포를 흡수할 버퍼와 보정 정책이 필요하다.

혼잡 제어는 송신자가 네트워크가 감당할 수 있는 전송률을 추정하고 조절하는 메커니즘이다. UDP를 사용한다고 네트워크 용량 제한이 사라지지 않는다. 애플리케이션이 무제한으로 보내면 자신과 다른 흐름의 손실·지연을 악화시킨다.

## 3. UDP의 계약

UDP는 메시지 경계를 보존하는 데이터그램 서비스다. 한 번의 송신 데이터그램은 수신 측에서 하나의 데이터그램으로 관찰되거나 도착하지 않는다.

UDP는 다음을 보장하지 않는다.

- 도착
- 중복 제거
- 송신 순서 유지
- 흐름 제어와 혼잡 제어
- 연결 상대의 신원

이 단순한 계약은 최신 상태가 오래된 상태를 대체하는 게임 데이터에 유용하다. 위치 스냅숏 10번이 사라졌다면 11번을 받기 위해 10번을 반드시 복구할 필요가 없을 수 있다.

반면 구매 결과, 매치 참가, 인벤토리 변경은 손실을 허용할 수 없다. 같은 UDP 소켓에서도 메시지 종류마다 전달 정책을 달리할 수 있지만 sequence, ACK, 재전송, 중복 제거, 순서 채널, 혼잡 제어와 보안이 필요하다.

불완전한 “Reliable UDP” 예제는 TCP보다 단순하지 않다. 특히 다음 경계가 빠지기 쉽다.

- 유한한 시퀀스 번호의 래핑 비교
- 재전송 타이머와 RTT 추정
- 수신 윈도와 메모리 상한
- 패킷 중복과 재정렬
- 단편 재조립 제한
- 혼잡 시 전송률 감소
- 인증되지 않은 ACK와 증폭 공격

## 4. TCP의 계약

TCP는 신뢰성 있고 순서가 있는 **바이트 스트림**을 제공한다. 애플리케이션이 보낸 패킷 경계나 `send` 호출 경계는 보존하지 않는다.

```cpp
std::uint32_t length{};
ReadExactly(socket, &length, sizeof(length));
ValidateLength(length);
ReadExactly(socket, payload.data(), length);
```

한 번의 `recv`가 메시지 전체를 반환한다고 가정하면 안 된다. 메시지 길이 또는 구분자를 애플리케이션 프로토콜에 둬야 한다.

TCP는 손실된 바이트를 재전송하고 앞선 바이트가 복구될 때까지 뒤 바이트를 애플리케이션에 공개하지 않는다(복구된 뒤에야 순서대로 공개한다). 이 동작은 파일과 명령 스트림에 적합하지만, 오래된 실시간 상태가 최신 상태의 전달을 막는 head-of-line 지연을 만들 수 있다.

“모든 TCP 패킷이 반드시 도착한다”는 표현은 정확하지 않다. 연결이 유지되는 동안 바이트 스트림의 신뢰성을 제공하며, 영구 장애나 연결 종료 후에는 애플리케이션이 어느 메시지까지 처리됐는지 별도 확인해야 한다.

TCP도 메시지의 비즈니스 처리를 보장하지 않는다. 송신이 성공해도 상대 애플리케이션이 저장을 완료하기 전에 종료될 수 있다. 중요한 명령은 애플리케이션 수준 ID, 응답, 멱등성 정책이 필요하다.

## 5. 게임 프로토콜 설계

전송 프로토콜보다 먼저 메시지 의미를 분류한다.

| 메시지 | 손실 허용 | 순서 요구 | 중복 처리 |
|---|---|---|---|
| 최신 위치 상태 | 가능 | 최신 번호만 중요 | 오래된 번호 폐기 |
| 플레이어 입력 | 제한적 | 틱 순서 필요 | 입력 번호로 제거 |
| 채팅 | 불가 | 채널 순서 필요 | 메시지 ID로 제거 |
| 구매 요청 | 불가 | 업무 규칙에 따름 | 멱등성 키 필요 |

헤더에는 필요한 정보만 명시적으로 둔다.

```text
protocol version
message type
payload length
connection or session identifier
sequence or command identifier
```

수신 측은 패킷을 신뢰하지 않는다. 타입, 길이, 정수 overflow, 문자열 인코딩, 배열 개수, 압축 해제 상한을 검증한다. 알 수 없는 버전과 메시지의 처리 정책도 정해야 한다.

직렬화는 ABI 구조체 복사가 아니다. 엔디언, 필드 크기, 선택 필드와 버전 호환성을 프로토콜로 정의한다. 부동소수점 값을 양자화하면 대역폭과 허용 오차를 함께 기록한다.

네트워크 스레드가 게임 상태를 직접 수정하면 패킷 도착 순서가 시뮬레이션 순서를 결정한다. 수신 데이터는 검증 후 명령 큐로 넘기고 명시적인 틱 경계에서 적용하는 편이 재현과 동기화에 유리하다.

## 6. 보안과 계측

암호화만으로 안전한 프로토콜이 되지 않는다. 기밀성, 무결성, 상대 인증, replay 방지를 구분해야 한다. 검증된 TLS, DTLS, QUIC 같은 프로토콜을 우선 사용하고 직접 만든 암호 조합은 피한다.

UDP 서버는 출발지 주소가 위조된 요청을 받을 수 있다. 인증 전 응답을 요청보다 크게 보내면 반사·증폭 공격에 악용될 수 있다. 쿠키나 주소 검증, rate limit, 응답 크기 제한이 필요하다.

네트워크 품질은 다음 분포로 측정한다.

```text
RTT와 단방향 지연 추정
jitter
loss와 burst length
reorder와 duplicate
송수신 bitrate
queue depth와 dropped message
재전송률과 유효 payload 비율
```

테스트에서는 지연, 지터, 손실, 중복, 재정렬, 대역폭 제한을 독립적으로 주입한다. 패킷 캡처와 애플리케이션 메시지 로그를 같은 connection·sequence ID로 연결하면 어느 계층에서 문제가 생겼는지 구분할 수 있다.

---

## 결론

네트워크는 지연과 손실이 있는 패킷 전달 시스템이다. UDP는 데이터그램 경계를 제공하지만 전달과 순서를 보장하지 않고, TCP는 순서 있는 신뢰성 바이트 스트림을 제공하지만 메시지 경계와 업무 처리를 보장하지 않는다.

프로토콜 선택은 “빠름 대 신뢰성”이 아니라 메시지별 손실, 순서, 중복, 시간과 보안 계약의 선택이다. 실제 지연 분포와 손실 패턴을 계측하고 장애를 주입해 복구 정책과 메모리 상한을 검증해야 한다.
