## 들어가며

자료구조는 데이터를 담는 문법이 아니라 연산과 메모리 배치의 계약이다. 어떤 연산을 얼마나 자주 수행하는지, 참조가 얼마나 오래 살아야 하는지, 데이터가 어떤 순서로 접근되는지에 따라 같은 객체 집합에도 다른 구조가 필요하다.

Big-O 표 하나만으로 자료구조를 선택하면 재할당, 캐시 지역성, 노드 할당, 참조 무효화 같은 실제 비용을 놓친다. 이 글은 게임 워크로드에서 자료구조를 선택하는 공통 기준을 다룬다.

## 1. 연산 계약부터 정의하기

자료구조 선택 전에 워크로드를 연산으로 적는다.

```text
상태: 최대 20,000개 엔티티
매 프레임: 살아 있는 엔티티 전체 순회
초당: 수백 개 생성과 제거
간헐적: ID로 단일 엔티티 조회
계약: 외부 핸들은 제거된 객체를 감지해야 함
```

이 요구를 “삽입이 빠른 컨테이너”라는 한 문장으로 줄이면 중요한 접근 패턴을 잃는다. 전체 순회가 지배적이면 연속 배치가 중요하고, ID 조회가 필요하면 별도 인덱스가 필요하며, 외부 참조가 오래 살면 세대가 있는 핸들이 필요하다.

복잡도 표에는 조건을 함께 적는다.

| 구조 | 위치 접근 | 값 탐색 | 끝 삽입 | 중간 삭제 | 주요 조건 |
|---|---:|---:|---:|---:|---|
| 동적 배열 | $O(1)$ | $O(n)$ | 상각 $O(1)$ | $O(n)$ | 재할당 시 참조 무효화 |
| 연결 리스트 | $O(n)$ | $O(n)$ | $O(1)$ | 노드를 알면 $O(1)$ | 노드별 할당과 포인터 추적 |
| 균형 트리 | 해당 없음 | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | 비교 순서 유지 |
| 해시 테이블 | 해당 없음 | 평균 $O(1)$ | 평균 $O(1)$ | 평균 $O(1)$ | 해시 분포와 재해시 |
| 이진 힙 | 루트 $O(1)$ | $O(n)$ | $O(\log n)$ | 루트 $O(\log n)$ | 한쪽 극값 조회 |

`O(1)`은 비용이 0이라는 뜻이 아니다. 해시 계산, 버킷 접근, 충돌 처리, 할당이 상수 안에 들어간다.

## 2. 연속 저장과 노드 저장

연속 배열은 인접한 원소를 같은 캐시 라인에 배치하기 쉽다. 게임의 갱신 루프처럼 모든 원소를 순서대로 읽는 작업에서 이 특성이 중요하다.

```cpp
for (Enemy& enemy : enemies) {
    enemy.Update(dt);
}
```

연결 리스트는 삭제 위치를 알고 있을 때 포인터 연결만 바꾸지만, 노드가 메모리에 흩어져 있으면 순회가 포인터 의존 사슬이 된다. 삭제가 $O(1)$이라는 이유만으로 순회 중심 워크로드에 리스트를 선택하면 전체 비용이 커질 수 있다.

동적 배열에서 순서를 보존할 필요가 없다면 swap-remove로 이동량을 줄일 수 있다.

```cpp
void RemoveUnordered(std::vector<Enemy>& values, std::size_t index) {
    values[index] = std::move(values.back());
    values.pop_back();
}
```

이 연산은 마지막 원소의 위치를 바꾸므로 인덱스와 포인터를 외부 식별자로 사용하면 안 된다. 역매핑이나 핸들 테이블도 함께 갱신해야 한다.

구조체 배열(AoS)과 필드별 배열(SoA)의 선택도 접근 패턴에 달려 있다.

```cpp
struct Particles {
    std::vector<Vec3> position;
    std::vector<Vec3> velocity;
    std::vector<float> lifetime;
};
```

위치와 속도만 대량으로 갱신한다면 SoA가 불필요한 필드 전송을 줄이고 SIMD에 유리할 수 있다. 한 객체의 모든 필드를 함께 사용하는 코드에서는 AoS가 단순하고 접근 횟수도 적을 수 있다.

## 3. 검색과 순서

해시 테이블은 키의 순서를 제공하지 않는다. 순회 순서가 시뮬레이션 결과에 영향을 주면 재해시나 플랫폼 차이가 결과를 바꿀 수 있다. 결정적인 순서가 계약이라면 키를 정렬하거나 순서가 정의된 구조를 사용해야 한다.

부동소수점 값을 트리 키로 사용할 때도 주의해야 한다. 같은 만료 시간을 가진 항목이 덮어써질 수 있고 `NaN`은 엄격 약순서 조건을 깨뜨릴 수 있다. 쿨다운 큐라면 시간과 안정적인 순번을 묶어 비교할 수 있다.

```cpp
struct Deadline {
    double time;
    std::uint64_t sequence;
    EntityId entity;
};
```

상위 $k$개만 필요하다면 전체 $n$개를 매번 정렬할 필요가 없다. 크기 $k$의 힙은 대략 $O(n\log k)$로 후보를 유지한다. 반대로 $n$이 작거나 결과 전체가 필요하면 단순 정렬이 더 명확하고 충분히 빠를 수 있다.

여러 인덱스를 함께 유지하면 조회는 빨라지지만 갱신 불변식이 늘어난다.

```text
dense array: 순회 순서와 실제 객체
id index: ID -> dense index
spatial index: cell -> entity handles
```

삽입, 이동, 제거가 세 구조에 모두 반영되어야 한다. 한 구조만 갱신된 순간을 다른 스레드나 시스템이 볼 수 있다면 동기화나 커밋 경계가 필요하다.

## 4. 수명과 참조 안정성

컨테이너가 보관하는 값의 수명과 외부 참조의 수명은 다르다. `std::vector` 재할당은 원소 주소를 바꾸고, erase는 뒤 원소를 이동한다. `reserve`는 지정한 용량을 넘지 않는 동안 재할당을 막지만 영구적인 주소 안정성을 보장하지 않는다. 정확한 재할당과 반복자 무효화 조건은 [C++ 표준 초안의 `vector.capacity`](https://eel.is/c++draft/vector.capacity)에 정의돼 있다.

안정적인 ID가 필요하면 슬롯과 밀집 배열을 분리할 수 있다.

```cpp
struct Handle {
    std::uint32_t slot;
    std::uint32_t generation;
};

struct Slot {
    std::uint32_t denseIndex;
    std::uint32_t generation;
    bool occupied;
};
```

객체를 제거할 때 세대를 증가시키면 재사용된 슬롯을 오래된 핸들이 가리키는 문제를 감지할 수 있다. 세대도 유한 정수이므로 래핑 정책과 핸들의 예상 수명을 정해야 한다.

포인터 대신 인덱스를 쓰면 직렬화와 이동이 쉬워질 수 있지만 인덱스만으로는 제거 후 재사용을 구분하지 못한다. 참조 방식은 주소 안정성, 검증 비용, 최대 객체 수, 직렬화 경계를 함께 고려한다.

## 5. 공간 질의

반경 안의 객체를 찾는 문제를 모든 객체에 대해 검사하면 질의당 $O(n)$이다. 공간을 셀이나 계층으로 나누면 실제 후보만 검사할 수 있지만, 성능은 분포와 갱신 빈도에 의존한다.

균일 격자에서 반경 $r$의 질의가 방문하는 셀 수는 셀 크기 $h$에 대략 다음처럼 의존한다.

$$
N_{\text{cells}} \propto
\left(\frac{2r}{h}+1\right)^d
$$

$h$가 너무 작으면 빈 셀을 많이 방문하고, 너무 크면 한 셀의 후보 수가 늘어난다. “셀 크기는 항상 검색 반경과 같아야 한다”는 보편 규칙은 없다. 객체 크기, 밀도, 질의 반경 분포, 차원을 측정해 선택한다.

음수 좌표를 셀로 변환할 때 0을 향한 정수 캐스팅을 사용하면 경계가 비대칭이 된다.

```cpp
int CellCoordinate(float value, float cellSize) {
    return static_cast<int>(std::floor(value / cellSize));
}
```

2차원 키는 두 정수 좌표를 구조체로 보관하고 해시하는 편이 명확하다. 임의의 부호 있는 좌표에 검증되지 않은 페어링 함수를 적용하면 충돌이나 오버플로를 숨기기 쉽다.

쿼드트리와 BVH 같은 계층 구조의 질의는 단순히 $O(\log n)$이라고 말할 수 없다. 겹치는 노드 수, 반환 결과 $k$, 트리 품질에 따라 비용이 달라진다. 모든 객체가 한 위치에 겹치거나 매우 큰 객체가 전체 공간을 덮는 퇴화 입력도 고려한다.

## 6. 선택과 검증

자료구조 선택은 다음 순서로 검증한다.

1. 입력 크기와 연산 빈도의 실제 범위를 기록한다.
2. 순서, 참조 안정성, 결정성 같은 정확성 계약을 적는다.
3. 후보 구조의 평균·최악·상각 비용을 구분한다.
4. 메모리 사용량에는 용량, 패딩, 버킷, 노드, 할당자 메타데이터를 포함한다.
5. 실제 접근 순서와 분포를 사용해 벤치마크한다.
6. 삽입·이동·삭제 뒤 모든 보조 인덱스의 불변식을 검사한다.

100개 원소에서 선형 탐색이 충분히 빠르다면 복잡한 인덱스는 갱신 버그와 메모리 비용만 늘릴 수 있다. 반대로 객체 수가 커지고 질의가 매 프레임 반복된다면 보조 인덱스의 유지 비용을 지불할 가치가 생긴다.

---

## 결론

자료구조는 시간 복잡도 하나가 아니라 연산 빈도, 데이터 배치, 수명과 참조 안정성의 결합이다. 연속 저장은 순회에 강하고, 해시와 트리는 조회 계약을 제공하며, 공간 인덱스는 후보 수를 줄이는 대신 갱신 불변식을 추가한다.

좋은 선택은 가장 복잡한 구조가 아니라 실제 워크로드의 지배 연산을 단순하게 만드는 구조다. 평균과 최악 비용, 메모리 배치, 무효화 규칙을 명시하고 실제 분포로 측정해야 한다.
