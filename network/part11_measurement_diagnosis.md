## 들어가며

네트워크 장애는 코드 한 줄에서 멈추지 않는다. 패킷은 로컬 링크, 라우터, 전송 계층, 보안 채널, 응용 서비스를 차례로 지나고 각 경계에서 다른 방식으로 사라지거나 늦어진다. 이 때문에 네트워크에서는 관찰 도구가 곧 디버거다. ping과 traceroute로 경로와 지연을 재고, Wireshark로 패킷을 해부하고, 그 위에 게임 서비스의 장애 진단 절차를 세운다.

도구 사용법 자체보다 *독법* 에 무게를 둔다. 관측값은 원인의 증명이 아니라 여러 가설을 줄이는 증거다. "3번 홉부터 RTT가 90ms 점프"는 물리 거리나 우회 경로를 의심하게 하고, "TLS ClientHello 후 침묵"은 방화벽·서버 과부하·경로 손실을 후보로 만든다. 좋은 진단은 이 후보들을 독립된 측정으로 하나씩 반증한다.

## 1. ping: 가장 작은 질문

`ping`은 ICMP Echo를 보내고 응답까지의 시간을 잰다 — "거기 있나, 얼마나 머나"의 최소 질문이다.

```text
$ ping -c 10 game.example.com
64 bytes from 198.51.100.7: icmp_seq=1 ttl=52 time=34.2 ms
64 bytes from 198.51.100.7: icmp_seq=2 ttl=52 time=33.8 ms
64 bytes from 198.51.100.7: icmp_seq=4 ttl=52 time=87.1 ms   ← 스파이크
...
--- statistics ---
10 packets transmitted, 9 received, 10% packet loss
rtt min/avg/max/mdev = 33.8/41.2/87.1/16.0 ms
```

독법:

- **min은 관측된 기준선의 근사다** — 표본 중 큐잉과 스케줄링 지연이 가장 작았던 왕복이다. 전파·전송 지연의 하한을 추정하는 데 유용하지만, 큐잉이 정말 0이었다는 뜻은 아니다. `현재 - min`도 큐잉량 그 자체가 아니라 큐잉·무선 재전송·서버 스케줄링 변동이 섞인 초과 지연이다.
- **mdev는 수신한 RTT 집합의 모집단 표준편차다** — iputils `ping`은 편차 제곱합을 수신 수 $N$으로 나눠 평균 주위의 산포를 요약한다. 통계적 모집단 전체를 관측했다는 뜻이 아니라 도구가 Bessel 보정($N-1$)을 쓰지 않는다는 뜻이다. 게임에서 말하는 지터와 관련은 있지만, 패킷 간 지연 변화처럼 별도 정의를 쓰는 프로토콜 지표와 동일하지 않다. min 34/avg 41/mdev 16이면 "기본 RTT보다 큰 변동이 섞인" 회선이라는 신호다.
- **icmp_seq의 구멍은 손실 의심 신호다** — seq 3이 없다. 응답 미관측일 뿐이고 echo 요청/응답 필터링이나 timeout이 섞일 수 있으므로, 손실로 단정하지 않고 연속인지(burst) 산발인지 패턴을 본다.
- **수신 TTL은 홉 수의 단서다** — 송신 호스트의 초기 TTL을 안다면 차이로 감소 횟수를 계산할 수 있다. 그러나 초기값은 운영체제·프로토콜 설정에 따라 다르고 경로도 바뀔 수 있으므로, `ttl=52`만 보고 정확히 12홉이라고 확정할 수는 없다.

한계도 명확하다 — ICMP는 라우터에서 후순위로 처리되거나 차단되므로, ping의 손실·지연이 게임 UDP의 그것과 같다는 보장이 없다. *게임의 진짜 RTT는 게임 프로토콜로 잰다* 는 원칙은 유지하고, ping은 빠른 정찰로 쓴다. 페이로드 크기를 바꿔 작은 패킷은 되는데 큰 패킷만 사라지는지 볼 수도 있다. 단 `ping -s`의 값은 IP·ICMP 헤더를 제외한 데이터 크기이고 도구별 단편화 금지 옵션도 다르므로, 한 숫자를 곧바로 애플리케이션 UDP 안전 크기로 옮기면 안 된다.

## 2. traceroute: 경로를 펼쳐 보기

traceroute는 TTL을 1, 2, 3…으로 늘려 보내며, 각 홉이 TTL 만료로 돌려주는 ICMP를 수집해 경로를 그린다.

```text
$ traceroute game.example.com
 1  192.168.0.1        1.2 ms    ← 집 공유기
 2  10.42.0.1          8.5 ms    ← ISP 접속망 (사설 주소 — CGNAT 흔적)
 3  isp-core.net      12.1 ms    ← ISP 코어
 4  ix-seoul.net      13.0 ms    ← 교환점
 5  * * *                        ← 응답 안 함 (ICMP 무시 라우터)
 6  pop-tokyo.cloud   46.8 ms    ← 국제 구간 진입 (+33ms 점프)
 7  game-lb           47.3 ms
```

독법:

- **RTT의 지속적인 계단을 찾는다** — 한 홉만 느리고 뒤 홉이 다시 빨라지면 그 라우터의 ICMP 응답 제한일 가능성이 크다. 어떤 지점부터 종점까지 RTT가 함께 증가하면 그 앞뒤 구간의 물리 거리·혼잡·경로 변경을 가설로 세울 수 있다. 예시의 서울→도쿄 표기와 +33ms는 국제 경로를 시사하지만, traceroute 하나만으로 해저 케이블이나 정확한 병목 링크를 증명하지는 못한다.
- **`* * *`는 곧 고장이 아니다** — 뒤 홉이 응답하면 해당 홉이 ICMP를 보내지 않았을 뿐 전달은 계속된 것이다. 마지막까지 응답이 없어도 목적지가 traceroute 프로브나 ICMP를 차단했을 수 있으므로, 실제 애플리케이션 포트 도달성으로 실패 여부를 별도 확인한다.
- **각 홉의 RTT는 그 홉까지의 왕복이다** — 단 돌아오는 경로는 다를 수 있고(비대칭 라우팅), 라우터의 ICMP 생성이 느려 실제보다 부풀 수 있다. 중간 홉의 단독 스파이크는 전달 경로의 병목으로 단정하지 않는다. 종점 수치도 ICMP 왕복의 관측일 뿐 게임 트래픽의 지연을 보장하지 않으므로, 뒤 홉까지 지속되는 변화와 애플리케이션 계측을 함께 본다.
- **주소의 사연을 읽어라** — 2번 홉의 사설 주소는 통신사 내부망이나 CGNAT의 흔적일 수 있다. 역방향 DNS 이름(ix-, pop- 등)에서는 경로의 지리를 추정할 수 있다. 단 사설 주소 하나만으로 NAT 동작 방식까지 확정할 수는 없다.

변종도 알아 둘 것 — UDP/TCP 기반 traceroute는 다른 프로브 포트와 프로토콜을 시험할 수 있지만, 중간 홉을 보여 주는 ICMP Time Exceeded 응답까지 우회하는 것은 아니다. `mtr`은 traceroute를 반복해 홉별 응답 누락과 RTT 통계를 만든다. 중간 홉의 응답 제한과 실제 전달 손실은 다를 수 있으므로 종점과 응용 계측으로 함께 확인한다. 그리고 경로는 방향마다 다르다는 것 — 서버에서 클라이언트 쪽으로의 역방향 traceroute(또는 RIPE Atlas 같은 외부 프로브)까지 봐야 왕복의 전모가 나온다.

## 3. Wireshark: 패킷의 해부학

Wireshark는 NIC를 지나는 패킷을 캡처해 계층별로 해부해 보여 준다 — 캡슐화·핸드셰이크·ack·윈도가 실물로 보이는 곳이다.

실무의 절반은 *필터* 다. 캡처 필터(BPF — 캡처량 자체를 줄임)와 표시 필터(잡은 것에서 골라 봄)를 구분하고, 게임 디버깅의 상비 필터를 손에 익힌다:

```text
udp.port == 7777                      # 게임 서버 포트
ip.addr == 198.51.100.7               # 특정 서버와의 대화만
tcp.analysis.retransmission           # TCP 재전송 관측 — 손실 의심(재정렬·지연·ACK 손실로도 발생)
tcp.analysis.zero_window              # 수신 윈도 0 — 흐름 제어 정체
tls.handshake.type == 1               # ClientHello — TLS 시작점 찾기
icmp.type == 3 && icmp.code == 4      # Fragmentation Needed — MTU 블랙홀 추적
icmpv6.type == 2                      # Packet Too Big — IPv6 경로 MTU 알림
```

게임 개발자에게 유용한 기능 셋. **Follow Stream** — TCP/UDP 대화 하나를 시간순으로 펼친다(API 호출 디버깅). **IO Graph** — 시간축 트래픽 그래프: 게임 트래픽의 주기성(틱), 버스트, 끊김이 그림으로 보인다. **전문가 정보(Expert Info)** — 재전송·중복 ack·윈도 문제를 자동 집계해 "이 캡처에서 수상한 것"의 목록을 준다.

자체 UDP 프로토콜은 Wireshark가 해석 못 하는 불투명 페이로드로 보인다 — 그래서 *Lua dissector* 를 한 번 짜 두면(헤더의 sequence·ack·채널을 필드로 등록) 팀 전체의 디버깅 해상도가 바뀐다. 암호화된 페이로드가 필요하면 개발 전용 세션 키 로깅처럼 통제된 진단 경로를 둔다(TLS의 `SSLKEYLOGFILE`도 같은 계열의 장치다). 키 로그에는 세션 평문을 복원할 능력이 있으므로 접근 제한·짧은 보존 기간·자동 삭제가 필요하며, 배포 빌드에 평문 모드나 무인증 우회 스위치를 남겨서는 안 된다.

## 4. 게임 트래픽 읽기: 캡처 분석 시나리오

캡처에서 핵심 개념들을 확인하는 분석 경로:

1. **접속 1초의 해부**: 캡처를 켜고 게임 로그인까지. DNS 질의/응답(시간은?) → TCP SYN/SYN-ACK/ACK → TLS ClientHello/ServerHello(몇 RTT?) → HTTP 요청. *첫 화면까지의 시간이 어느 단계에 쓰였는지* 가 한 화면에 나온다 — 접속 최적화의 출발점.
2. **게임플레이 트래픽의 리듬**: 매치 중 UDP를 IO Graph로. 틱 주기의 규칙적 맥박, 패킷 크기 분포(전투 시 커지는가), 상행/하행 비대칭을 확인한다. 이상적 그래프는 *지루할 만큼 규칙적* 이다 — 버스트와 공백이 보이면 송신 루프·페이싱의 버그 후보.
3. **나쁜 회선의 재현 관찰**: netem으로 손실 5%를 주입하고 같은 캡처를. 자체 프로토콜의 재전송이 설계대로 동작하는지(재전송 간격, ack 비트필드), TCP 쪽(API)에서는 재전송·버스트가 어떻게 보이는지 대조한다.
4. **MTU 블랙홀 사냥**: 단편화 금지 조건에서 페이로드를 점점 키우며 어느 크기부터 응답이 사라지는지, IPv4 `Fragmentation Needed`나 IPv6 `Packet Too Big`이 오는지 본다. 캡슐화·IP 버전·프로토콜 헤더를 포함한 실제 경로 패킷 크기를 함께 계산해야 한다. 약 1200바이트 UDP 페이로드를 택하는 것은 여러 경로와 터널에서 단편화를 피하려는 보수적 제품 정책이지 모든 인터넷 경로의 보장값은 아니다.

## 5. 대역폭·품질 측정의 함정

"인터넷 속도"를 둘러싼 흔한 혼동들을 정리해 둔다 — 플레이어 안내문과 진단 페이지를 만들 때 필요한 정확성이다.

- **속도 테스트는 게임 품질을 말해 주지 않는다**: speedtest류는 *처리량* (병목 링크 용량)을 잰다. 게임은 처리량을 거의 안 쓰고 지연·지터·손실에 산다 — 1Gbps 회선에 bufferbloat가 있으면 100Mbps 회선보다 게임이 나쁠 수 있다.
- **부하 중 지연(working latency)이 진짜 지표다**: 회선을 채운 상태에서의 지연 상승 — bufferbloat의 측정이다. 전용 테스트(예: "responsiveness" 측정)들이 등장하는 추세이고, 게임사의 진단 도구가 잴 가치가 있는 값이다: 유휴 RTT vs 다운로드 중 RTT의 차이.
- **무선 첫 홉을 분리해 측정하라**: 와이파이 경쟁·간섭·링크 계층 재전송은 지연 변동의 흔한 원인이지만 모든 회선의 주원인은 아니다. 같은 단말에서 유선과 무선을 비교하고 로컬 게이트웨이 RTT와 원격 RTT를 함께 보면 첫 홉의 기여를 분리할 수 있다. 게임 클라이언트 텔레메트리에는 가능한 범위에서 연결 종류(유선/와이파이/셀룰러)를 남긴다.
- **시간대를 통제하라**: 혼잡은 저녁에 온다. 핑 민원의 재현은 같은 시간대에 — 그리고 상시 텔레메트리가 시간대별 분포를 갖고 있으면 재현 자체가 필요 없어진다.

## 6. 계층별 장애 진단 절차

"접속이 안 돼요" 앞에서의 체계적 절차는 계층 모델을 진단 순서로 바꾸는 것이다:

```text
[링크]    로컬 연결이 사는가?           — 다른 사이트 접속, 와이파이/유선 전환
[네트워크] 목적지까지 경로가 사는가?      — ping/traceroute/mtr, 다른 지역에서도?
[전송]    포트가 열리는가?              — TCP: 연결 시도. UDP: 게임 핸드셰이크 응답
[보안]    TLS가 성립하는가?             — 인증서 만료·시계 오류·중간자(캡티브 포털)
[응용]    서비스가 옳게 답하는가?        — 상태 코드, 응답 내용, 특정 API만 실패?
```

방향을 가르는 질문들 — *전원인가 일부인가* (전원이면 서버·DNS·인증서, 일부면 지역·ISP·클라이언트 환경), *언제부터인가* (배포·인증서 만료·ISP 작업과의 시간 상관), *우리 쪽인가 경로인가* (서버 지표는 멀쩡한데 특정 지역 RTT만 상승 → BGP/ISP — 외부 프로브(RIPE Atlas)로 교차 확인).

게임 특유의 단골들을 표로:

| 증상 | 유력 원인 | 확인 |
|---|---|---|
| 로그인은 되는데 매치 입장 실패 | UDP 차단 (호텔·회사망) | TCP 443은 되고 UDP만 침묵 — TCP/relay 폴백 안내 |
| 특정 ISP만 높은 핑 | 피어링 부재·우회 경로 | 해당 ISP에서의 traceroute 수집 |
| 큰 패치만 실패 | MTU/단편화 또는 미들박스 | 작은 요청 성공 여부, 크기 경계 탐색 |
| 저녁에만 끊김 | 혼잡 (가정망 or ISP) | 시간대별 텔레메트리 분포 |
| 새 클라이언트 배포 후 접속 급감 | 인증서 고정·프로토콜 버전 실수 | 버전별 접속 성공률 분리 |

## 7. 게임 서비스의 상시 네트워크 관측

도구로 손에 익힌 것을 서비스의 상설 장비로 옮기는 것이 마지막 단계다.

- **클라이언트 텔레메트리**: 접속 퍼널 단계별 시간(DNS/TCP/TLS/첫 응답), 게임 RTT·지터·손실(게임 프로토콜 실측), 연결 종류, 직결/relay 여부 — 를 매치 종료 요약으로 수집한다. 분포(P50/P95/P99)로 보고, *지역×ISP×버전* 으로 쪼갤 수 있어야 진단이 된다.
- **합성 모니터링**: 주요 지역에 둔 프로브가 주기적으로 실제 접속 시나리오(DNS→TLS→로그인→매치 핸드셰이크)를 수행한다 — 유저 신고보다 먼저 아는 체계. 외부 측정망(RIPE Atlas 등)은 자사 인프라 바깥의 시야를 보탠다.
- **서버 쪽 카운터**: 포트별 수신 PPS·드롭(소켓 버퍼 오버플로), 핸드셰이크 성공률, 지역별 RTT 분포 — netcode 운영 계측과 같은 체계에 네트워크 계층 항목을 더하는 것.
- **진단의 셀프서비스화**: 위 절차(6절)를 클라이언트 안의 "네트워크 진단" 버튼으로 만든다 — MTU 탐색, 지역별 핑, UDP 도달성, 결과 코드 한 줄. CS가 받는 신고의 절반이 "진단 코드 첨부"로 바뀌는 투자다.

## 8. 관측값과 원인 사이

네트워크 측정은 대부분 간접 관측이다. RTT 상승을 보았다고 혼잡을 직접 본 것은 아니고, 패킷 손실을 보았다고 어느 링크의 큐가 넘쳤는지 아는 것도 아니다. 하나의 관측값은 여러 원인과 양립한다.

| 관측 | 가능한 원인 |
|---|---|
| RTT 상승 | 큐잉, 경로 변경, 서버 스케줄링 지연, 무선 재전송 |
| 손실 상승 | 혼잡 큐 드롭, 무선 오류, 소켓 버퍼 넘침, 방화벽 정책 |
| traceroute 중간 홉 손실 | 실제 전달 손실, ICMP 응답 제한, 제어 평면 후순위 처리 |
| TCP 재전송 | 경로 손실, 수신 측 지연, 패킷 재정렬·capture loss에 따른 오판 |
| TLS 핸드셰이크 정지 | 경로 손실, DPI 차단, 서버 과부하, 인증서 검증 대기 |

따라서 진단은 관측에서 결론으로 바로 뛰지 않고, 경쟁 가설을 세운 뒤 서로 다른 관측으로 줄여 가야 한다. 예를 들어 게임 RTT만 상승했을 때 다음 비교가 원인을 분리한다.

```text
게임 RTT 상승
  ├─ 같은 목적지의 ICMP RTT도 상승?  예 → 경로·링크 후보
  │                                  아니오 → 서버 처리·게임 프로토콜 후보
  ├─ 같은 ISP의 여러 사용자에게 동시 발생? 예 → 공유 경로·피어링 후보
  └─ 서버의 tick overrun과 시간 상관?       예 → 네트워크가 아닌 시뮬레이션 지연 후보
```

이 과정의 핵심은 *독립적인 증거* 다. 같은 장비의 같은 카운터를 다른 그래프로 그린 것은 독립 증거가 아니다. 클라이언트 RTT, 서버 소켓 드롭, 외부 프로브 경로, 서버 틱 지연처럼 관측 위치와 메커니즘이 다른 증거가 서로 같은 가설을 가리킬 때 결론의 신뢰도가 올라간다.

관측 도구 자체도 트래픽을 바꾼다. 패킷 캡처는 CPU와 디스크를 쓰고, 매우 높은 PPS에서는 캡처 프로그램이 패킷을 놓칠 수 있다. traceroute와 ping은 실제 게임 패킷과 다른 우선순위·경로를 탈 수 있다. 측정값에는 언제나 "무엇을, 어디에서, 어떤 부하로 측정했는가"가 붙어야 한다.

## 9. 분포와 시간축으로 측정하기

평균 RTT 하나로는 플레이 경험을 설명할 수 없다. 99번의 20ms와 한 번의 1초 정지는 평균 약 30ms지만, 플레이어는 명확한 끊김을 느낀다. 네트워크 품질은 분포와 시간 순서를 함께 봐야 한다.

- **백분위수**: P50은 평상시, P95·P99는 꼬리 지연을 보여 준다.
- **최솟값**: 전파·전송 지연에 가까운 기준선을 추정한다.
- **지터**: 도착 간격의 변동이다. 표준편차, 절대 편차, RTP식 지수 이동 추정 등 정의를 명시해야 한다.
- **버스트 손실**: 같은 손실률이라도 연속 손실은 복구하기 어렵다. 평균 손실률과 손실 run 길이를 함께 기록한다.
- **시간 창**: 1분 평균은 2초짜리 장애를 희석한다. 장애 탐지 창과 용량 추세 창은 달라야 한다.

상관된 손실을 단순한 독립 베르누이 손실로 가정하면 복구 설계를 낙관하게 된다. 독립 손실률이 $p$일 때 두 패킷 연속 손실 확률은 $p^2$이지만, 무선 음영이나 큐 버스트에서는 이전 패킷이 손실되었을 때 다음 패킷도 손실될 조건부 확률이 훨씬 높다. 네트워크 에뮬레이션과 테스트 데이터는 평균 손실률뿐 아니라 이 상관 구조를 보존해야 한다.

집계 차원도 신중해야 한다. 전 세계 평균은 특정 ISP·리전·빌드의 장애를 숨긴다. 반대로 계정 ID처럼 고유값이 많은 차원을 모두 지표 라벨로 넣으면 관측 시스템 자체가 무너진다. 운영 지표는 리전·ISP·플랫폼·빌드처럼 행동이 달라지는 낮은 카디널리티 차원으로 나누고, 개별 사건 조사는 샘플 로그와 트레이스로 연결한다.

좋은 기준선은 고정 임계값보다 문맥을 가진다. 저녁 시간대의 정상 RTT와 새벽의 정상 RTT가 다르고, 패치 직후 다운로드 트래픽은 평시와 다르다. 같은 요일·시간·리전의 과거 분포와 비교해야 "높다"가 장애 신호가 된다.

## 10. 시계와 상관관계

클라이언트와 서버 로그를 한 줄의 사건 흐름으로 합치려면 시계 문제가 먼저 해결되어야 한다. 벽시계는 NTP 보정, 사용자 설정, 절전 복귀 때문에 앞으로도 뒤로도 움직일 수 있다. 한 프로세스 안의 지속 시간은 단조 시계로 재고, 서로 다른 호스트의 사건을 연결할 때만 동기화된 벽시계를 쓴다.

```text
duration = monotonic_end - monotonic_start
timestamp = synchronized_wall_clock
```

단조 시계는 한 호스트 안의 순서를 안전하게 보존하지만 다른 호스트와 직접 비교할 수 없다. 벽시계는 호스트 간 대략적 상관관계를 주지만 오차 범위가 있다. 따라서 로그의 `12:00:00.100`과 `12:00:00.105`만 보고 5ms 차이의 인과 순서를 단정해서는 안 된다.

분산 요청에는 시간보다 강한 연결 고리가 필요하다. 접속 시도, 인증 요청, 매치 배정, 게임 연결에 하나의 correlation ID 또는 trace ID를 전달하면 서로 다른 시스템의 로그를 같은 사용자 흐름으로 묶을 수 있다. UDP 게임 패킷에는 연결 ID·sequence·tick을 기록하면 네트워크 순서와 시뮬레이션 순서를 함께 복원할 수 있다.

캡처 지점도 명시해야 한다. 클라이언트 NIC 앞의 패킷 시각, 서버 NIC 도착 시각, 응용이 소켓에서 읽은 시각, 시뮬레이션이 처리한 시각은 서로 다르다. 이 네 시각의 차이를 분리하면 경로 지연, 커널 큐 대기, 응용 스케줄링 지연을 구별할 수 있다.

## 11. 재현 가능한 진단 설계

좋은 진단 절차는 숙련자의 직감에만 의존하지 않는다. 같은 증상에 같은 질문을 던지고, 각 단계가 어떤 가설을 제거했는지 기록한다.

```text
1. 증상을 관측 가능한 문장으로 바꾼다.
   "렉이 있다" → "19:20~19:25, 서울 ISP A, UDP RTT P99가 40ms에서 240ms로 상승"

2. 변경하지 않은 기준군을 확보한다.
   다른 ISP, 다른 리전, 이전 빌드, TCP 기반 API 등

3. 한 번에 한 변수만 바꾼다.
   와이파이→유선, 직결→relay, 리전 A→B

4. 가설별 예측을 먼저 적는다.
   "ISP 피어링 문제라면 같은 ISP의 다른 사용자와 외부 프로브도 같은 홉에서 상승"

5. 결과와 반증된 가설을 남긴다.
```

네트워크 조건을 주입할 때도 재현 가능성이 필요하다. "손실 5%"만으로는 부족하다. 방향, 지연 분포, 재정렬, 중복, 버스트 길이, 대역폭, 큐 크기, 적용 시점과 지속 시간을 함께 기록해야 같은 실패를 다시 만들 수 있다. 특히 상행과 하행은 병목과 품질이 다르므로 독립적으로 제어해야 한다.

장애가 끝난 뒤에는 탐지부터 완화까지의 타임라인과 함께 *왜 기존 측정이 더 빨리 드러내지 못했는가* 를 묻는다. 새 대시보드를 하나 더 만드는 것이 목적이 아니라, 다음에는 더 적은 가설과 더 짧은 시간으로 원인을 좁히도록 관측 계약을 개선하는 것이 목적이다.

## 결론

ping은 min(관측 기준선)·mdev(RTT 산포)·seq 구멍(손실 의심)으로 읽고, traceroute는 뒤 홉까지 지속되는 RTT 계단과 주소·경로 단서로 읽고, 손실 위치는 mtr과 애플리케이션 계측을 함께 써서 좁힌다. Wireshark는 캡슐화·핸드셰이크·재전송을 실물로 보여 주는 해부대이고, 자체 프로토콜의 dissector는 팀의 시력을 바꾸는 투자다. 측정의 함정 — 처리량≠게임 품질, 유휴 지연≠부하 중 지연, 상관관계≠원인 — 을 피하고, 계층 순서의 진단 절차를 거쳐, 마지막에는 그 전부를 클라이언트 텔레메트리·합성 프로브·셀프 진단이라는 상설 관측으로 옮긴다.

도구의 목표는 명령어를 외우는 것이 아니라, 패킷의 여정 중 어느 계층에서 문제가 생겼는지를 관찰 가능한 증거로 좁히는 것이다.
