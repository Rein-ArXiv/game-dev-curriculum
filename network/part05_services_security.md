## 들어가며

서비스에 접속하는 과정은 IP 주소를 아는 것에서 끝나지 않는다. 이름을 주소와 서비스 위치로 해석하고, 상대의 신원을 검증하며, 요청과 응답의 의미를 합의해야 한다. DNS, 서비스 디스커버리, HTTP, TLS는 이 접속 경계를 담당한다.

이 글은 이름 해석과 캐시, 장애 전환, HTTP 의미론과 연결 재사용, TLS 인증과 키 합의를 하나의 접속 경로로 다룬다. 각 단계의 지연과 실패를 분리해야 로그인과 패치, 운영 API의 문제를 정확히 진단할 수 있다.

## 1. 질의 한 번의 여정

`login.mygame.com`을 처음 묻는 순간의 전체 경로:

```text
[게임 클라이언트] → [OS 스텁 리졸버 + 캐시]
  → [재귀 리졸버 (ISP 또는 8.8.8.8 등)]     ← 캐시 미스라고 가정
      → [루트 서버]      ".com 은 저쪽" (TLD 서버 주소)
      → [.com TLD 서버]  "mygame.com 은 저쪽" (권위 서버 주소)
      → [mygame.com 권위 서버] "login 은 203.0.113.10, TTL 60"
  ← 응답이 거슬러 올라오며 각 단계에 캐시됨
```

구조의 요점 셋. 첫째, *계층 위임* — 루트는 TLD만 알고, TLD는 도메인의 권위 서버만 안다. 분산 덕에 단일 장애점이 없고, 루트·TLD는 anycast로 전 세계에 복제되어 있다. 둘째, *재귀와 권위의 분리* — 클라이언트를 대신해 발품을 파는 재귀 리졸버(ISP·공용)와, 정답의 원본을 가진 권위 서버(게임사가 관리·위탁)는 다른 역할이다. 게임사가 통제하는 것은 권위 쪽 데이터뿐이고, 그 데이터가 *어떻게 퍼지는지* 는 수백만 개의 재귀 리졸버에 달려 있다. 셋째, *전송* — 전통적으로 UDP 53(작은 질의·응답에 최적)이고, 큰 응답은 TCP로 폴백한다. "UDP 위 요청-응답 + 캐시"라는 형태 자체가 작은 분산 시스템의 교본이다.

캐시가 다 차 있는 평시에는 이 여정이 OS 캐시 한 번으로 끝난다(µs). 콜드 캐시의 최악은 왕복 3~4번(수백 ms)이다 — "첫 접속만 느린" 현상의 흔한 성분이다.

## 2. 캐시와 TTL: DNS의 시간 상수

모든 DNS 레코드에는 TTL(초)이 붙는다 — "이 답을 몇 초 동안 캐시해도 좋다". TTL은 게임 인프라가 쥐는 가장 중요한 DNS 다이얼이다.

| TTL | 의미 | 용도 |
|---|---|---|
| 30~60초 | 변경이 1분 내 전파 | 장애 우회·트래픽 전환용 진입점 |
| 5~15분 | 균형 | 일반 서비스 엔드포인트 |
| 수 시간~1일 | 질의 부하 최소 | 거의 안 바뀌는 레코드 (NS, 정적 자산) |

트레이드오프는 명확하다 — 짧으면 변경이 빨리 퍼지지만 질의량(과 권위 서버 부하·비용)이 늘고 콜드 미스가 잦아진다. 길면 그 반대다. 운영의 고전 수법: 평시에는 5분 TTL로 두고, *계획된 전환(서버 이전·배포) 전에 미리 TTL을 60초로 낮춰* 둔다 — 전환 순간의 전파 지연을 산 다음, 안정되면 다시 올린다.

함정 — TTL은 *권고* 다. 일부 리졸버·미들박스는 TTL을 무시하고 더 오래 캐시하거나(특히 0에 가까운 값), OS·앱 캐시가 한 겹 더 있다. "DNS 바꿨는데 일부 유저가 옛 서버로 온다"는 현상은 정상이고, 따라서 *옛 주소도 전환 후 한동안 살아 있어야 한다*(우아한 이중 운영). DNS 전환은 스위치가 아니라 페이드다.

## 3. 레코드 타입 실전 독해

게임 인프라에서 실제로 다루는 레코드들:

- **A / AAAA**: 이름 → IPv4 / IPv6 주소. 이중 스택이면 둘 다 제공한다 — 클라이언트는 둘 다 받아 happy eyeballs로 빠른 쪽을 쓴다.
- **CNAME**: 이름 → 다른 이름. `login.mygame.com → lb-1234.cloudprovider.com` 같은 위탁의 표준 수단. 체인이 길면 질의가 한 번씩 늘어난다는 비용도 있다.
- **NS / SOA**: 위임과 존 메타데이터. 도메인 등록·이전 때만 만지지만, 잘못 만지면 도메인 전체가 죽는 곳.
- **SRV**: `_service._proto.domain → 우선순위, 가중치, 포트, 대상`. 이름에 *포트와 부하 분산 가중치까지* 담는 레코드 — 비표준 포트의 게임 서버 디스커버리에 쓸 수 있는 타입이지만, 웹 생태계 밖이라 지원이 들쭉날쭉해 게임은 대개 [자체 서비스 디스커버리 API](#6-dns-너머의-서비스-디스커버리)로 대신한다. 마인크래프트가 SRV를 쓰는 대표 사례.
- **TXT**: 임의 텍스트 — 도메인 소유 증명, SPF 등. 게임에서는 환경 설정 배포에 쓰는 변칙도 있으나 권장하기 어렵다.
- **CAA**: 해당 도메인의 인증서를 발급할 수 있는 CA를 제한해 TLS 인증서 운영을 보강.

## 4. 게임 인프라의 DNS 패턴

DNS가 게임 운영에서 일하는 표준 패턴들:

**진입점 추상화.** 클라이언트에 IP를 하드코딩하지 않고 이름을 박는다 — 서버 이전·확장·장애 우회가 클라이언트 패치 없이 가능해진다. 단 게임 *세션* 트래픽은 보통 이름이 아니라 매치메이커가 내려준 IP로 직결한다(세션 중 DNS 변동은 원하지 않으므로). 즉 DNS는 *첫 문* (로그인·API·패치)의 추상화다.

**지오 DNS와 리전 분배.** 권위 서버가 질의자(의 리졸버) 위치를 보고 가까운 리전의 주소를 응답한다 — `api.mygame.com`이 서울에서는 서울 LB로, 프랑크푸르트에서는 프랑크푸르트 LB로 풀린다. 한계도 명확하다: 권위 서버가 보는 것은 *재귀 리졸버의 주소* 이지 사용자가 아니다(EDNS Client Subnet이 보완하지만 보급이 불완전). 공용 리졸버(8.8.8.8) 사용자는 위치 추정이 어긋날 수 있다 — 그래서 정밀한 리전 선택은 DNS가 아니라 *클라이언트 실측 핑* 으로 하고, 지오 DNS는 첫 진입의 근사로만 쓴다.

**가중 응답과 점진 배포.** 같은 이름에 여러 주소를 가중치로 응답해 트래픽을 나눈다 — 새 인프라에 5%만 흘리는 카나리아, 또는 단순 부하 분산. 캐시 때문에 비율이 정확하지 않다는 한계를 안고 쓰는 거친 다이얼이다(정밀 분배는 LB의 일).

**헬스체크 연동 장애 우회.** DNS 제공자의 헬스체크가 리전 장애를 감지하면 해당 주소를 응답에서 뺀다 — TTL이 짧을수록 우회가 빠르다(2절의 60초 TTL이 이 시나리오의 보험료다).

## 5. 클라이언트 쪽 현실: 리졸버의 다양성

게임 클라이언트가 도는 환경의 DNS는 통제 밖 변수다.

- **느린/고장난 ISP 리졸버**: 첫 질의가 수 초 걸리거나 실패하는 환경이 실존한다. 게임 클라이언트의 표준 방어는 *타임아웃 + 재시도 + (가능하면) 복수 리졸버* 와, 성공한 주소의 *앱 레벨 캐시* (다음 실행 시 DNS 실패해도 마지막 주소로 시도)다.
- **하이재킹과 오염**: 일부 ISP는 NXDOMAIN을 광고 페이지로 바꾸고, 호텔·기내 네트워크의 캡티브 포털은 연결을 가로챌 수 있다. DNS 응답은 상대의 신원을 인증하지 않으므로 연결 뒤에도 hostname, 신뢰 사슬과 유효 기간을 포함한 TLS 인증서 검증이 필요하다.
- **암호화 DNS(DoH/DoT)**: OS·브라우저가 DNS를 HTTPS/TLS로 감싸는 흐름이 확산 중이다. 게임에 직접 영향은 적지만, "DNS 트래픽을 망에서 관찰·조작하기 어려워진다"는 변화는 알아 둘 것.
- **모바일 전환**: 와이파이↔셀룰러 전환 시 리졸버도 바뀐다 — 전환 직후의 DNS 재질의 실패가 "지하철에서 로그인 안 됨"의 한 성분이다.

## 6. DNS 너머의 서비스 디스커버리

DNS는 디스커버리의 *바깥쪽 절반* 이다 — 플레이어가 게임사의 문을 찾는 일. 안쪽 절반, 즉 *서비스가 서비스를 찾는 일* 과 *플레이어가 자기 게임 서버를 찾는 일* 은 다른 도구가 맡는다.

```text
플레이어 → (DNS) → API 게이트웨이 → (매치메이킹) → "네 서버는 203.0.113.77:7777, 토큰은 이것"
백엔드 서비스 → (서비스 레지스트리/디스커버리) → 다른 백엔드 서비스
```

게임 세션 할당이 DNS가 아닌 이유는 명확하다 — 세션 배정은 *상태 있는 1회성 결정* (이 매치, 이 서버, 이 토큰)이고, DNS는 *캐시되는 공용 답* 이기 때문이다. 매치메이커의 응답(서버 주소+포트+연결 토큰)이 게임의 진짜 서비스 디스커버리다.

백엔드 내부의 디스커버리(서비스 레지스트리, 쿠버네티스 내부 DNS, 사이드카)는 인프라 스택의 영역이지만, 원리는 같은 패턴의 반복이다 — 이름 → 살아 있는 인스턴스 목록 → 헬스체크로 갱신. DNS에서 배운 캐시·TTL·헬스체크의 사고법이 그대로 이식된다.

## 7. 실패 모드와 보안

게임 서비스에서 실제로 겪는 DNS 사고의 유형:

| 사고 | 원인 | 예방 |
|---|---|---|
| 출시 날 접속 불가 | 권위 서버가 질의 폭주에 다운 | 관리형 DNS(anycast 분산) 사용, 자체 운영 금지 |
| 전환 후 일부만 이전됨 | TTL 캐시 잔존(2절) | 사전 TTL 인하 + 구 인프라 이중 운영 |
| 도메인 전체 마비 | 등록 만료, NS 설정 실수, 등록기관 계정 탈취 | 자동 갱신·잠금·2FA — 도메인은 인프라의 단일 실패점 |
| 특정 지역만 실패 | 그 지역 리졸버의 캐시 오염·하이재킹 | TLS 검증 강제, 앱 레벨 주소 캐시 |
| 간헐적 첫 접속 지연 | 콜드 캐시 + 느린 리졸버 | 짧지 않은 TTL, 클라이언트 선질의(로딩 화면에서 미리) |

보안 측면 — DNS 응답은 전통적으로 인증되지 않는다(위조 응답을 먼저 꽂는 캐시 오염 공격이 가능). DNSSEC이 서명 검증을 제공하지만 보급이 부분적이다. 실무 결론은 단순하다: *DNS를 신뢰 경계로 삼지 말 것*. DNS는 "어디로 갈지의 힌트"이고, 도착한 곳이 진짜인지는 TLS 인증서 검증이 판정한다. 게임 클라이언트가 자체 인증서 고정(pinning)까지 갈지는 주제다.

운영 습관 하나로 마무리 — *DNS도 계측하라*. 클라이언트 텔레메트리에 "DNS 해석 시간"과 "해석 실패율"을 넣으면, 접속 퍼널의 첫 단계가 보인다. 이 지표 없이는 "로그인 느림" 민원에서 DNS 성분을 분리할 수 없다.



## 8. HTTP의 모델: 요청-응답과 무상태

HTTP는 단순한 계약이다 — 클라이언트가 메서드+경로+헤더+본문의 *요청* 을 보내면, 서버가 상태 코드+헤더+본문의 *응답* 을 돌려준다. 게임 개발자가 정확히 쓸 가치가 있는 부분:

- **메서드의 의미론**: GET은 읽기(부작용 없음·캐시 가능), POST는 생성/실행, PUT은 전체 교체(멱등), DELETE는 삭제(멱등). 이 의미론을 지키면 인프라(캐시·재시도·LB)가 공짜로 옳게 동작한다 — GET에 부작용을 넣는 순간 캐시와 선요청이 그 부작용을 임의 횟수 실행한다.
- **상태 코드의 분류**: 2xx 성공, 3xx 리다이렉트, 4xx는 대체로 요청 수정이 필요한 실패(400·401·403·404), 5xx는 서버·게이트웨이 실패다. 그러나 status class만으로 재시도 가능성을 결정하면 안 된다. `429 Too Many Requests`는 4xx여도 `Retry-After`와 idempotency를 지키며 백오프할 대표적인 일시 실패이고, 5xx도 비멱등 요청을 무조건 반복하면 중복 부작용이 생긴다. 재시도 정책은 [15절의 실패 분류](#15-데드라인과-재시도-실패를-증폭하지-않는-계약)를 따른다.
- **무상태**: 각 요청은 HTTP 계층에서 독립적으로 해석되고, 서버는 요청 사이의 대화를 프로토콜 수준에서 기억하지 않는다 — 기억이 필요하면 access token이나 세션 식별자를 요청마다 실어 나른다. 다만 이것은 *프로토콜*의 성질이지 애플리케이션이 자동으로 무상태가 된다는 뜻이 아니다. 로그인 session·작업 상태·멱등성 key를 공유 저장소(세션 스토어·DB·캐시)로 외부화하고 요청이 그 계약을 따를 때라야 백엔드는 아무 인스턴스로나 요청을 보낼 수 있다(수평 확장). 외부화하지 않은 backend 메모리 상태에 의존하면 "HTTP이므로 어느 서버라도 된다"는 보장이 없고, 그게 안 되는 게임 세션 서버와의 차이도 상태를 어디에 두는가에 있다.

## 9. HTTP/1.1: 연결 재사용과 그 한계

HTTP/1.0은 요청마다 TCP 연결을 새로 맺었다 — 요청 하나에 핸드셰이크 1 RTT + TLS까지 2~3 RTT의 선불이 붙는 낭비다. HTTP/1.1의 핵심 개선이 *지속 연결* (keep-alive): 한 연결로 요청-응답을 연달아 보낸다.

그러나 1.1의 연결은 *한 번에 한 요청* 이다 — 앞 요청의 응답이 끝나야 다음 요청이 나간다(파이프라이닝은 명세에 있었으나 HoL·중간장비 문제로 사장). 동시성이 필요하면 연결을 여러 개 연다 — 브라우저가 호스트당 6개 연결을 여는 관행이 그것이고, 게임 클라이언트의 HTTP 라이브러리도 내부적으로 연결 풀을 운영한다.

게임 관점의 교훈 — *연결 풀 설정이 성능 설정이다*. 풀이 작으면 요청이 풀 대기열에서 기다리고(서버는 멀쩡한데 클라이언트가 느림), 풀이 크면 서버 연결 수가 폭증한다. 로그인 직후처럼 요청이 몰리는 구간(프로필+인벤토리+친구+공지 동시 로드)의 지연은 종종 네트워크가 아니라 클라이언트 풀 고갈이다.

## 10. HTTP/2와 3: 다중화의 진화

**HTTP/2** 는 한 TCP 연결 안에 *스트림* 다중화를 넣었다 — 여러 요청-응답이 한 연결에서 동시에, 프레임 단위로 섞여 흐른다. 연결 수가 줄고, 헤더 압축(HPACK)으로 반복 헤더(토큰·UA)의 비용이 사라진다. 게임 API처럼 작은 요청이 많은 워크로드에 잘 맞는다.

남은 문제가 낯익다 — *TCP 계층의 HoL*. 스트림은 응용 계층에서 독립이지만 같은 TCP 스트림 위에 있으므로, 패킷 하나가 유실되면 모든 스트림이 함께 기다린다. 응용에서 분리해도 전송에서 다시 묶이는 구조적 한계다.

**HTTP/3** 가 그 답이다 — TCP를 버리고 UDP 기반 QUIC 위로 옮겼다. QUIC의 스트림은 전송 계층에서 독립이라 한 스트림의 손실이 다른 스트림을 막지 않고, TLS가 전송에 통합되어 핸드셰이크가 1 RTT(재방문 0-RTT)로 준다. 모바일에서 의미가 큰 *연결 마이그레이션* (IP가 바뀌어도 연결 유지)도 따라온다.

게임 백엔드 실무의 위치 — 클라이언트 HTTP 라이브러리와 서버/CDN이 지원하면 2는 기본값으로 쓰고, 3은 모바일 비중·핸드셰이크 비용이 아픈 서비스부터 켠다. 중요한 것은 버전 자체보다 *이 진화의 방향* 이다: 연결 선불 비용의 제거, HoL의 전송 계층 해소 — 게임 UDP 프로토콜이 처음부터 갖고 있던 성질들을 웹이 30년 걸려 따라온 것이고, 그 합류점이 QUIC이다.

## 11. TLS: 핸드셰이크의 비용과 절약

TLS는 전송 위에 기밀성(암호화)·무결성(MAC)·인증(인증서)을 얹는다. 게임 서비스에서 "HTTPS냐 HTTP냐"는 더 이상 선택이 아니므로(토큰이 흐르는 모든 채널은 TLS), 실무 질문은 *비용 관리* 다.

TLS 1.3 기준 핸드셰이크:

```text
ClientHello (지원 버전·암호군·키 교환 공개값)  ─▶
◀─ ServerHello (선택·키 교환 공개값) + 인증서 + Finished
[client Finished + 첫 request]                  ─▶   ← 송신 준비 완료(2 RTT)
◀─ 첫 response                                        ← 응답 수신(+서버 처리·왕복)
```

1.3은 핸드셰이크가 *1 RTT* 로 끝난다(1.2는 2 RTT였다). 여기에 TCP 핸드셰이크 1 RTT가 선행하므로, 새 연결이 애플리케이션 데이터를 *송신할 준비*를 갖추기까지 최소 2 RTT다 — RTT 100ms 모바일이면 본론 전에 200ms. 첫 *응답*을 받는 시점은 여기에 서버 처리 시간과 응답 왕복이 더해져 약 3 RTT + 서버 처리 시간이 될 수 있다. 절약 수단:

- **연결 재사용**([9절](#9-http11-연결-재사용과-그-한계)): 핸드셰이크를 amortize하는 가장 큰 수단. 게임 클라이언트는 API 호스트당 연결을 세션 내내 유지하는 것이 기본이다.
- **세션 재개**: 이전 핸드셰이크의 비밀을 재사용해 재연결 핸드셰이크를 줄인다. TLS 1.3의 0-RTT 재개는 재연결 시 첫 요청을 핸드셰이크와 *함께* 보낸다 — 단 0-RTT 데이터는 리플레이 공격에 노출될 수 있어 [멱등 요청](#13-게임-클라이언트의-http-실무)만 실어야 한다.
- **OCSP 스테이플링 등 검증 왕복 제거**: 인증서 유효성 확인을 위한 추가 왕복을 서버가 미리 첨부해 없앤다 — 서버 설정의 영역.

CPU 비용에 대한 결론 — 대칭 암호(AES-GCM·ChaCha20)는 하드웨어 가속과 적절한 record 크기에서 작은 비용이 측정되지만, 가속 유무·record 크기·복사·연결 재사용에 의존하므로 "사실상 무료"로 일반화할 수 없다. 공개키 연산이 지배적인 워크로드가 많아 핸드셰이크 횟수 최적화가 비용 최적화의 큰 축이라는 것, 그리고 "암호화 때문에 무조건 느리다"는 직관이 낡았다는 결론은 유지된다.

## 12. 인증서: 신뢰의 사슬과 고정

TLS의 암호화는 "지금 대화하는 상대가 진짜 그 서버"일 때만 의미가 있다. 그 인증을 맡는 것이 인증서다.

**사슬의 구조** — 서버 인증서는 중간 CA가 서명하고, 중간 CA는 루트 CA가 서명하며, 루트 CA들은 OS·플랫폼에 내장되어 있다. 클라이언트는 받은 사슬을 따라 서명을 검증하고, 도메인 이름 일치와 유효 기간을 확인한다. DNS가 공격자 주소를 돌려주더라도 이 검증을 통과하지 못하면 연결은 성립하지 않는다 — *신뢰의 최종 판정자는 DNS가 아니라 인증서 검증* 이다.

운영 현실 — 인증서는 만료된다. "인증서 만료로 전 서비스 접속 불가"는 업계의 고전 사고이고, 처방은 자동 갱신(ACME/Let's Encrypt 또는 클라우드 관리형)과 만료 30/7/1일 전 경보다. 수동 갱신 프로세스가 남아 있다면 그것이 시한폭탄이다.

**인증서 고정(pinning)** — 클라이언트가 "이 공개키(또는 CA)만 신뢰"를 하드코딩하는 기법. OS 신뢰 저장소에 악성 루트가 끼어드는 시나리오(기업 프록시, 멀웨어)까지 막아 주므로 중간자 공격과 트래픽 분석(치트 개발의 정찰 단계)을 어렵게 한다. 대가는 운영 경직성이다 — 고정된 키를 교체하려면 클라이언트 업데이트가 필요하므로, *백업 키를 함께 고정* 하고 교체 주기를 설계에 넣어야 한다. 고정 실수로 전 유저가 접속 불가가 되는 사고는 만료 사고보다 회복이 어렵다(서버 쪽에서 고칠 수 없으므로). 게임에서는 결제·인증 등 민감 API에 선별 적용하는 것이 균형점이다.

## 13. 게임 클라이언트의 HTTP 실무

게임 클라이언트의 HTTP 계층이 갖춰야 할 것들 — 라이브러리가 기본으로 안 해 주는 부분 중심으로:

- **타임아웃의 분리**: 연결 타임아웃(수 초)과 응답 타임아웃(요청 성격별 — 로그인 10초, 텔레메트리 30초)을 따로 잡는다. 무한 대기는 금지 — 로딩 화면이 영원히 도는 버그의 단골 원인.
- **재시도와 백오프**: 5xx·429·타임아웃·네트워크 오류만 재시도하고, 지수 백오프 + 지터(`base × 2^n + random`)를 쓴다. 지터 없는 동시 재시도는 장애 중인 서버에 *동기화된 재시도 폭풍* 을 만든다 — 서버 장애를 클라이언트가 연장하는 패턴.
- **멱등성 키**: "결제 요청을 보냈는데 타임아웃 — 재시도하면 이중 결제?"의 답. 클라이언트가 요청에 고유 키를 붙이고, 서버는 같은 키의 재요청에 같은 응답을 돌려준다(저장 후 중복 제거). 재시도를 *안전하게* 만드는 장치이고, 결제·보상 지급 API의 필수 설계다.
- **오프라인·전환 대응**: 모바일은 와이파이↔셀룰러 전환·백그라운드 복귀가 일상이다. 연결 풀의 죽은 연결 감지, 전환 후 재시도, 그리고 "네트워크 없음"의 빠른 감지(OS 신호 구독)가 체감 품질을 가른다.
- **요청 합치기**: 로그인 직후 N개 API를 따로 부르는 대신 부트스트랩 엔드포인트 하나로 합친다 — 왕복 수 자체를 줄이는 것이 모든 최적화 중 가장 크다(특히 고 RTT 환경).

## 14. 게임 백엔드의 HTTP 실무

서버 쪽에서 게임 특유의 패턴들:

- **로그인 폭풍 설계**: 게임 백엔드의 최악 부하는 평시가 아니라 *동시 사건* — 서버 오픈, 점검 해제, 인기 방송 — 의 로그인 폭주다. 처방의 층위: CDN·정적화(공지·버전 체크는 캐시에서), 대기열(큐 토큰으로 입장 속도 제어), 레이트 리밋(429 + Retry-After), 그리고 백엔드 자체의 수평 확장. 429를 받은 클라이언트가 [백오프 계약](#15-데드라인과-재시도-실패를-증폭하지-않는-계약)을 지키는 것까지 한 몸의 설계다.
- **캐시 계층의 활용**: [HTTP GET의 캐시 가능성](#8-http의-모델-요청-응답과-무상태)을 살려 버전 체크·카탈로그·공지를 CDN에 태우면 원 서버 부하를 크게 줄일 수 있다. `Cache-Control` 헤더가 그 다이얼이고, DNS의 TTL과 같은 사고법(신선도 vs 부하)이 적용된다.
- **폴링 vs 푸시**: "매치 잡혔나요?"를 1초마다 묻는 폴링은 단순하지만 부하와 지연이 모두 나쁘다. 롱 폴링(서버가 사건까지 응답 보류), WebSocket(연결 유지 + 양방향 메시지), SSE(서버→클라 단방향 스트림)가 대안이고, 게임은 로비·매치 통지·채팅에 WebSocket을 흔히 쓴다 — TCP 기반이므로 실시간 게임플레이용은 아니고(HoL), "수 초 내 통지"급 실시간성의 도구다.
- **역프록시와 LB 뒤의 진실**: 백엔드가 보는 연결은 LB와의 연결이고, 클라이언트 IP는 `X-Forwarded-For` 헤더로 온다(위조 가능 — 신뢰 경계의 LB가 덮어쓰도록 설정). 타임아웃·keep-alive 설정이 LB와 백엔드 양쪽에 있어 *더 짧은 쪽이 이긴다* 는 것도 단골 함정이다. 어느 한 계층이 먼저 유휴 연결을 닫으면 다른 계층은 다음 재사용 시점에야 죽은 연결을 발견한다.

## 15. 데드라인과 재시도: 실패를 증폭하지 않는 계약

분산 호출에서 가장 위험한 상태는 명시적 실패가 아니라 *결과를 모르는 상태* 다. 클라이언트가 구매 요청을 보낸 뒤 응답 전에 연결이 끊겼다면 서버가 요청을 실행하지 않았을 수도 있고, 실행하고 응답만 잃었을 수도 있다. 네트워크 오류만 보고 연산 결과를 추론할 수 없다.

이 모호함을 다루려면 세 계약을 분리해야 한다.

- **타임아웃(timeout)**: 한 번의 대기를 언제 포기할지 정한다.
- **데드라인(deadline)**: 사용자 작업 전체가 언제까지 가치가 있는지 정한다.
- **취소(cancellation)**: 호출자가 더는 결과를 원하지 않는다는 신호다. 이미 실행된 부작용을 되돌린다는 뜻은 아니다.

하위 호출마다 독립적인 10초 타임아웃을 주면 4단 호출 체인의 최악 지연은 40초가 된다. 대신 최상위 요청이 절대 시각의 데드라인을 만들고, 각 하위 호출은 *남은 예산* 을 전달받아야 한다.

```text
사용자 요청 예산: 2.0s
  게이트웨이 처리 후 남음: 1.8s
  인증 서비스 처리 후 남음: 1.2s
  인벤토리 저장소가 받을 수 있는 예산: 최대 1.2s
```

재시도는 성공률을 높이지만 장애 중에는 부하를 곱한다. 호출 경로가 세 층이고 각 층이 실패 시 최대 3번 시도하면, 최하위 서비스는 하나의 사용자 요청 때문에 최악의 경우 $3^3=27$번 호출된다. 그래서 재시도는 보통 *한 계층만 소유* 하고, 다음 조건을 갖춰야 한다.

1. 연산이 멱등하거나 멱등성 키로 중복 실행을 막는다.
2. 남은 데드라인 안에서만 시도한다.
3. 지수 백오프와 무작위 지터로 동시 재시도를 흩는다.
4. 최대 횟수뿐 아니라 전체 재시도 예산을 제한한다.
5. 과부하를 뜻하는 `429`·`503`과 영구 실패를 구분한다.

```text
delay_n = min(cap, base * 2^n) * random(0.5, 1.5)
```

지터가 없으면 같은 장애를 본 수십만 클라이언트가 같은 순간에 재시도하여 서버를 다시 쓰러뜨린다. 백오프는 서버를 기다려 주는 예의가 아니라, 닫힌 고리 제어에서 양의 피드백을 끊는 안정화 장치다.

느린 요청을 다른 복제본에도 보내 먼저 온 응답을 쓰는 *헤지 요청(hedged request)* 은 꼬리 지연을 줄일 수 있다. 그러나 이것도 부하를 늘리므로 읽기 전용 요청에만, 지연 분포의 높은 백분위수를 넘긴 소수 요청에만 적용해야 한다. 평균 지연을 줄이려고 모든 요청을 복제하면 평시 용량을 스스로 소모한다.

## 16. 서비스 전환: 발견과 준비 상태의 분리

DNS나 서비스 레지스트리에 주소가 있다는 사실은 그 인스턴스가 지금 요청을 받을 준비가 되었다는 뜻이 아니다. 서비스 전환은 다음 상태를 분리해야 안전하다.

```text
생성됨 → 시작 중 → 준비됨 → 트래픽 수신 → 드레이닝 → 종료됨
```

- **생존(liveness)** 은 프로세스가 교착되어 재시작이 필요한지를 묻는다.
- **준비(readiness)** 는 새 요청을 받아도 되는지를 묻는다.
- **드레이닝(draining)** 은 새 요청은 받지 않되 이미 받은 작업은 끝내는 상태다.

준비 검사는 얕아야 한다. 모든 의존 서비스를 연쇄 호출하는 준비 검사는 하위 서비스 하나의 장애를 전체 서비스의 준비 실패로 전파한다. 반대로 프로세스가 떠 있다는 사실만 확인하면 아직 캐시·모델·설정이 준비되지 않은 인스턴스로 트래픽이 들어간다. 준비 검사는 *이 인스턴스가 자신의 핵심 계약을 수행할 최소 조건* 만 확인해야 한다.

DNS 기반 전환에는 캐시 TTL이 있고, 로드 밸런서 기반 전환에는 연결 재사용과 헬스 체크 간격이 있다. 따라서 제거 순서는 중요하다.

1. 디스커버리와 로드 밸런서에서 새 요청 대상에서 제외한다.
2. 최소한 TTL·연결 유휴 시간·헬스 체크 전파 시간을 기다린다.
3. 진행 중 요청과 세션이 끝나도록 드레인한다.
4. 마지막으로 프로세스를 종료한다.

이 순서를 거꾸로 하면 이미 캐시된 주소와 살아 있는 연결이 종료된 인스턴스로 향한다. 장애 전환에서도 같은 문제가 생긴다. 헬스 체크가 실패한 주소를 너무 빨리 뺄수록 고장난 인스턴스를 피하지만, 일시적 네트워크 흔들림을 실제 장애로 오판해 멀쩡한 용량을 동시에 제거할 가능성이 커진다. 헬스 체크는 진실 판정기가 아니라 지연과 오탐률을 가진 실패 감지기다.

대규모 전환의 마지막 위험은 *동시 콜드 스타트* 다. 새 리전이나 새 버전으로 트래픽을 한 번에 옮기면 연결 풀, DNS 캐시, 애플리케이션 캐시, JIT, 데이터베이스 버퍼가 모두 차가운 상태에서 최대 부하를 받는다. 안전한 전환은 소량 트래픽으로 준비 상태를 검증하고, 지표를 보며 비율을 단계적으로 올린다.

## 17. TLS의 실제 보장 경계

TLS 연결이 성공했다는 말은 다음을 뜻한다.

1. 협상한 암호 스위트 아래에서 전송 중 내용의 기밀성과 무결성이 보호된다.
2. 클라이언트가 검증한 이름과 인증서의 신원이 일치한다.
3. 핸드셰이크가 인증한 상대와 세션 키를 공유한다.

반대로 TLS가 보장하지 않는 것도 분명하다. 서버 응용이 안전하다는 뜻이 아니고, 인증된 사용자가 권한을 가졌다는 뜻도 아니며, 서버나 클라이언트 메모리에서 데이터가 보호된다는 뜻도 아니다. 인증서가 올바르더라도 서버가 침해되었거나 잘못된 데이터를 반환할 수 있다.

신원 검증은 단순히 "인증서 서명이 맞다"가 아니다. 클라이언트는 최소한 다음을 확인해야 한다.

- 요청한 호스트 이름이 인증서의 Subject Alternative Name과 일치하는가
- 인증서 사슬이 신뢰 저장소의 루트까지 이어지는가
- 현재 시각이 유효 기간 안인가
- 허용한 서명 알고리즘과 키 강도를 쓰는가
- 서버가 보낸 중간 인증서와 협상한 프로토콜(ALPN)이 기대와 맞는가

TLS 1.3의 일반 키 교환은 서버의 장기 키(인증서 개인키)가 나중에 유출되어도 과거 트래픽 복호화로 이어지지 않는 *순방향 비밀성(forward secrecy)* 을 제공한다. 그러나 세션 재개의 0-RTT 데이터는 재전송될 수 있다. 공격자가 암호문을 해독하지 못해도 같은 0-RTT 요청을 다시 전달할 수 있으므로, 구매·보상 지급처럼 한 번만 실행되어야 하는 요청을 0-RTT에 실어서는 안 된다.

인증서 폐기는 또 다른 현실적 경계다. CRL과 OCSP가 존재하지만 클라이언트가 항상 실시간으로 폐기 상태를 확인하는 것은 아니며, 네트워크 실패 시 검증을 허용하는 구현도 있다. 따라서 장기 키 유출에 대한 방어는 폐기 기능 하나가 아니라 짧은 인증서 수명, 자동 교체, 키 접근 통제, 침해 탐지의 조합이다.

인증서 고정은 공개 CA 생태계의 위험을 줄이는 대신 복구 경로를 좁힌다. 고정 키 하나만 앱에 넣으면 그 키를 잃거나 교체해야 할 때 서버 변경만으로 복구할 수 없다. 최소 두 개의 독립 키를 준비하고, 실제 교체가 가능한지 주기적으로 검증하지 못한다면 고정은 방어가 아니라 새로운 단일 실패점이 된다.


---

## 결론

이름 해석, 서비스 선택, 보안 채널, 응용 요청은 서로 다른 계약이다. DNS가 성공해도 서비스가 준비되지 않았을 수 있고, TCP가 연결되어도 TLS 신원 검증이나 HTTP 의미가 실패할 수 있다.

접속 경로를 단계별로 측정하고 캐시 수명, 인증서와 키, 재시도 가능성을 명시하면 서비스 장애를 한 덩어리로 취급하지 않고 안전하게 복구할 수 있다.
