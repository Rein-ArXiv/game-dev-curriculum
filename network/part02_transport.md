## 들어가며

전송 계층은 IP가 전달한 데이터그램 위에 프로세스 식별, 신뢰성, 순서, 흐름 제어와 혼잡 제어 같은 종단 계약을 만든다. UDP와 TCP는 단순히 빠른 프로토콜과 느린 프로토콜이 아니라 서로 다른 실패와 순서 의미를 제공한다.

이 글은 소켓 API에서 출발해 UDP와 TCP의 상태 기계, 재전송 timer, 흐름·혼잡 윈도, head-of-line blocking까지를 연결한다. 선택 기준은 평균 처리량이 아니라 데이터의 수명, 지연 허용 범위, 손실과 중복을 응용이 어떻게 처리할 수 있는가다.

## 1. 전송 계층의 두 가지 일

IP는 패킷을 *호스트* 까지 나른다. 그 기계의 어느 프로그램에게 줄지는 모른다. 전송 계층의 첫 번째 일이 그 분배다 — *포트 번호* 로 프로세스를 식별하는 다중화/역다중화.

- UDP의 역다중화 키는 *비연결* UDP 소켓의 기본 모델에서 `(도착 IP, 도착 포트)` 2-튜플이다 — 어디서 왔든 같은 포트면 같은 소켓으로 간다. 게임 서버가 소켓 하나로 수천 클라이언트를 받는 구조의 근거다(누가 보냈는지는 `recvfrom`이 알려 주는 출발지 주소로 게임이 직접 구분한다). 다만 이는 프로토콜의 connectionless 성질을 소켓 API로 단순화한 모델이고, `connect()`를 호출한 connected UDP 소켓은 커널이 지정 peer를 기억해 그 peer만 수신하도록 거를 수 있다.
- TCP의 역다중화 키는 `(출발 IP, 출발 포트, 도착 IP, 도착 포트)` 4-튜플이다 — *연결마다* 소켓이 하나다. 같은 서버 포트 443이라도 클라이언트마다 별개의 소켓 객체로 갈라진다.

두 번째 일이 *서비스 수준의 선택* 이다. IP의 best-effort(손실·재정렬·중복 가능) 위에 무엇을 더할 것인가 — UDP는 거의 아무것도 더하지 않고, TCP는 신뢰·순서·흐름·혼잡 제어 전부를 더한다. 선택적 신뢰성과 채널별 순서가 필요했던 게임은 UDP 위에 직접 프로토콜을 지었고, 여러 독립 스트림을 제공하는 QUIC도 같은 문제의식에서 출발한다.

## 2. UDP: 다중화만 얹은 IP

UDP 헤더는 8바이트가 전부다 — 출발 포트, 도착 포트, 길이, 체크섬. 제공하는 것: 프로세스 다중화, 페이로드 손상 검출(체크섬). 제공하지 않는 것: 그 외 전부.

```text
UDP가 약속하지 않는 것
- 도착          (사라질 수 있다)
- 순서          (뒤바뀔 수 있다)
- 비중복        (두 번 올 수 있다)
- 흐름/혼잡 제어 (수신자·네트워크 사정을 모른 채 쏜다)
- 메시지 크기   (MTU 넘는 데이터그램은 IP가 단편화 — 위험은 보낸 자의 몫)
```

대신 UDP가 보존하는 결정적 성질이 있다 — *메시지 경계* 다. `sendto`로 보낸 한 번이 `recvfrom`의 한 번으로 나온다. 게임 패킷처럼 "한 덩어리가 한 의미"인 데이터에 자연스러운 모델이고, [TCP의 스트림](#3-tcp-신뢰-스트림이라는-약속)과 가장 크게 갈리는 지점이다.

또 하나 — 프로토콜 차원의 *연결 없음* 은 상태 없음에 가깝다는 뜻이다. 비연결 서버 소켓은 누가 말을 걸든 받고, 핸드셰이크도 연결 테이블도 커널에 없다. 그러나 이것은 프로토콜 성질이고, API의 `connect()`를 호출한 connected UDP 소켓은 handshake 없이도 peer 선택·필터링 상태를 커널에 둘 수 있다 — "커널에 연결 관련 상태가 전혀 없다"고 일반화할 수는 없다. 그래서 게임이 자기 연결 개념(주소+세션 상태)을 응용 계층에 직접 만든다. 자유의 이면은 책임이다: 커널이 연결을 모르므로 스푸핑·증폭 방어도 응용이 맡아야 한다.

## 3. TCP: 신뢰 스트림이라는 약속

TCP는 IP의 무보장 위에 "바이트 스트림이 빠짐없이, 순서대로, 중복 없이" 도착하는 추상을 짓는다. 시퀀스 번호, 누적 ack, 재전송 타이머, 수신 윈도, 혼잡 윈도가 이 약속을 함께 지킨다.

- **스트림, 메시지 아님**: TCP에는 메시지 경계가 없다. `send`를 세 번 해도 `recv` 한 번에 다 올 수 있고, 한 번 보낸 것이 두 번에 나뉘어 올 수 있다. TCP 위에 메시지를 얹으려면 길이 프리픽스 같은 프레이밍을 *응용이* 만들어야 한다 — TCP를 쓰는 게임 백엔드(채팅, 로비)의 단골 버그가 이 프레이밍 누락이다.
- **연결**: 통신 전에 3-way 핸드셰이크로 양쪽 커널에 상태를 만든다. 연결은 4-튜플로 식별되고, 종료에도 절차(FIN)가 있다.
- **전이중**: 한 연결로 양방향이 독립적으로 흐른다.
- **신뢰의 단위는 바이트**: "세그먼트 N이 도착했다"가 아니라 "바이트 오프셋 X까지 받았다"로 관리된다.

게임 관점에서 TCP의 약속은 *너무 강하다* — 그 강함이 Head-of-Line Blocking(유실분이 채워질 때까지 이후 데이터 보류)으로 나타나고, 실시간 상태 동기화에 부적합한 이유가 된다. 하지만 게임 *서비스* 의 대부분 — 로그인, 상점, 매치메이킹 API, 패치 다운로드 — 은 정확성이 전부고 수백 ms 지연이 무해하므로 TCP(위의 HTTPS)가 옳은 선택이다. "게임은 UDP"가 아니라 "게임플레이 동기화는 UDP, 나머지는 TCP"가 정확한 문장이다.

## 4. 의미론 대조: 게임 데이터로 읽기

| 성질 | TCP | UDP | 게임에서의 판단 |
|---|---|---|---|
| 경계 | 스트림 (프레이밍 직접) | 메시지 보존 | 패킷 단위 사고엔 UDP가 자연 |
| 도착 보장 | 연결이 유지·복구되는 동안 전부 | 없음 | 상태는 "없음"이 오히려 적합 (낡으면 버림) |
| 순서 | 전체 순서 강제 | 없음 | 전체 순서가 곧 HoL — 채널별 선택이 필요 |
| 지연 특성 | 손실 시 스파이크 (RTO·재전송) | 손실=구멍, 지터는 큐·pacing에 따라 변함(예시 분포) | 지연 민감 게임은 스파이크가 더 아픔 |
| 혼잡 제어 | 내장 (처리량 지향) | 없음 (직접 구현) | 지연 지향 제어를 직접 짓는 자유/부담 |
| 연결 상태 | 커널이 관리 | 없음 (직접 구현) | 토큰·타임아웃을 직접 |
| 방화벽/NAT 통과 | 잘 통과 | 가끔 막힘 | UDP 차단 환경용 TCP 폴백을 두기도 |
| 전형적 용도 | 로그인, API, 다운로드, 채팅 | 게임플레이 상태, 보이스, 핑 측정 | |

표의 마지막 행이 실무 결론이다. 그리고 중간의 "지연 특성" 행이 가장 오해받는 지점이라 한 번 더 — 정상 연결·동일 무손실 경로·유사한 전송 정책이라는 조건에서 TCP의 평상시(P50) 지연은 UDP와 비슷하다(같은 IP 위에서 같은 경로를 쓴다). 어느 한쪽이 항상 같다는 보장이 아니라 예시 분포이며, 차이는 *분포의 꼬리*에 있다: 손실이 났을 때 TCP는 복구가 끝날 때까지 수백 ms를 멈추고, UDP는 그냥 그 패킷만 없다. 게임은 평균이 아니라 P99로 체감되므로, 꼬리가 두꺼운 TCP가 지는 것이다.

## 5. 소켓 API의 동작 모델

소켓 API에서 게임 서버가 실제로 고민하는 것은 함수 이름이 아니라 *대기 모델* 이다 — 데이터가 없을 때 무엇이 일어나는가.

- **블로킹**: `recvfrom`이 데이터가 올 때까지 스레드를 재운다. 단순하지만, 게임 서버 루프는 네트워크 말고도 할 일(틱 시뮬레이션)이 있으므로 메인 루프에서 쓸 수 없다.
- **논블로킹**: 데이터가 없으면 즉시 `EWOULDBLOCK`으로 돌아온다. 틱 루프 앞머리에서 "지금 도착해 있는 것 전부"를 비우는 게임 서버의 표준 모델이다(6절).
- **readiness 통지 (select/poll/epoll/kqueue)**: "어느 소켓이 읽을 준비가 됐는지"를 커널이 알려 준다. 소켓이 많은 TCP 서버(API·채팅)의 표준이고, UDP 게임 서버는 소켓이 하나라 필요가 덜하다 — 대신 *틱까지 남은 시간만큼만 대기* 하는 타임아웃 용도로 쓴다.
- **완료 통지 (io_uring/IOCP)**: 읽기 작업과 버퍼를 미리 제출하고 완료를 회수하는 모델이다. 제출·완료를 묶어 호출 횟수를 줄이고 다수의 in-flight 작업을 표현할 수 있지만, payload 복사가 자동으로 사라지는 것은 아니다. 단순 논블로킹 루프, batch API, 완료 모델의 손익분기점은 PPS 하나로 정할 수 없으며 패킷 크기, 연결 수, 틱 예산, 플랫폼 호출 비용을 함께 측정해야 한다.

어느 모델이든 변하지 않는 그림 — 커널 소켓 버퍼가 게임과 네트워크 사이의 완충이다. NIC가 받은 패킷은 소켓 수신 버퍼에 쌓이고, 게임이 안 꺼내면 *버퍼가 넘쳐 조용히 버려진다*. 게임 프레임이 길어지는 순간(로딩, GC) 수신 버퍼가 그 시간을 버텨 줘야 하므로, 버퍼 크기는 기본값에 맡기지 말고 직접 잡는다(7절).

## 6. 게임 서버 UDP 루프의 기본형

부품을 모으면 게임 서버 네트워크 루프의 뼈대가 된다.

```cpp
// 초기화: 논블로킹 UDP 소켓 + 수신 버퍼 확장
SocketHandle CreateGameSocket(uint16_t port) {
    SocketHandle s = socket(AF_INET6, SOCK_DGRAM, 0);   // v6 소켓으로 v4도 수용(7절)
    SetNonBlocking(s);
    int rcvbuf = 1 << 20;                                // 1MB — 프레임 스파이크 완충
    setsockopt(s, SOL_SOCKET, SO_RCVBUF, &rcvbuf, sizeof rcvbuf);
    Bind(s, port);
    return s;
}

// 틱 앞머리: 도착해 있는 패킷 전부를 비운다
void PumpNetwork(SocketHandle s, double now) {
    uint8_t buf[2048];                                   // MTU 여유 — 더 크면 어차피 단편화 의심
    for (;;) {
        Address from;
        int n = RecvFrom(s, buf, sizeof buf, &from);
        if (n < 0) break;                                // EWOULDBLOCK — 다 비웠다(Windows는 ICMP Port Unreachable을 WSAECONNRESET으로 돌려주므로 SIO_UDP_CONNRESET을 꺼 두지 않으면 여기서 남은 패킷을 놓친다)
        if (n < kMinPacketSize) continue;                // 쓰레기 선별: 크기
        OnPacket(from, buf, n, now);                     // protocolId·연결 조회·복호화·파싱
    }
}
```

설계 포인트 셋. 첫째, *do-while 비우기* — 한 틱에 한 패킷이 아니라 도착분 전부를 처리해야 큐가 안 쌓인다(단, 수신 폭주 방어로 틱당 처리 상한을 두고 넘으면 카운터를 올린다). 둘째, *수신 즉시 처리 vs 큐잉* — 파싱까지만 하고 게임 적용은 틱 시뮬레이션 단계에서 하는 2단 구조가 보통이다(입력은 입력 버퍼로, 상태 요청은 큐로). 수신 콜백이 게임 상태를 직접 만지기 시작하면 재진입·순서 문제가 스며든다. 셋째, *송신도 같은 소켓으로* — UDP는 연결이 없으므로 `sendto(from 주소)`로 답한다. 송신 버퍼(SO_SNDBUF)가 가득 차면 `EWOULDBLOCK`이 나는데, 게임 패킷은 그 순간 *버리는 것* 이 옳다(다음 틱에 더 새 상태가 나간다) — 여기서 블로킹하면 틱이 멈춘다.

## 7. 소켓 옵션과 실무 함정

게임 서버가 실제로 만지는 옵션과 부딪히는 함정들:

- **SO_RCVBUF / SO_SNDBUF**: 6절의 완충. OS 기본값(수십~수백 KB)은 PPS 높은 서버에 작다. Linux는 `sysctl net.core.rmem_max`가 상한이므로 함께 올려야 실제로 커진다.
- **이중 스택**: IPv6 소켓 하나로 v4까지 받는 구성(`IPV6_V6ONLY` 끄기)이 운영을 단순화한다. 모바일 망은 v6 단독(NAT64)인 경우가 많아 v6 지원은 선택이 아니다.
- **TCP_NODELAY** (TCP 한정): Nagle 알고리즘이 아직 확인되지 않은 작은 세그먼트가 있을 때 추가 작은 쓰기를 보류하는 동작을 끈다. delayed ACK 정책과 맞물리면 대화형 트래픽에 눈에 띄는 지연을 만들 수 있지만, 지연값은 OS와 경로마다 다르고 모든 작은 TCP 쓰기의 원인은 아니다. RPC처럼 작은 요청의 지연이 중요하면 측정 후 켜고, 패킷 수 증가를 막기 위해 애플리케이션 메시지는 의도적으로 한 번에 직렬화한다.
- **DF와 단편화**: IPv4는 DF가 꺼져 있으면 경로에서 단편화될 수 있고, IPv6 중간 라우터는 단편화하지 않는다. 송신자가 경로 MTU 안으로 패킷화하고 PMTUD/PLPMTUD 결과에 따라 크기를 조절하는 것이 기본이다. IPv4 DF 또는 플랫폼의 동등한 옵션으로 너무 큰 데이터그램을 실패시켜 버그를 드러낼 수도 있다.
- **체크섬을 믿지 말 것**: UDP 체크섬은 16비트라 우연 통과가 있고, NAT가 헤더를 고치며 재계산하므로 종단 무결성 보장이 아니다 — 게임 계층의 암호화 MAC(AEAD)이 진짜 무결성 검사다.
- **포트 고갈과 임시 포트**: 클라이언트 쪽 출발 포트는 OS가 임시로 할당한다. NAT·방화벽·로드밸런서의 UDP 유휴 타임아웃은 장비와 정책에 따라 달라진다. 연결 유지가 필요하면 관측한 경로 수명보다 짧은 keepalive를 쓰되, 모바일 무선 깨우기와 배터리·트래픽 비용도 함께 측정한다.
- **localhost의 한계**: 루프백은 외부 네트워크 손실·지연·MTU 변동이 없어 WAN 특성을 대신하지 못한다(MTU 65KB). 그렇다고 localhost에서 손실이 항상 0인 것은 아니다 — 수신 큐를 소비 속도보다 빠르게 채우면 버퍼 포화로 패킷이 버려지고 스케줄링 지연도 생긴다. **localhost만으로 WAN 특성을 검증할 수 없고**, "내 컴퓨터에선 되는데"의 네트워크판인 이유이며 조건 주입 테스트가 필수인 이유다.



## 8. 연결: 3-way 핸드셰이크와 상태 기계

TCP 통신은 연결 수립으로 시작한다.

```text
클라이언트                         서버
   │ ── SYN (seq=x) ──────────────▶ │   "연결하자, 내 시작 번호는 x"
   │ ◀─ SYN+ACK (seq=y, ack=x+1) ── │   "좋다, 내 번호는 y, x 잘 받았다"
   │ ── ACK (ack=y+1) ────────────▶ │   "y도 잘 받았다" + 데이터 시작 가능
```

핸드셰이크가 하는 일은 둘이다 — 양쪽의 초기 시퀀스 번호 교환(이후 모든 바이트가 이 번호 위에서 셈해진다), 그리고 양쪽 커널에 연결 상태 블록 생성. 비용은 데이터 전송 전 1 RTT다 — 짧은 요청(API 호출)에서는 이 1 RTT가 전체 시간의 절반일 수 있고, TLS 핸드셰이크까지 더하면 2~3 RTT가 *본론 시작 전에* 나간다. HTTP keep-alive(연결 재사용)·세션 재개·QUIC 0-RTT가 전부 이 선불 비용과의 싸움이다.

서버 쪽에는 SYN을 받고 ACK를 기다리는 *반열림 상태* 가 생기는데, 위조된 SYN을 대량으로 보내 이 상태로 메모리를 채우는 것이 SYN flood 공격이다. 방어인 SYN cookie — 상태를 저장하는 대신 검증 가능한 값을 시퀀스 번호에 인코딩해 보내고, ACK가 돌아오면 재계산으로 확인 — 는 게임 UDP 프로토콜의 무상태 challenge와 정확히 같은 발상이다. *인증 전에는 상태를 만들지 않는다* 는 원칙의 TCP판.

종료에도 절차가 있다(FIN 교환, TIME_WAIT). 게임 백엔드 운영에서 TIME_WAIT 상태가 수만 개 쌓이는 현상(짧은 연결의 대량 반복)은 포트 고갈로 이어질 수 있다 — 연결 재사용(keep-alive, 커넥션 풀)이 처방이다.

## 9. 신뢰 전송: 시퀀스, ack, 재전송

TCP 신뢰성의 뼈대는 게임 프로토콜과 같은 재료다 — 번호 붙이기, 수신 확인, 시간 초과 재전송. 다른 것은 *단위와 정책* 이다.

- **바이트 시퀀스**: TCP의 시퀀스 번호는 패킷이 아니라 *바이트 오프셋* 이다. "세그먼트 3개를 받았다"가 아니라 "바이트 4096까지 연속으로 받았다"로 상태가 관리된다.
- **누적 ack**: ack 번호는 "이 바이트 *직전까지* 전부 받았다"는 뜻이다. 중간에 구멍이 나면 ack는 구멍 앞에서 멈춘다 — 구멍 *뒤에* 도착한 데이터는 ack에 반영되지 않는다(SACK 옵션이 이를 보완해 "뒤쪽 어디어디도 받았다"를 따로 알린다 — 게임 프로토콜의 ack bitfield와 같은 역할이다).
- **재전송의 두 경로**: ① 타임아웃(RTO) — 보수적인 최후 수단. ② 빠른 재전송 — 같은 ack가 3번 중복되면(수신자가 구멍 뒤 데이터를 받을 때마다 같은 ack를 반복) 타임아웃을 기다리지 않고 즉시 재전송한다.

게임이 가져간 것: 번호·ack·타이머의 구조 전체, SACK의 비트필드화. 게임이 버린 것: *바이트 연속성* — 게임은 메시지 단위로 선택적 신뢰성을 주므로, "구멍 앞에서 모든 것이 멈추는" 누적 의미론을 버리고 메시지별 독립 재전송으로 바꿨다. 이 한 가지 차이가 [HoL](#14-head-of-line-blocking의-해부) 유무를 가른다.

## 10. RTT 추정과 RTO

재전송 타이머를 몇 ms로 잡을 것인가 — 너무 짧으면 멀쩡한 패킷을 중복 전송하고, 너무 길면 복구가 늦다. TCP의 답(Jacobson/Karels, RFC 6298)은 평활 평균과 분산의 동시 추정이다.

```text
RTTVAR ← (1-β)·RTTVAR + β·|SRTT_old-표본| (β = 1/4)
SRTT   ← (1-α)·SRTT + α·표본               (α = 1/8)
RTO    ← SRTT + max(clockGranularity, 4·RTTVAR)
```

RFC 6298의 `RTTVAR`는 표준편차가 아니라 절대 오차의 지수 평활값이므로, “정규분포의 4시그마 바깥” 같은 통계적 보장으로 읽으면 안 된다. 위 순서처럼 편차를 갱신할 때는 갱신 전 `SRTT`를 쓴다. RFC는 계산된 RTO가 1초보다 작으면 1초로 올릴 것을 규정하지만 실제 TCP 구현은 더 작은 최소값을 쓰기도 하므로, 프로토콜 명세와 운영체제 구현을 구분해야 한다. 재전송된 세그먼트의 모호한 ACK에서는 RTT 표본을 취하지 않는 Karn의 원칙과, timeout마다 RTO를 지수 backoff하는 규칙도 함께 작동한다. TCP timestamp와 구현의 ACK 판정은 모호성을 더 줄일 수 있다.

게임 신뢰 채널도 평활 RTT와 변동치를 이용해 재전송 시간을 잡을 수 있지만 TCP 공식을 숫자까지 그대로 복사할 이유는 없다. 50ms 같은 하한은 LAN처럼 RTT가 짧은 경로에서 복구를 늦추고, 500ms 같은 상한은 RTT가 더 큰 경로에서 즉시 중복 전송을 만든다. 메시지 기한, ACK 빈도, packet loss·reordering 분포, 재전송 byte budget으로 최소·최대와 backoff를 정하고 시뮬레이션에서 spurious retransmission 비율을 측정한다.

## 11. 흐름 제어: 수신 윈도

흐름 제어는 *수신자* 보호 장치다 — 수신 버퍼가 넘치지 않도록, 수신자가 "지금 내 버퍼 여유가 N바이트"라고 모든 ack에 실어 보내고(수신 윈도 광고), 송신자는 그 이상을 in-flight로 두지 않는다.

윈도가 처리량의 상한을 만든다는 것이 핵심 산수다 — 송신자는 ack가 돌아와야 윈도가 다시 열리므로, 처리량 ≤ 윈도 / RTT. 64KB 윈도, RTT 100ms면 최대 5.2Mbps — 회선이 1Gbps여도 그렇다. 대륙 간 대용량 전송(패치 배포)이 "회선은 넓은데 느린" 이유의 단골이 이 *대역폭-지연 곱(BDP)* 부족이고, 현대 OS의 윈도 스케일링·자동 버퍼 튜닝이 이를 푼다. 게임 백엔드에서 대륙 간 복제·백업이 느릴 때 가장 먼저 볼 것이 이 윈도 산수다.

게임의 최신 상태 채널은 오래된 패킷을 버릴 수 있어 TCP식 byte-stream receive window가 필요하지 않을 수 있다. 그러나 신뢰 채널·에셋 전송·재조립 버퍼에는 수신 측 메모리와 처리량 한계가 분명히 존재한다. 처리하지 못한 reliable message 수, reassembly bytes, command queue depth에 상한을 두고 광고·backpressure·연결 종료 정책을 정해야 한다. 흐름 제어와 혼잡 제어는 각각 수신자와 경로를 보호하는 서로 다른 계약이다.

## 12. 혼잡 제어: 네트워크에 대한 예의

흐름 제어가 수신자를 보호한다면, 혼잡 제어는 *네트워크* 를 보호한다. 네트워크는 "여유가 N"이라고 광고해 주지 않으므로, 송신자가 *추론* 해야 한다 — 손실·지연을 신호로 자기 송신 속도(혼잡 윈도 cwnd)를 조절한다.

고전 TCP Reno 계열의 개념적 정책:

- **슬로 스타트**: ACK마다 cwnd를 늘려 이상적인 ACK 흐름에서는 RTT마다 대략 두 배 — 지수적으로 회선 용량을 탐색한다. 초기 cwnd는 역사적으로 1 MSS였지만 현대 표준과 구현은 여러 세그먼트에서 시작할 수 있다.
- **혼잡 회피**: 임계 이후 RTT마다 +1 MSS — 선형 증가로 조심스럽게 더듬는다.
- **손실 반응**: 중복 ACK로 감지한 손실과 재전송 timeout은 서로 다른 방식으로 cwnd와 slow-start threshold를 줄인다. 정확한 값은 Reno/NewReno와 RFC·구현 버전에 달려 있다.

이 AIMD(가산 증가·승산 감소) 패턴의 톱니 그래프가 고전 손실 기반 TCP의 서명이다. 동일한 RTT·동일한 파라미터·공통 이진 혼잡 신호라는 이상화 모델에서는 흐름들이 균등 분할로 수렴한다. 실제 인터넷에서는 RTT, 시작 시각, ACK 정책, 여러 병목, AQM과 알고리즘이 달라 “TCP-friendly”와 공정성 자체가 별도 측정 대상이다.

게임이 버린 것: 목표 자체 — Reno류는 손실이 날 때까지 큐를 채우는, 즉 *지연을 희생해 처리량을 얻는* 정책이다. 게임이 가져간 것: 의무 — UDP에는 혼잡 제어가 없으므로 게임이 직접 구현해야 하며(RFC 8085가 이를 UDP 응용의 책무로 명시한다), 그 정책은 목표를 뒤집어 지연을 우선한다. "혼잡 제어를 안 하는 것"은 선택지가 아니다 — 폭주하는 UDP는 같은 병목의 모든 TCP를 밀어내는 불공정 트래픽이 되고, 결국 자기 큐잉 지연으로 자멸한다.

### AIMD가 공정성으로 수렴하는 이유 — Chiu-Jain 벡터 분석

왜 *가산 증가·승산 감소* 조합이 이상화된 공통-feedback 모델에서 공정성을 개선하는지 Chiu와 Jain(1989)의 벡터 분석으로 볼 수 있다. 이는 설계 직관과 기준선을 주지만, 실제 게임 전송의 비동기 ACK·RTT 차이·지연 신호까지 증명하는 모델은 아니다.

모델을 줄인다. 용량 $C$의 병목을 $n$개 흐름이 공유하고, 각 흐름의 송신률을 $x_i$라 하자. 네트워크는 한 비트만 되먹인다 — 총량 $\sum_i x_i$가 $C$를 넘으면 과부하 신호 1, 아니면 0. 모든 흐름이 같은 신호를 보고 같은 *선형* 규칙으로 반응한다고 두면

$$x_i \leftarrow \begin{cases} a_I + b_I\,x_i & (\text{과부하 아님}) \\ a_D + b_D\,x_i & (\text{과부하}) \end{cases}$$

증가는 $(a_I>0,b_I=1)$이면 가산, $(a_I=0,b_I>1)$이면 승산이고, 감소도 같은 식으로 가산·승산이 갈린다. 네 조합(AIAD, AIMD, MIAD, MIMD) 중 어느 것이 공정과 효율 양쪽으로 수렴하는가가 질문이다.

공정성을 한 숫자로 재는 도구가 Jain 공정성 지수다.

$$F(\mathbf{x}) = \frac{\left(\sum_i x_i\right)^2}{n\sum_i x_i^2}, \qquad \frac1n \le F \le 1$$

한 흐름이 전부 차지하면 $F=1/n$, 모두 같으면 $F=1$이다. 이 지수의 두 성질이 분석의 전부다.

첫째, *척도 불변* — 모든 흐름을 같은 배율 $b_D$로 줄이면 $F(b_D\mathbf{x})=F(\mathbf{x})$다. 분자·분모가 똑같이 $b_D^2$만큼 변해 상쇄되기 때문이다. 즉 *승산 감소는 공정성을 건드리지 않는다*. 기하적으로 승산 감소는 원점을 향한 축소라, 운전점을 원점에서 그은 같은 광선 위에 머무르게 한다(비율 보존).

둘째, *가산 증가는 공정성을 키운다* — 모든 흐름에 같은 상수 $a_I$를 더하면 차이 $x_i-x_j$는 그대로지만($\Delta$ 불변) 평균은 $a_I$만큼 오른다. 변동계수 $\mathrm{CV}=\sigma/\mu$에서 분자 $\sigma$는 고정, 분모 $\mu$는 증가하므로 $\mathrm{CV}$가 줄고, $F=1/(1+\mathrm{CV}^2)$ 관계로 $F$가 단조 증가한다. 기하적으로 가산 증가는 $(1,1,\dots,1)$ 방향, 즉 공정선과 나란히 움직이는 평행 이동이라 공정선에 점점 다가선다.

두 성질을 합치면 모델 안에서 AIMD의 한 cycle은 공정성을 낮추지 않는다. 공통 가산 증가는 $F$를 높이고 공통 승산 감소는 $F$를 보존한다. 반복되는 증가가 각 흐름에 같은 절대량으로 적용되고 feedback을 모두가 함께 받으며 rate가 양수로 유지된다는 전제에서 공정선으로 접근한다. MIMD는 비율을 보존해 초기 불공정을 고치지 못하고, 단순 AIAD는 rate 하한이 없으면 음수를 만들 수 있으며 감소가 상대 차이를 키울 수 있다. “선형 조합 중 AIMD가 조건을 만족한다”는 결론은 이 피드백·업데이트 모델의 정리이지 모든 네트워크 제어기의 유일성 정리가 아니다.

고정된 “40주기”, “평균 이용률 90%”는 AIMD 일반 성질이 아니다. 증가량, 감소계수, feedback이 발생하는 overshoot, RTT와 rate clamp에 따라 달라진다. 문서나 테스트에서 수치를 제시하려면 recurrence와 혼잡 판정 순서를 코드로 고정하고 결과를 재현해야 한다.

게임 혼잡 제어는 AIMD를 단순한 기준선으로 쓸 수 있지만, 지연 기반·모델 기반·수신 추정 기반 제어도 가능하다. 공정성은 공짜로 따라오지 않는다. 특히 “최소 송신률을 보장”하며 혼잡 신호를 무시하면 병목을 더 악화시키고 다른 흐름을 굶길 수 있다. 게임이 유지해야 하는 최소 품질은 네트워크에 강제할 권리가 아니라 제품 임계값이다. 허용 rate 아래에서는 업데이트 정밀도·빈도·관심 영역을 줄이고, 그래도 입력·필수 상태 예산을 못 지키면 매치를 거부하거나 연결을 종료한다.

## 13. 혼잡 제어의 진화: Reno, CUBIC, BBR

혼잡 제어는 살아 있는 분야다 — 회선이 변하면 정책도 변한다.

| 세대 | 신호 | 발상 | 비고 |
|---|---|---|---|
| Reno (80년대) | 손실 | AIMD 톱니 | 원형 — 좁고 얕은 회선의 산물 |
| CUBIC (2000년대) | 손실 | 감소 후 3차 곡선으로 복귀 — 큰 BDP 회선에서 빠른 회복 | 여러 운영체제에서 널리 사용 |
| Vegas/지연 기반 (90년대~) | RTT 상승 | 큐가 차기 *전에* 감속 | 손실 기반과 경쟁 시 양보만 하다 굶음 |
| BBR (2016, Google) | 대역폭·RTT 직접 추정 | 병목 용량과 최소 RTT를 측정해 그 운전점에 맞춰 페이싱 | 큐를 채우지 않으면서 처리량 유지 |

손실 외에 지연·전달률을 함께 추정하는 방향은 실시간 트래픽에도 중요하다. 다만 BBR은 “큐가 언제나 빈 최대 처리량”을 보장하지 않는다. 병목 대역폭과 최소 RTT 모델을 갱신하기 위한 probe가 queue를 만들 수 있고, 버전과 경쟁 알고리즘에 따라 공정성·지연 결과가 달라진다. 패치 전송에 BBR을 채택해도 자동으로 빨라지는 것이 아니며 CDN 경로, 병목, receiver와 다른 트래픽을 포함해 A/B 측정해야 한다.

Vegas의 사례에서 배울 교훈 하나는 *신호가 다른 정책의 공존을 따로 검증해야 한다*는 점이다. 지연 기반 흐름은 queue를 먼저 감지해 줄이는 동안 손실 기반 흐름이 계속 늘어 불리해질 수 있다. 해결은 혼잡을 무시하는 고정 하한이 아니라 AQM·pacing·우선순위가 통제된 네트워크, 품질 단계 하향, 다른 제어기와의 coexistence 테스트다.

## 14. Head-of-Line Blocking의 해부

게임이 TCP를 떠난 단 하나의 이유를 메커니즘으로 정리한다. 세그먼트 N이 유실되고 N+1~N+5가 도착한 상황:

```text
수신 버퍼:  [N-1까지 전달됨] [구멍 N] [N+1][N+2][N+3][N+4][N+5] ← 도착해 있음
                              ↑
            애플리케이션은 여기서 멈춘 채 N의 재전송을 기다린다
복구 시간:  손실 감지(중복 ack 3개 또는 RTO) + 재전송 왕복 — 대략 1 RTT 규모, 최악 수백 ms
            (뒤 데이터가 이미 도착해 있으면 구멍이 복구될 때까지의 남은 대기는 그보다 짧을 수 있다)
```

이 동안 게임에 일어나는 일 — N+1~N+5에 담긴 *더 새로운 스냅샷들이 커널 버퍼에 있는데도* 게임은 받지 못한다. 복구가 끝나면 묵은 데이터가 한꺼번에 쏟아진다(버스트). 즉 TCP 게임의 손실 체감은 "조금 나빠짐"이 아니라 "멈췄다가 빨리감기"다.

HoL은 스트림 *의미론의 필연* 이지 구현 결함이 아니라는 점이 중요하다. "순서대로 빠짐없이"를 약속하는 한 구멍 앞에서 기다리는 것 외에 방법이 없다. 응용이 서로 독립적인 순서 채널로 데이터를 분리하면 한 채널의 구멍이 다른 채널의 전달까지 막는 범위를 줄일 수 있다.

## 15. 게임 서비스에서 만나는 TCP 성능 문제

게임플레이는 UDP로 갔지만, 백엔드는 TCP 위에 산다. 운영에서 만나는 단골 문제와 이 글의 지식이 연결되는 지점:

- **작은 API 호출에 주기적인 지연 봉우리가 생김**: 패킷 캡처로 작은 쓰기, ACK 시각, 애플리케이션 flush, 런타임 버퍼링을 함께 확인한다. Nagle과 delayed ACK의 상호작용이 원인이면 `TCP_NODELAY`가 도움이 되지만, 무조건 켜기 전에 메시지를 한 번에 직렬화하는지와 작은 패킷 증가도 확인한다.
- **대륙 간 전송이 느림**: [11절의 수신 윈도](#11-흐름-제어-수신-윈도)와 BDP 산수를 확인한다. 윈도 스케일링, 병렬 연결 또는 가까운 미러를 검토한다.
- **로드밸런서 뒤 연결 끊김**: 유휴 연결의 LB 타임아웃 — TCP keepalive 또는 응용 ping 주기를 LB 타임아웃보다 짧게.
- **다운로드가 게임플레이를 죽임**: 같은 병목 회선에서 패처가 큐를 채워 게임 UDP의 지연이 치솟을 수 있다. 패처의 적응형 속도 제한, 플레이 중 우선순위 하향, AQM이 있는 경로, 적합한 혼잡 제어를 실측해 조합한다. 특정 혼잡 제어 알고리즘 하나가 모든 경로에서 해결책인 것은 아니다.
- **모바일에서 첫 요청만 느림**: 무선 절전에서 깨어나는 시간과 DNS·전송·TLS 핸드셰이크 연쇄를 분해한다. 연결 재사용과 세션 재개가 왕복을 줄인다. 0-RTT를 쓴다면 재생 공격이 가능한 요청을 배제하거나 멱등성 키로 보호한다.
- **부하 테스트에서 accept 실패**: SYN 백로그·파일 디스크립터 한도 — 커널 큐와 프로세스 자원 한계를 함께 확인한다.

TCP 성능 진단에서는 왕복 횟수, 혼잡·흐름 윈도, 송수신 큐가 핵심 축이지만 애플리케이션 직렬화, 런타임 정지, DNS·TLS, 프록시와 서버 처리도 같은 지연에 섞인다. 양 끝의 애플리케이션 타임스탬프와 패킷 캡처를 맞춰 어느 구간에서 시간이 소비됐는지 분해해야 한다.



---

## 결론

전송 프로토콜 선택은 패킷 형식보다 응용이 필요로 하는 순서와 실패 의미를 정하는 일이다. TCP는 신뢰 바이트 스트림과 흐름·혼잡 제어를 제공하고, UDP는 최소한의 다중화 위에서 응용이 필요한 의미를 직접 정의하게 한다.

소켓과 프로토콜의 실제 비용은 버퍼, 재전송, 혼잡, head-of-line blocking, 연결 상태에서 드러난다. 이를 패킷과 큐의 시간축으로 측정하고 데이터의 수명에 맞춰 선택해야 한다.
