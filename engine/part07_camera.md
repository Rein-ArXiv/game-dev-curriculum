## 들어가며

카메라는 플레이어가 게임을 보는 유일한 창인데도, 엔진 기능 목록에서 자주 빠진다. 렌더링 쪽에서는 뷰·투영 행렬의 수학으로 환원되고, 게임플레이 쪽에서는 "캐릭터 뒤에 붙이면 되는 것"으로 치부된다. 그 사이에 실제 일감이 있다 — 따라가되 멀미 나지 않게, 벽을 뚫지 않게, 전투의 타격감을 흔들림으로 전하게, 컷씬과 게임플레이 사이를 매끄럽게 건너가게.

이 글은 게임플레이 카메라 시스템을 다룬다. 스프링-댐퍼 팔로우와 데드존, 스프링 암의 충돌 처리, 노이즈 기반 셰이크, 카메라 스택과 블렌딩, 3인칭 궤도 카메라의 입력 결합, 그리고 FOV와 멀미 배려까지 — 뷰 행렬을 *만들기 직전까지* 의 모든 결정이 주제다. 변환의 수학 자체(행렬·쿼터니언·투영)는 전제로 깔고 출발한다.

## 1. 카메라 상태와 뷰 행렬의 분리

카메라 시스템의 첫 설계 결정은 *상태와 출력의 분리* 다. 카메라의 상태는 게임 공간의 위치·회전·FOV이고, 뷰·투영 행렬은 그 상태에서 매 프레임 *유도되는 출력* 이다.

```cpp
struct CameraState {
    Vec3  position;
    Quat  rotation;     // 오일러가 아니라 쿼터니언 — 블렌딩·셰이크 합성 때문이다
    float fovY;         // 수직 FOV (라디안)
    float nearZ, farZ;
};
// 뷰 행렬은 소비 시점에 유도한다. 상태를 행렬로 들고 다니면 블렌딩이 망가진다.
Mat4 ViewOf(const CameraState& c) { return Inverse(TRS(c.position, c.rotation, Vec3{1,1,1})); }
```

행렬이 아니라 (위치, 쿼터니언, FOV)를 상태로 두면 각 성분의 의미에 맞는 합성이 가능하다. 행렬을 성분별로 보간하면 회전과 직교성이 일그러지지만, 회전은 쿼터니언 slerp로, 위치는 선형 보간으로 다룰 수 있다. 셰이크도 행렬을 직접 변형하지 않고 위치·회전 오프셋으로 합성할 수 있다.

갱신 순서는 카메라가 어느 시간축의 대상을 읽는지 명시해야 한다. 단일 가변 스텝 루프라면 게임 로직·물리 뒤에 카메라를 갱신하고 렌더가 그 결과를 소비하는 순서가 자연스럽다. 고정 물리 틱과 가변 렌더 틱을 분리한 엔진에서는 물리의 최신 discrete 변환이 아니라 렌더 시각으로 보간한 대상을 카메라가 따라가야 한다. 공통 불변식은 카메라가 읽은 타깃과 화면에 그린 타깃이 같은 렌더 시각을 나타내야 한다는 것이다.

## 2. 팔로우 카메라: 스프링-댐퍼와 데드존

목표 위치에 카메라를 그대로 붙이면(하드 어태치) 캐릭터의 모든 미세한 움직임 — 계단의 덜컥임, 착지의 튕김 — 이 화면 전체의 흔들림이 된다. 카메라는 대상을 *따라가되 걸러야* 한다. 표준 도구는 임계 감쇠 스프링(critically damped spring)이다.

```cpp
// 목표가 이 스텝 동안 고정되었다고 보고 임계 감쇠 해를 정확히 적분한다.
// smoothTime은 응답의 시간 척도이며, omega = 2 / smoothTime으로 둔다.
Vec3 SpringFollow(Vec3 current, Vec3& velocity, Vec3 target,
                  float smoothTime, float dt) {
    dt = Max(dt, 0.0f);                  // 다항식·지수 항이 같은 dt를 쓰도록 입구에서 정규화
    float omega = 2.0f / Max(smoothTime, 1e-4f);
    float decay = Exp(-omega * dt);

    Vec3 x0 = current - target;
    Vec3 j1 = velocity + x0 * omega;

    Vec3 next = target + (x0 + j1 * dt) * decay;
    velocity = (velocity - j1 * omega * dt) * decay;
    return next;
}
```

지수 감쇠 lerp(`current + (target-current) * (1-exp(-k·dt))`)와 달리 속도 상태를 가지므로 속도 연속성을 만들 수 있다. 위 식은 **스텝 동안 목표가 고정된 임계 감쇠계**의 닫힌 해다. 고정 목표에 대한 수치 적분 오차는 없지만, 움직이는 목표를 프레임마다 표본화하는 전체 시스템까지 완전히 프레임레이트 독립이 되는 것은 아니다. 임계 감쇠는 진동을 없애지만 임의의 초기 속도와 이동 목표에서 한 번의 교차까지 보편적으로 금지하지도 않는다. 오버슈트가 허용되지 않는 제약이라면 결과를 목표 쪽으로 클램프하고 그 축의 속도를 재설정해야 한다.

축마다 `smoothTime`을 다르게 둘 수 있다. 수평은 빠르고 수직은 느리게 시작해 플레이테스트와 프레임 시간 분포로 조정한다. 점프·착지의 수직 운동을 카메라가 그대로 복제하면 화면 전체가 움직여 멀미를 유발할 수 있기 때문이다. `0.05~0.15s`와 `0.3~0.5s` 같은 값은 가능한 시작점이지 장르 전체의 상수가 아니다.

**데드존**은 스프링 앞단의 필터다 — 대상이 화면 중앙의 작은 사각형 안에서 움직이는 동안은 카메라가 아예 안 움직인다. 정밀 조작(좁은 발판 점프)을 하는 동안 화면이 미동도 하지 않는 안정감을 주고, 대상이 존을 벗어나는 순간부터 스프링이 잡는다. **룩어헤드**는 반대 방향의 보정이다 — 이동 방향으로 카메라를 미리 밀어, 플레이어가 *가려는 곳* 을 보여 준다. 진행 방향이 급변하는 게임일수록 룩어헤드 자체에도 스프링을 걸어 출렁임을 막는다.

## 3. 스프링 암과 충돌

3인칭 카메라의 기본 자세는 "대상 뒤 거리 d"이고, 그 d를 유지하는 가상의 막대가 스프링 암이다. 문제는 그 막대가 벽을 관통할 때다 — 카메라가 벽 너머로 나가면 화면이 지오메트리 안을 비추고, 컬링·클리핑이 깨진 화면이 나온다.

해법의 골격은 스윕(sweep)이다.

```cpp
// 피벗(대상 머리쯤)에서 이상적 카메라 위치까지 구를 스윕한다.
// 구 반지름은 near plane 크기와 허용 여백에서 정한다.
// 구 스윕은 카메라 절두체를 보수적으로 근사할 뿐, near plane 사각형과 동일하지 않다.
float armLen = Max(0.0f, idealDistance);
if (SweepSphere(pivot, idealDir, idealDistance, cameraRadius, &hit))
    armLen = Max(0.0f, hit.distance);            // 막힌 곳까지만 줄인다 (즉시)
float springLen = SpringFollow1D(currentLen, vel, armLen, /*halfLife=*/0.3f, dt); // 늘리기: 천천히
if (armLen < springLen) {                         // 막힘으로 잘리는 구간: 즉시 줄이고 속도 재설정
    currentLen = armLen;
    vel = 0;
} else {
    currentLen = Min(armLen, Max(0.0f, springLen));  // 음수 길이 방지
}
```

비대칭이 핵심 규칙이다 — *줄이기는 즉시, 늘리기는 스프링으로*. 벽 관통은 한 프레임도 허용할 수 없으니 즉시 줄이고, 장애물이 사라졌을 때 원래 거리로 *튕겨* 돌아가면 그 자체가 또 하나의 화면 출렁임이므로 천천히 푼다. 점 레이보다 부피 스윕을 쓰는 이유는 실제 가시 부피가 점이 아니기 때문이다. 다만 구는 near 평면의 사각형이나 전체 절두체와 같지 않으므로 얇은 모서리에서는 과보호하거나 놓칠 수 있다. 필요한 품질에 따라 다중 레이, 캡슐·박스 스윕, 최종 near-plane 코너 검사를 더한다. sweep이 시작부터 overlap으로 실패하거나 teleport로 피벗이 순간이동하면 법선과 목표 거리가 불안정하므로, 이때는 스프링 대신 안전한 최소 거리로 스냅하고 `vel`을 0으로 두는 별도 경로를 둔다.

가늘고 작은 장애물(난간·가로등)마다 카메라가 덜컥이며 줄어드는 것도 문제다. 채널 분리로 푼다 — 카메라 충돌 채널에서 작은 동적 오브젝트·다른 캐릭터를 빼고, 큰 정적 지오메트리만 남긴다. 그래도 남는 가림(수풀 따위)은 거리 조절 대신 머티리얼 페이드(가린 물체를 반투명하게)로 처리하는 편이 화면이 조용하다.

## 4. 카메라 셰이크

셰이크는 타격감·폭발·긴장을 전달하는 가장 싼 연출이지만, 잘못 만들면 가장 빨리 멀미를 부른다. 두 가지 원칙이 품질을 가른다.

**원하는 주파수 대역을 설계한다.** 매 프레임 독립 난수는 나이퀴스트 근처까지 에너지가 퍼진 백색 잡음이라 거칠게 보인다. 연속 노이즈, 필터링한 난수, 감쇠 진동의 조합으로 저주파 충격과 고주파 진동을 분리한다. Perlin 계열은 가능한 선택 중 하나이며, 축마다 상관되지 않은 시드나 회전된 기저를 사용한다.

**이동과 회전의 역할을 분리한다.** 회전 셰이크는 작은 각도로도 화면 전체에 강하게 느껴지고 충돌 부피를 옮기지 않는다. 위치 셰이크는 폭발의 충격이나 근거리 시차를 표현할 수 있지만 카메라를 지오메트리 안으로 밀 수 있으므로 충돌 제약 앞에서 합성하거나 허용 변위를 제한해야 한다. 어느 한쪽만 정답은 아니다. 멀미 옵션에서는 두 성분을 독립적으로 감쇠하거나 끌 수 있어야 한다.

```cpp
// trauma 기반 셰이크 — 이벤트는 trauma 를 더하기만 하고, 감쇠와 매핑은 시스템이 맡는다.
struct CameraShake {
    float trauma = 0;                       // [0,1]. 폭발 +0.6, 피격 +0.3 식으로 가산
    float decayRate = 1.5f;                 // 초당 trauma 감쇠량
    float freq = 12.0f;                     // 노이즈 좌표 진행률 (엄격한 cutoff/샘플링 주파수와 다름)
    float maxYaw = 0.05f, maxPitch = 0.05f, maxRoll = 0.03f;  // 최대 각 진폭(rad)
    int   seed0 = 0, seed1 = 1, seed2 = 2;  // 축마다 다른 노이즈 계열
    void AddTrauma(float amount) {
        if (!(amount > 0) || !std::isfinite(amount)) return;
        trauma = Min(1.0f, trauma + amount); // [0,1] 상한 유지
    }
    void Update(float dt) {
        if (!(dt > 0) || !std::isfinite(dt)) return;    // 음수·비유한 dt 무시
        trauma = Max(0.0f, trauma - decayRate * dt);
    }
    Quat  Offset(float t) const {
        float amp = trauma * trauma;        // 제곱 매핑 — 작은 trauma 는 거의 안 흔들리게
        float yaw   = maxYaw   * amp * Perlin1D(t * freq, seed0);
        float pitch = maxPitch * amp * Perlin1D(t * freq, seed1);
        float roll  = maxRoll  * amp * Perlin1D(t * freq, seed2);
        return QuatFromEuler(pitch, yaw, roll);
    }
};
```

trauma의 제곱(또는 세제곱)을 진폭으로 쓰는 매핑이 요점이다 — 잔챙이 이벤트가 누적돼도 화면은 조용하고, 큰 이벤트만 크게 흔들린다. 셰이크 결과는 1절의 카메라 상태에 *마지막에 합성되는 오프셋* 으로 둔다 — 팔로우·충돌 로직이 셰이크에 오염되지 않고, 셰이크 끄기(접근성 옵션!)가 한 줄이 된다. 다만 회전·FOV 오프셋도 near 평면 사각형이 쓸고 지나가는 실제 부피를 바꾸므로, 셰이크를 충돌 뒤에 무조건 더하면 가시 부피가 지오메트리 안으로 들어갈 수 있다. 충돌 전에 합성하거나, 합성 후 최종 유효성을 검사해 위반 시 오프셋을 줄이는 경로를 둔다. 충돌 스윕의 구 반경으로 최대 FOV·near 평면·회전을 포괄해 보호한다면 그 상한을 명시한다.

## 5. 카메라 스택과 블렌딩

실제 게임에는 카메라가 여럿이다 — 기본 팔로우, 조준 카메라, 대화 카메라, 컷씬 레일, 사망 연출. "지금 어느 카메라인가"와 "어떻게 건너가는가"를 관리하는 것이 카메라 디렉터다.

한 가지 실용적 구조는 카메라 요청을 우선순위와 활성 조건으로 평가하는 디렉터다. 후보는 상태를 계산하는 가상 카메라일 수 있지만 모두를 매 프레임 완전 평가할 필요는 없다. 비활성 후보의 값비싼 추적·충돌 계산은 생략하고, 선택되거나 블렌드에 참여할 때 필요한 상태를 준비한다. 단순 스택, 상태 머신, 점수 기반 선택 중 어느 구조든 동일 우선순위 충돌과 중단된 블렌드의 규칙을 명시해야 한다.

```cpp
// 전환: 이전 활성 카메라의 '출력 상태'를 스냅샷해 두고 새 카메라와 섞는다.
CameraState Blend(const CameraState& a, const CameraState& b, float t) {
    float s = SmoothStep(t);                       // 이즈 곡선 — 선형은 기계적으로 보인다
    float focalA = 1.0f / Tan(0.5f * a.fovY);     // 센서 크기를 2로 정규화한 초점거리
    float focalB = 1.0f / Tan(0.5f * b.fovY);
    float focal = Lerp(focalA, focalB, s);
    return { Lerp(a.position, b.position, s),
             Slerp(a.rotation, b.rotation, s),     // 행렬이 아니라 쿼터니언이라 가능
             2.0f * Atan(1.0f / focal),
             Lerp(a.nearZ, b.nearZ, s),
             Lerp(a.farZ, b.farZ, s) };
}
```

FOV 각도를 직접 lerp하면 화면 확대율이 비선형으로 변한다. 위 예시는 동일한 센서 크기를 가정하고 정규화한 초점거리를 보간한다. near/far 평면이 크게 달라지면 깊이 정밀도와 temporal history도 달라지므로, 가능하면 공통 클립 평면을 쓰고 불연속 변경은 카메라 컷으로 취급한다.

블렌딩의 함정은 *위치 경로* 다 — 두 카메라 사이에 벽이 있으면 보간 경로가 벽을 통과한다. 짧은 전환도 공간에 따라 눈에 띌 수 있으므로 경로 충돌을 검사하고, 해결할 수 없으면 컷(즉시 전환)을 선택한다. 컷 직후에는 모션 블러·TAA의 히스토리를 리셋해야 잔상이 남지 않는다.

컷씬 레일은 스플라인 위에 카메라를 태우는 것이다 — 위치는 Catmull-Rom 스플라인의 호 길이 매개화로(등속 이동), 시선은 타깃 룩앳 또는 키프레임 회전의 slerp로. 곡선 도구는 보간 계층의 재사용이고, 카메라 시스템 고유의 일은 "게임플레이 카메라 ↔ 레일"의 출입 블렌딩이다.

## 6. 3인칭 궤도 카메라와 입력

3인칭 카메라의 회전은 플레이어 입력(마우스·우측 스틱)이 직접 모는 요·피치 궤도다.

- **요는 순환하고 피치는 제한** — 허용 범위는 캐릭터·충돌·조준 설계로 정한다. 월드 업 벡터로 `lookAt`을 만들 때 시선이 업과 평행해지면 기저를 만들 수 없고, 요·피치 매개화도 극점에서 요의 의미를 잃는다. 피치 제한은 이 극점과 뒤집힘을 피하는 정책이지 모든 오일러 짐벌락을 해결하는 일반 기법은 아니다.
- **상태는 요·피치 두 스칼라로 들고, 회전은 `yawQuat ⊗ pitchQuat`로 합성** — 자유 쿼터니언 누적은 롤이 스며들어 수평선이 기운다. 궤도 카메라는 의도적으로 자유도를 2로 제한한 시스템이다.
- **감도 곡선**: 스틱 입력에 데드존 → 응답 곡선 → 최대 각속도를 적용한다. 마우스 원시 델타에는 예측 불가능한 OS 가속을 강제하지 않는 것이 일반적이지만, 사용자가 선택한 가속 곡선과 접근성 보조는 지원할 수 있다. "1:1"도 장치 count, 감도, FOV와 화면 회전각 사이의 계약을 명확히 해야 의미가 있다.
- **자동 보정**: 이동 중 입력이 없으면 카메라 요를 이동 방향으로 서서히 정렬(스프링), 전투 중에는 타깃 쪽으로 약하게 끌기. 강도가 세면 플레이어와 카메라가 조종권을 다투는 느낌이 나므로, 입력이 들어오는 순간 보정을 즉시 끊는 것이 철칙이다.

이 모든 회전 갱신은 캐릭터 이동 *입력 해석* 과 얽힌다 — "앞으로"는 캐릭터 기준이 아니라 카메라 기준이기 때문이다. 이를 지난 프레임 카메라에 무조건 의존시키면 한 프레임의 입력 지연이 생긴다. 보통은 입력으로부터 **카메라 방향 의도**를 먼저 계산해 그 요를 이동 벡터 해석에 쓰고, 물리 결과가 나온 뒤 충돌·가림 제약을 적용한 최종 카메라 위치를 계산한다. 방향 의도와 제약된 출력 자세를 분리하면 업데이트 순환 의존을 끊을 수 있다. 엔진 구조상 이 분리가 어렵다면 지난 프레임 요는 가능한 절충안이지 보편적인 표준 해법은 아니다.

## 7. FOV, 컷, 그리고 멀미

FOV는 카메라의 마지막 표현 수단이다. 질주·부스트에서 FOV를 넓히면 속도감을 줄 수 있고, 조준에서는 좁혀 확대 효과를 만든다. 변화량은 화면 크기, 기준 FOV, 종횡비와 멀미 테스트로 정하며 장르 전체에 통하는 각도 범위는 없다. 계단형 전환이 의도된 컷이 아니라면 초점거리 또는 확대율 공간에서 연속적으로 보간한다.

멀미는 카메라 시스템의 접근성 문제다. 원인의 대부분이 *시각 정보와 전정 기관의 불일치* 이고, 카메라가 만드는 불일치는 줄일 수 있다.

| 유발 요인 | 완화 |
|---|---|
| 잦은 수직 출렁임 | 수직 스프링을 느리게(2절), 보브(머리 흔들림) 옵션화 |
| 회전 셰이크 과다 | 셰이크 강도 슬라이더·끄기 옵션(4절의 합성 분리 덕에 한 줄) |
| 좁은 FOV + 빠른 회전 | FOV 옵션 제공(PC 표준), 회전 최대 각속도 제한 |
| 가속 중 시점 회전 강제 | 자동 보정 강도 옵션, 컷씬 중 카메라 강탈 최소화 |

"카메라 옵션이 많은 게임"은 사치가 아니라 기본기다 — 셰이크·보브·자동 보정·FOV·감도 곡선이 각각 독립 옵션으로 빠질 수 있는 구조(상태 합성의 분리)가 이 글 전체 설계의 부산물이라는 점이 요점이다.

## 8. 구도와 다중 타깃

카메라는 단순히 한 점을 따라가는 장치가 아니라, 플레이어가 봐야 할 정보를 화면 안에 배치하는 시스템이다. 이 배치를 구도(composition)라고 본다. 추적 대상의 월드 위치만으로는 부족하고, 대상이 화면의 어느 지점에 있어야 하는지까지 상태에 포함해야 한다.

```text
world target -> desired screen position -> camera offset/orientation/FOV
```

어깨너머 3인칭 카메라가 캐릭터를 화면 중앙이 아니라 좌하단에 두는 이유는 조준선과 진행 방향의 시야를 확보하기 위해서다. 대화 카메라는 두 인물의 얼굴과 시선 방향을, 격투 게임 카메라는 두 캐릭터를 동시에, 전략 게임 카메라는 선택 유닛과 위협 방향을 함께 보여야 한다.

다중 타깃 카메라의 기본은 bounding volume이다.

```cpp
struct CameraTarget {
    Vec3 position;
    float weight;
    float radius;
};

Vec3 center = WeightedAverage(targets);
float radius = BoundingSphereRadius(targets, center);
```

카메라는 `center`를 바라보고, 모든 타깃이 안전 영역 안에 들어오도록 거리나 FOV를 조정한다. 그러나 거리와 FOV는 같은 문제가 아니다. 거리를 뒤로 빼면 원근감이 줄고 배경이 더 많이 보이며, FOV를 넓히면 가장자리 왜곡과 멀미 위험이 늘어난다. 격투 게임은 보통 거리를 조정하고, 일시적 부스트나 조준은 FOV를 조정한다. 거리 하한은 구 중심을 바라볼 때 구 반지름 r이 세이프 프레임의 유효 반각 θ 안에 들어오는 조건에서 나온다. 중심에서 거리 d에 있으면 구가 차지하는 각 반지름은 대략 `asin(r/d)`이므로, r이 화면을 넘지 않게 하려면 `d >= r / sin(θ)`로 둔다. θ는 수평·수직 유효 반각 중 작은 값(세이프 프레임과 종횡비를 반영)을 쓴다. 이는 프레이밍 하한일 뿐 clipping·가림 해결과는 별개다.

화면 안전 영역도 필요하다. 타깃이 화면 끝에 딱 붙으면 UI, 화면 흔들림, 플랫폼별 overscan, 스트리밍 지연에서 쉽게 잘린다. 따라서 구도 계산은 보통 NDC의 `[-1,1]` 전체가 아니라 더 안쪽의 safe frame을 사용한다.

```text
example safe frame x: [-0.75, 0.75]
example safe frame y: [-0.65, 0.65]
```

구도 시스템의 실패는 "대상이 보인다/안 보인다"보다 미묘하다. 플레이어가 반응해야 할 위협을 너무 늦게 보여 주거나, 이동 방향보다 캐릭터의 과거 위치를 더 크게 보여 주거나, 카메라가 구도를 맞추려고 플레이어 입력을 이기는 순간 체감이 나빠진다. 따라서 카메라 목표에는 위치뿐 아니라 *의도* 가 들어간다.

- 이동 중: 진행 방향과 착지 지점 우선
- 전투 중: 타깃과 공격 예고 우선
- 탐험 중: 지형과 목표 방향 우선
- 컷씬 중: 연출 구도 우선

이 의도는 카메라 스택의 우선순위와 별개로, 같은 활성 카메라 안에서 구도 가중치를 바꾸는 입력이다.

## 9. 시간축: 물리 틱, 렌더 틱, 보간

카메라 떨림의 많은 원인은 수학이 아니라 시간축이다. 물리는 고정 틱에서 돌고, 렌더링은 가변 주기로 돌며, 입력은 OS 이벤트나 폴링 시점에 들어온다. 카메라가 어느 시점의 대상을 따라가는지 명확하지 않으면 대상은 부드러운데 카메라만 떨리거나, 반대로 카메라는 부드러운데 캐릭터가 화면 안에서 미끄러진다.

표준 구조는 시뮬레이션 상태와 렌더 상태를 분리한다.

```text
physics tick n-1: target_prev
physics tick n:   target_curr
render time:      alpha between n-1 and n

render_target = Lerp(target_prev, target_curr, alpha)
camera updates from render_target
```

물리 결과를 보간한 렌더 타깃을 카메라가 따라가면 고정 틱의 계단이 화면에 직접 보이지 않는다. 반대로 카메라가 물리 tick의 discrete 위치를 그대로 따라가면 스프링이 있어도 입력이 계단형이라 미세 떨림이 남는다.

스프링도 시간 적분 문제다. 단순 Euler 적분으로 스프링을 구현하면 큰 `dt`에서 오버슈트하거나 폭발할 수 있다. 고정 목표에 대한 닫힌 해나 안정화된 근사를 쓰면 적분 오차와 큰 `dt` 민감도를 줄일 수 있다. 그러나 목표가 프레임 사이에 움직이고 충돌 제약이 비선형으로 개입하면 결과는 여전히 표본화 주기와 업데이트 순서의 영향을 받는다. 탭 전환이나 긴 hitch 후에는 `dt`를 상한으로 clamp하거나, 여러 작은 step으로 나누어 카메라가 한 프레임에 멀리 순간이동하지 않게 한다.

```text
effectiveDt = min(realDt, 1/15초)
```

렌더러의 temporal 기법도 카메라 시간축과 연결된다. TAA, motion blur, temporal upsampling은 이전 프레임 카메라 행렬과 현재 프레임 행렬을 사용한다. 카메라 컷, teleport, 큰 FOV 변화, projection jitter reset이 있으면 히스토리를 유지하면 안 된다. 카메라 시스템은 렌더러에 다음 신호를 넘겨야 한다.

```cpp
struct CameraFrameInfo {
    CameraState current;
    CameraState previous;
    bool cut;              // temporal history reset
    bool teleport;         // motion vector clamp
    Vec2 jitter;           // projection jitter for temporal AA
};
```

이 경계가 없으면 카메라 전환은 논리적으로 맞아도 화면에는 잔상과 번짐으로 나타난다.

리플레이 재현성도 시간축의 문제다. 물리 tick 상태와 입력·노이즈 seed가 같아도 가변 presentation dt와 alpha가 다르면 스프링 추적·충돌·셰이크 합성이 달라져 화면이 어긋난다. 물리 결과를 보간한 렌더 시각은 최신 권위 상태보다 한 tick 지연된 시점을 나타내므로, 픽셀 단위 재현이 필요하면 render dt·alpha·카메라 상태 또는 고정 presentation 정책을 함께 기록한다. state hash 결정론은 게임 상태 비교이고, 이 시각적 결정론과는 별개다.

## 10. 가림 처리 정책

스프링 암 충돌은 카메라가 벽 밖으로 나가는 문제를 막지만, 타깃이 보이는지는 별개의 문제다. 카메라와 타깃 사이에 장애물이 있으면 선택지는 여러 가지다.

| 정책 | 장점 | 실패 |
|---|---|---|
| 카메라 당기기 | 타깃을 확실히 보이게 함 | 좁은 공간에서 과도한 줌인과 멀미 |
| 장애물 투명화 | 카메라 안정성 유지 | 월드 규칙이 깨져 보일 수 있음 |
| 카메라 옆으로 밀기 | 거리 유지 | 벽과 코너에서 미끄러짐 |
| 타깃 실루엣 표시 | 안정적이고 저렴 | 몰입감이 낮아질 수 있음 |
| 컷 또는 고정 카메라 | 명확함 | 플레이어 조종권 감소 |

좋은 시스템은 하나의 정책만 쓰지 않는다. 가까운 얇은 장애물은 투명화하고, 큰 벽은 카메라를 당기며, 당김이 너무 심하면 shoulder side를 바꾸거나 컷한다. 정책 선택은 장애물의 크기, 지속 시간, 타깃과의 거리, 현재 카메라 모드에 따라 달라진다.

가림 판정은 점 하나가 아니라 목표의 중요한 영역을 기준으로 해야 한다.

```text
target samples:
  head
  chest
  feet
  aim point
```

머리와 조준점은 보여야 하지만 발은 가려져도 될 수 있다. 샘플별 가중치를 두면 카메라가 모든 점을 무리하게 보이려 하지 않는다. 이 구조는 보스전처럼 중요 부위가 여러 개인 대상에도 그대로 확장된다.

가림 정책에는 hysteresis가 필요하다. 한 프레임 보였다고 투명화를 끄고 다음 프레임 다시 켜면 장애물이 깜빡인다. 최소 유지 시간, alpha fade, 거리 임계값의 진입·이탈 분리를 둔다.

```text
example: occluded for 0.12s -> fade obstacle
example: clear for 0.25s    -> restore obstacle
```

카메라 충돌 채널과 게임플레이 충돌 채널은 다르게 설계해야 한다. 총알은 통과하지 못하지만 카메라는 무시해야 하는 장식물, 플레이어는 지나갈 수 있지만 시야는 가려야 하는 수풀처럼 요구가 다르다. 채널 설계가 없으면 카메라 로직이 물리 월드의 우연한 태그 조합에 끌려다닌다.

## 11. 디버깅과 계측

카메라 버그는 “기분이 나쁘다”로 보고되는 경우가 많다. 따라서 내부 상태를 화면에 보여 줄 수 있어야 한다.

- 피벗, 이상적 위치, 충돌 후 위치
- 스프링 속도와 half-life
- 데드존과 safe frame
- 활성 가상 카메라와 블렌드 가중치
- 스프링 암 hit point와 hit normal
- occlusion sample별 가시성
- 현재 FOV, 셰이크 trauma, 보정 강도
- temporal cut/reset 플래그

디버그 뷰는 카메라가 왜 그 위치에 있는지 설명해야 한다. 최종 행렬만 보이면 원인을 알 수 없다. 의도 위치, 제약 적용 후 위치, 연출 오프셋 후 위치를 단계별로 그리면 어느 계층이 문제를 만들었는지 분리된다.

계측 지표도 필요하다.

```text
평균/최대 카메라 속도와 각속도
스프링 암이 줄어든 시간 비율
타깃이 safe frame 밖에 있던 시간
occlusion 정책별 발동 횟수
컷/히스토리 리셋 횟수
플레이어 입력 중 자동 보정이 개입한 시간
```

이 지표들은 QA와 접근성 조정의 근거가 된다. 예를 들어 멀미 신고가 많은 구간에서 수직 카메라 속도와 회전 셰이크가 높게 나온다면 원인을 정량화할 수 있다. 반대로 전투 가독성이 낮은 구간에서 타깃이 safe frame 밖에 머문 시간이 길다면 구도 정책을 조정해야 한다.

리플레이와 디버깅을 위해 카메라 입력과 모드 전환도 기록해야 한다. 카메라가 게임 상태와 플레이어 입력, 시간, 난수 노이즈에 의존한다면 같은 리플레이에서 같은 카메라가 나오려면 노이즈 seed와 카메라 이벤트도 재현 가능해야 한다. 셰이크가 비결정적 난수를 직접 읽으면 전투 판정은 같아도 화면 재현이 달라진다.

## 결론

카메라 시스템은 여러 겹의 합성이다 — 의도(어느 카메라가 활성인가, 어떤 구도를 원하는가) 위에 추적(스프링·데드존·룩어헤드)이, 그 위에 제약(충돌·가림·safe frame)이, 마지막에 연출(셰이크·FOV 펄스)이 얹힌다. 각 겹이 (위치, 쿼터니언, FOV) 상태에 독립적으로 기여하고 뷰 행렬은 맨 끝에서 한 번 유도되는 구조가, 블렌딩을 가능하게 하고 옵션화를 한 줄로 만들고 각 겹의 디버깅을 분리해 준다.

기억할 규칙 셋. 줄이기는 즉시·늘리기는 스프링(충돌), 불연속 랜덤보다 대역이 제한된 노이즈(셰이크), 해결되지 않는 관통 경로보다 명확한 컷(전환). 위치·회전 셰이크는 역할과 접근성 옵션을 분리한다. 여기에 시간축과 관측성을 더해야 한다. 물리 틱과 렌더 틱 사이의 보간, temporal history reset, 가림 정책의 hysteresis, 디버그 뷰와 지표가 없으면 카메라는 재현하기 어려운 체감 버그의 덩어리가 된다.
